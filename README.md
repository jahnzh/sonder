# Sonder

A dark, mobile-first, self-hosted audiobook PWA inspired by [Vaka](https://github.com/vaka-hq/mobile). React, TypeScript, Vite, Tailwind, Radix dialogs, Fastify, SQLite/Drizzle, and Dexie. No Vaka account is needed.

## Run on this Ubuntu server

Node 24 and Docker are required. The 4 TB drive is mounted at `/mnt/usb_4t_1`. Media lives in `/mnt/usb_4t_1/sonder`; the app refuses to write media to the root filesystem if that mount is missing.

```bash
npm ci
node scripts/setup-local-torrents.mjs
# The setup script generates APP_PASSWORD privately in .env if one is not set.
docker compose build
docker compose up -d --no-build
```

Reading-sync alignment runs on the remote CTC pool hosts, not on this server; set them up with `scripts/install-ctc-workers.sh` (see [CTC pool setup](docs/CTC_WORKER_POOL.md)).

Open **https://sonder.pecori.no** and sign in as `admin` with `APP_PASSWORD` from `.env` (an empty username also signs in as admin). Caddy proxies this domain to the loopback-only app on port 3001; HTTPS cookies are enabled. The site block is recorded in `deploy/audiobooks.caddy`. For development, `npm run dev` starts the frontend at **http://localhost:5173** and the API at port 3001. Stop the production container before running development on the same API port. The server reads `.env` at startup.

`setup-local-torrents.mjs` creates a dedicated `sonder-torrents` Transmission 4 queue using the installed image and the **existing `transmission-openvpn` container’s network**. It does not change the existing daemon or its downloads. Its RPC uses port 9092, requires generated credentials, and is not published on the host. A stable volume marker is checked by both the app and the torrent daemon, so Docker cannot silently redirect media onto the system disk when the HDD is absent. Both incomplete and completed audiobook files are on the HDD. Credentials are written to the ignored, private `.env`; daemon settings live under ignored `data/transmission/`. If the VPN container is recreated with a different private IP, run the setup script again and restart Sonder. The VPN container must be running before the torrent queue starts.

`sonder-torrents` joins the VPN container's network namespace when it starts. A restart of `transmission-openvpn` keeps its container ID but gives it a new namespace, and `sonder-torrents` stays in the old one: its RPC no longer answers at `TRANSMISSION_RPC_URL` and downloads stall (#123). Settings and Activity's Now then say the client cannot be reached and name the fix, `docker restart sonder-torrents`, which makes it join the VPN's current namespace; Transmission resumes the torrents from `incomplete`. The setup script restarts it for the same reason: it compares the two containers' `State.StartedAt` and restarts `sonder-torrents` when the VPN started after it (every start of `sonder-torrents` joins the namespace of that moment, so no label is needed). To do this unattended, install the watcher on the host once from the main checkout: `scripts/install-torrent-watch.sh` (`--print` shows the systemd user unit, `--remove` removes it). It runs `scripts/torrent-vpn-watch.mjs`, which follows `docker events` for the VPN's start and checks every five minutes as a backstop. Once the VPN has stayed up for three minutes it restarts `sonder-torrents` if the VPN started after it, at most three times an hour; at the limit it stops restarting and says so in `journalctl --user -u sonder-torrent-watch.service`. It does nothing when either container is missing or `sonder-torrents` is stopped, and leaves a container on another VPN container's network to the setup script. The Sonder server itself has no Docker access.

Why the VPN restarts: between 2026-10-27 and 2026-11-14 the Docker daemon restarted `transmission-openvpn` 50 times, all with exit code 0 (Docker daemon journal). They came in six episodes: four bursts of 3 to 22 restarts about two minutes apart (2026-10-28, 10-30, 11-09, 11-13; the longest lasted 47 minutes) and single restarts on 11-04 and 11-06. The likely mechanism, from the current start's log: PIA pushes `ping 10, ping-restart 60`, and the image (haugene/transmission-openvpn) remaps OpenVPN's soft restart to SIGTERM ("Remap SIGUSR1 signal to SIGTERM"), so a tunnel that stays silent for 60 s (a PIA server or upstream outage) ends OpenVPN cleanly with exit code 0, and the container's `unless-stopped` policy starts it again until a connection holds. Health checks do not restart it (`SELFHEAL=false`, and no autoheal container runs), and the kernel log of that boot has no out-of-memory kill. The container's own logs from before its last start (2026-11-14, the host restart) are gone, so the OpenVPN message of each exit could not be read. The container lives in `/home/jahn/homelab`, so any change there (another PIA region, other ping options) belongs to that repository.

The app container binds to loopback. Put an HTTPS reverse proxy in front of it for phone access and set `COOKIE_SECURE=true`. PWA installation, OPFS, and service workers require HTTPS or localhost. On first use, add your TorBox key in Settings › Connections to enable cached streaming; without it, magnet links use the local client.

## Local checks and backups

`npm run check` checks the committed `HEAD` in a disposable directory: dependency installation, build/typecheck, unit tests, then browser tests, including extra runs of specs changed against `origin/main`. Uncommitted changes are recorded in the report and are excluded from the snapshot. Use `npm run check -- --ref <commit>` to check another revision. Each invocation has its own logs and reports under `artifacts/ci/`.

Before deploying an existing installation, create a consistent SQLite snapshot with `npm run backup -- data/sonder.db data/backups/before-<change>-$(date +%s).db`. The destination must be new; the command verifies the backup before reporting success. See [local checks and verification](docs/LOCAL_CHECKS.md) for details.

The server also makes a **daily backup** itself (#361), with the same backup function: `<DATA_DIR>/backups/daily-<day>.db`, where the day is the UTC day and its backup is due from 03:00 UTC. The loop checks every 10 minutes, so a server that was down at 03:00 makes the day's backup within 10 minutes of starting (one backup for the latest day, not one per missed day). Every backup passes `PRAGMA integrity_check` before it appears. Whether a backup is due is decided from the recorded successful runs (`backup_runs`) only, never from the file names in the folder, and a recorded day later than today (a clock that ran ahead) is ignored. Each run stores the size and SHA-256 of its verified copy before it publishes it; when a later attempt of the same day finds that file at the day's name (the earlier attempt published it, then failed before it recorded its result), it adopts the file instead of failing, and any other file there is a failure that is never deleted or overwritten. Retention removes older daily backups after a successful run only, and deletes a file only when a successful run names it, it is a regular file directly in the folder, and its size and SHA-256 are still the recorded ones; only such files count toward the 14 kept. It works newest first, one file at a time, and checks each file right before deleting it: opened without following a symlink, a regular file of the recorded size, hashed through that same descriptor, unchanged by a write during the hash, and still the inode the path names; then the path is unlinked at once. The one window it cannot close is between that last check and the `unlink` call (which takes a path): another process writing into the backups folder at that instant could have its file removed. When the rows cannot exceed the 14 kept, no file is read. A missing, replaced, changed or non-regular entry is left alone and its run stops counting. A file that cannot be read or removed stops retention for that run: nothing further is deleted, and Activity › Server shows the run on its Database backups row as succeeded with the reason its old backups were not removed. The `before-*` deploy copies and every other file in the folder are never touched, and a failed run removes nothing. A run claims its day in the database first, so two servers sharing the database never back up the same day at once; a working run renews its claim at each stage and every minute, and only a claim not renewed for 30 minutes is a run whose server stopped or hung, which the next check takes over (after a restart mid-run the day's backup therefore waits up to 30 minutes). Every failure, including an unusable backups folder, is recorded as a failed run with its reason. A run is refused, and shown as failed on the Database backups row of Activity › Server with the reason, when the backup folder has less than 1 GiB free or when it is inside the media root and the media drive check (`REQUIRE_MEDIA_MOUNT`) fails. A failed day is tried again at the next check. The backups stay on the same disk as the database; an off-machine copy is not made.

## Users

Sonder has one administrator (`admin`, password `APP_PASSWORD`) and any number of users, created in Settings → **Users**. Passwords are stored as scrypt hashes; users change their own password in Settings → **Account**. Without `APP_PASSWORD` (development and browser tests) there is no sign-in and every request acts as the admin.

- **Shared:** the catalogue and its files (works, editions, recordings, server copies, ebooks, reading-sync maps). Anyone can add an existing title to their library, stream it and save it on their own device.
- **Per user:** library, favourites, hidden titles, listening progress (still per recording), reader positions, bookmarks, appearance. Device storage is separate per user, and queued writes carry an `X-Sonder-User-Id` header so another tab's sign-in can never receive them (the server answers 409).
- **Admin only:** TorBox, torrents, Prowlarr, AudioBookBay and Library Genesis search, imports, Save to server, fault flags, removing server copies, preparing reading sync, linking ebooks, server settings and user management.

The first start after upgrading copies all existing per-user rows to the admin and leaves the old single-user tables untouched, so the previous version can still run against the same database.

## Addresses and Back

Every page has an address behind the `#` (ADR 0020; the table is in issue #480, "Addresses and the page stack"). `src/routes.ts` is the only code that reads or writes one; `src/navigation.ts` keeps the browser's history as the page stack. The four places are **Library** (`#library`), **Discover** (`#discover`), **Activity** (`#activity`) and **Settings** (`#settings`), in the tab bar on a phone and in the rail on a desktop. A book's pages hang off its Book page `#book/<workId>`: `/audiobook`, `/ebook`, `/sync` (and `/sync/details`), `/chapters`, `/bookmarks`, `/search`, `/match` and `/edit`. Get is a sheet over the page it opens from: `#book/<workId>/get/audiobook` (with `/magnet` for **Paste a magnet link**), `#book/<workId>/get/ebook`, and `#discover/get/<words>` for a recording without a book. A series is `#series/<id>`, its Add sheet `#series/<id>/add`. Activity's parts are `#activity` (Now), `#activity/device` and `#activity/server`, a worker `#activity/server/<worker>`. Settings' pages are `#settings/<page>` (`account`, `appearance`, `playback`, `connections`, `users`, `library`, `app`), and Keyboard shortcuts is `#settings/keyboard`, a page under Playback ("Back to Playback"). Now playing has two addresses, one per face: `#listen/<workId>` and `#read/<workId>`.

Switching place with the tab bar or the rail adds a step for Back, and tapping the tab of the place you are in returns to its first page without adding one. A reload shows the same page and keeps what lies behind it. An address that names nothing, a page not built yet, or a page of the administrator's (Activity's Server and its workers, Get, Settings › Connections, Users, Library and storage) for someone who is not the administrator shows the place's first page, and the address is replaced by it; someone who is not the administrator gets the book's own page at a Get sheet's address. After signing in you land on the address you opened. Back returns a list to where it was scrolled. The installed app starts on the Library.

**Old names.** Addresses from before the redesign keep working for good (#455). Each is one row of the table of old names in `src/routes.ts` (`OLD_NAMES`); reading one opens the page that took its place and replaces the history entry, so Back afterwards does not reopen it:

- `#downloads` (the Downloads page) opens Activity's Now, `#activity`.
- `#reader/<ebook id>` (the reader on its own) opens Now playing's Read face of that ebook's book, `#read/<workId>`, with that edition; a link to an ebook that has been removed shows the Library in its place. There is no reader of its own any more: a book with only an ebook is read on the same Read face, with no narration.
- `#book/<workId>/hardcover` (the Hardcover page) opens the book's match page, `#book/<workId>/match`; an older build's `work-hc-<n>` id opens the work stored as matched to that book (see Hardcover, below).

## Listening workflow

1. **Find a book.** The included public-domain recordings are on the server from the start. **Discover** (`#discover`; **Add a book**, the Library's plus, opens it with its field focused) searches, under **Books**, the server's books, AudiobookDB and Open Library at once, and under **Series** AudiobookDB's series; a result opens its Book page or Series page, and each book row's bookmark button adds it to or removes it from **Want to read**. The Book page (`#book/<workId>`) has **Listen** and **Read** for a book in the library, **Add to library** and **Want to read** for one that is not, and its **Files** group: **Audiobook** (the Audiobook page), **Ebook** (the Ebook page) and **Reading sync**. Filename order is natural, so chapter 2 precedes chapter 10.
2. **Get** (administrator). The Book page's **Get** on its Audiobook row (a book with no recording), **Get another recording** on the Audiobook page, and Now playing's Listen for a book with no recording open the Get audiobook sheet (`#book/<workId>/get/audiobook`). Discover's last group for the administrator, **Search for a recording**, opens the same sheet without a book (`#discover/get/<words>`, "A recording for a new book"): the recording chosen makes the book ("Adds the book to your library."). The sheet searches MyAnonamouse when its session is saved (#911, below), AudioBookBay, and Prowlarr when it is connected, for the title and author (**Search for a recording**); **Language** (English by default, kept on this device; All languages, English, then the languages found) filters it. Each recording row shows the narrator or the release title, format · bitrate · size, and the seeders ("Plays now" for a copy TorBox has). Choose a row and **Get this recording**; the line under the button says what happens ("Plays from TorBox right away.", "Downloads to your server first.", "Plays at once if TorBox has it, else downloads to your server."). The foot of the sheet is built from the bottom: **Get this recording** is pinned to the foot and never moves; above it stands the line that says what it will do, and above that, while a row is chosen whose address is a web page (http or https, no credentials in it), a link to the release's own page that opens in a new tab (#889): **On AudioBookBay**, **On <indexer>** for a Prowlarr result that names its indexer, **On the indexer's page** for one that does not (a refusal after a failed Get stands above them all). Nothing is reserved: with nothing chosen the foot is the button alone, and it grows upward into the list only when there is something to say, scrolling the chosen row into view. The link follows the choice, and a row holds no link. **Preview**, at the left of Get this recording while the chosen row says "Plays now", plays a stretch of that recording before it is got (#889): the server puts the cached release on TorBox (`add_only_if_cached`, never a download), picks its first audio file in Get's order that is neither under 3 MB nor has the word credits, intro, introduction, preface, foreword, sample, epilogue, afterword or outro in its name (else the largest), and serves that file's bytes under a preview id of its own (`/api/discover/previews/<id>/audio`; the client never names an address). It plays in an audio element of its own, not the player: no book is replaced, no listening position written, nothing set in Media Session. It starts at 3:00 in a file over six minutes long (from the start when nothing sounds five seconds after that seek), reads **Stop** with the time played, and stops after two minutes, on another choice, on Get, when the sheet closes, when the page is hidden and when the book starts playing; while the book plays Preview is off ("Pause the book to preview."). A preview makes no library row, recording, acquisition or Activity entry. The sheet ends it on the server when it closes or another release is previewed, and the server ends it 30 minutes after it was made (`torbox_previews`, checked at start and every minute); an ended preview is no longer served. A previewed release stays on the TorBox account for now, whether it is got or not: nothing removes it. Removing what a preview added is a later ticket. A new recording of a book stays linked to the same work, and each recording keeps its own progress. **Load more recordings** pages AudioBookBay. **Other ways to get it**: **Paste a magnet link** (a sheet over Get, `#book/<workId>/get/audiobook/magnet`: the **Magnet link** field and **Get this recording**) and **Import files from this device** ("Uploading · 43%", then "Preparing the audio…" or "Importing…").
   With Prowlarr connected (Settings › **Connections** › Prowlarr: **Address** plus **API key**, stored encrypted; **Test** checks status and counts enabled torrent indexers), Get also searches Prowlarr’s audiobook category (3030) and book categories (7000, kept only when the title marks it as audio). Sonder only reads Prowlarr; indexers are managed there. Each source fills in as it answers, and a failing source shows a short note above the others ("AudioBookBay could not be searched." or "Prowlarr could not be searched.", with the reason and Retry). Releases are merged by info hash, then across sources by normalized title and size within 1%; merged rows list every source. Results sort by title match, then TorBox cache (known hashes only), then seeders. Indexers do not report language, so their releases stay visible under every language filter. Prowlarr download links contain its API key and never reach the browser: the server keeps them for six hours per search and replays them only against the configured Prowlarr address, turning a magnet redirect or `.torrent` file into a magnet. A chosen Prowlarr release then follows the same TorBox check, local queue and validation as any other magnet. Prowlarr results load on the first page only; **Load more recordings** pages AudioBookBay.
   When the server's own connection cannot reach the mirror, set `ABB_PROXY_URL` in `.env` to an HTTP proxy that can (on this server the VPN container's web proxy, `http://127.0.0.1:8118`) and restart Sonder: the AudioBookBay search, release page and magnet requests then go through it, and every other request stays direct (#755). A mirror that cannot be reached shows "The mirror could not be reached." under the source's note, or "The mirror could not be reached through the server's proxy." when the proxy is set. The mirror address is Settings › Connections › AudioBookBay › **Mirror address**.
3. A magnet is checked against TorBox’s cache. A cache hit creates a TorBox torrent with `add_only_if_cached=true` to protect against a cache race. A miss still asks TorBox to take the job without cache-only (`add_only_if_cached=false`). If TorBox cannot take the job, or TorBox is not configured, the magnet uses local Transmission when that path is healthy.
4. Local downloads run independently of the browser. The persistent server queue (Activity's Now and Server's **Download queue**) has checking, preparing, downloading, paused, ready, and error states. Stable info hashes deduplicate repeated requests. Downloads resume after an application restart. A book joins the library only after Transmission reports completion, every wanted audio file is complete, and local metadata can be read. Preallocated partial files are never considered playable.
5. **Listen.** Now playing's Listen face (`#listen/<workId>`) shows the cover and the book, the timeline, the transport (**Rewind 30 seconds**, **Play**, **Forward 30 seconds**), then **Speed**, **Sleep timer** and **Chapters**, then, under Source and device, **Plays from**, **Earlier positions** and **Keep on this device**. Headphone/lock-screen next, previous and seek commands all jump 30 seconds, including across audio files with known durations, while preserving paused playback. **Chapters** opens the chapter list (`#book/<workId>/chapters`; on a desktop a list beside the face); choosing one is recorded in Position history. Imported and locally downloaded M4B/MP3 files expose their embedded QuickTime, Nero, or ID3 chapters; the physical file and recording identity remain unchanged when seeking between chapters. Streaming files obtain embedded metadata when saved to the server; multi-file streams expose one chapter per file until then. Progress is keyed by recording and track, saved locally every five seconds and on pause/seek, then reconciled with the server by timestamp.
   **Speed** is a stepper (**Slower**, **Faster**) from 0.5× to 3× in 0.05× steps; pitch is preserved. A speed chosen in the player is remembered per recording, on this device only, in the signed-in user’s local database, so each narrator keeps its own speed and offline playback needs no server. **Use default** next to it removes that recording’s own speed so it follows the default again. Recordings without their own speed use Settings › **Playback** › **Default speed**, which is saved with the user’s playback settings on the server as soon as it changes and so follows the user across devices (unless an earlier build kept appearance on this device only). Until a default is saved, the device-wide speed from earlier builds still applies, and a speed chosen while the player has no book becomes that device-wide speed. At any speed other than 1×, the timeline shows the time left at that speed for the book or chapter (following **Progress bar shows**). Chapter lists show real chapter lengths at any speed; only the current chapter’s time left is shown at the speed the book plays at. The lock-screen position state reports the actual playback rate on every rate change and position update. **Sleep timer** opens a picker (Off, 5, 15, 30, 45 or 60 minutes); the row shows the minutes left.
6. **Recordings and where they play from.** The Audiobook page (`#book/<workId>/audiobook`, the Book page's Audiobook row) lists **Recordings**, **Available from** (**Device copy**, **Server copy**, **Original stream**, each with its size, "3 of 12 files", "TorBox" or "None") and, under Playback, **Plays from** and **Report a problem** (administrator). It separates recordings from their delivery sources. **Plays from** (also on Listen) chooses Automatic, Device copy, Server copy or Original stream (the online or TorBox stream). Switching delivery source preserves position and paused playback. Choosing another recording keeps a newer checkpoint of the target as it is. When the target has no checkpoint, or an older one than the recording in the player, a **Where to resume** dialog asks first: **Resume at <chapter or N%> (hh:mm:ss)**, **Start from beginning**, and, if the target has an older checkpoint of its own, **Resume saved position (hh:mm:ss)**; nothing is switched or transferred before the choice, and the chosen place is saved to the target recording right away. **Start from beginning** replaces the target’s own saved position (the helper line under the buttons names it, for example “replaces your saved position at 00:00:42”); the replaced place stays in that recording’s position history. A recording that is open in the player, playing or paused, counts as listened to now when it is compared with the target’s checkpoint. The position is carried over by chapter (the same chapter index when both recordings have the same number of chapters, otherwise the chapter with the same title, keeping the offset into it and clamped to the target chapter’s length), and otherwise by the share of the whole book (tracks of unknown length are left out of that share). Two recordings with the same number of chapters are matched by index with high confidence even when their chapter splits differ, so check the resume label when the releases were cut differently. **Earlier positions** after switching recordings only restores a place within the recording now playing; it does not switch back to the previous recording. A mapping is marked low confidence, with a warning line, when the total durations differ by more than 10% (such as abridged against unabridged) or only the share of the book was usable. Sentence alignment maps are not used for this yet. Progress is never merged between recordings: each keeps its own position.
   Automatic prefers a healthy device copy, then server media, then the original stream; explicitly selected sources never silently fall back. The one exception is a Server copy or Original stream choice that cannot reach the server (offline, or online with no route): when a complete, un-flagged device copy exists, that playback switches to it at the same position, the mini player's source reads “Device cache”, a short notice says so ("Original stream unreachable. Playing the device copy." or "Server unreachable. Playing the device copy."), and the saved choice is left unchanged. A gateway answer (502, 503 or 504, such as the reverse proxy answering while the Sonder process is down) counts as unreachable; other HTTP refusals and decode errors do not trigger it, and an incomplete device copy is never used. A pause or seek made while the app checks the connection is kept. A stream that stalls or waits for 10 s gets the same check, so a connection that goes silent without an error also switches to the device copy at the current position; a stall that clears while the check runs is left alone, and the check is not repeated for it. Once the server is confirmed unreachable it is remembered for 60 s, and the next chapters of that recording play the device copy straight away without trying the stream first. A successful answer from the server, the browser reporting `online`, or choosing a source in **Plays from** clears that memory sooner. The notice appears once per recording, not on every chapter, and not when the player only opens a chapter without starting it.
   **Report a problem** marks an entire recording or an individual copy faulty (**What is faulty**: Recording, Device copy, Server copy or Original stream; a **Reason** and an optional **Note**; **Mark as faulty**). Device flags stay on the device; recording/server/original flags persist on the server. **Clear the mark** when resolved. Tapping a copy under Available from offers **Remove from this device** or **Remove server copy**, each asked once ("Your place and the library entry stay."); removing a downloaded copy preserves the library and progress. Server removal deletes only managed downloads in `MEDIA_ROOT/saved`, preserving original imports and torrent files.
7. **Save to server** (administrator; Available from › **Server copy**) keeps a permanent copy on the HDD, including TorBox or LibriVox streams. Up to three files of a book are copied at once, in chapter order (`SONDER_DOWNLOAD_CONCURRENCY`). A file that fails is retried three more times with a fresh TorBox link (waits of 2, 5 and 15 seconds, `SONDER_DOWNLOAD_RETRY_MS`) before the copy stops; failures a retry cannot fix, such as TorBox not being connected, stop it at once. Complete chapters survive pause/retry/restart. An interrupted file is kept as a partial file and continued with a range request; a source that ignores the range, or answers with a range that does not reach the end, sends the file again from the start. Partial files are named after their source, so a re-linked source never continues an older file; cancelling a copy deletes them. Completed media is committed atomically. Keeping a cached recording does not change its recording identity or listening progress. The copy shows on Activity's Now ("Copying to server · 33%") and Server's **Copies to server**.
8. **Keep on this device** (a switch in the Book page's This device group and on Listen; a standing choice, ADR 0018, recorded on the server for each device, ADR 0021) keeps a complete copy of the book's audio and its EPUB's prepared text (#805, #806; the reader reads it offline) in the current browser using persistent IndexedDB chunks and Cache Storage. Completed chapter metadata is written only after size validation. While it saves, Activity › This device shows it under Saving now ("Keep Sonder open while saving."); pause or retry can reuse completed sections after reload. Partial books show as "Not complete · 3 of 12 files"; only fully saved books count as **On device** in the Library. This copy is independent of the server copy.

Settings › **Playback** has **Default speed**, **Progress bar shows** (**Whole audiobook** or **Current chapter**), **Reading mode** and **Follow the narration** (see the reader below), and **Keyboard shortcuts**. Current chapter uses embedded chapters inside M4B files. Whole audiobook spans files when their durations are known; otherwise it explicitly shows the current file. Drag the bar horizontally to seek; moving farther above or below it reduces sensitivity ("Drag away from the bar for finer seeking"). The drag previews your destination and seeks on release; keyboard arrows skip 30 seconds.

**Earlier positions** (its button reads **Undo a jump**) opens Position history ("No jumps in the last 24 hours" when it is empty) after a seek, a chapter chosen, Listen from here, or a source change that moves the position; a row restores a position inside the recording that is playing, and never switches to another recording. Starting another recording is recorded for the recording that was left, so its earlier positions are there when you return to it. Undoing a Listen from here with the reader's notice takes its history entry back too. Repeated 30-second skips within ten seconds share one undo point. History stays on this device, separately for each recording and user, and holds at most 20 positions for 24 hours. Removing the library entry or resetting this device clears its history; a restored position is saved through the normal progress sync.

A paused player picks up a newer place saved on another device (#773): when the app comes back into view, and before a resume from a pause (the play button, `Space`, or play from the lock screen or headphones), it reads the server's place for the recording it holds (`GET /api/progress/<recordingId>`, the asking user's own row or `{ progress: null }`). When that place was saved after this device's last save for the recording and is more than a second away, the paused player moves there (to another file if the place is on one) without starting to play, and the place it left is in Position history as "Other device". A playing player is never moved, a newer save of this device's own wins, and only the recording in the player is compared. Without a connection, or with no answer within 1.5 s, play resumes from this device's place and its queued saves stay as they were.

Keyboard shortcuts: `Space` plays or pauses (with no audio loaded it does nothing), `←` and `→` skip 30 seconds (on Read while nothing plays they turn the page), `/` puts you in the search of the Library or of Discover (not while typing in a field), and on Read `F` returns to the narration (also with the focus in the pages or on a button; not while a dialog is open above the reader, while typing in a field, with Ctrl, Alt or Meta, or without the book's narration in the player). Settings › Playback › **Keyboard shortcuts** opens the Keyboard shortcuts page (`#settings/keyboard`), which lists exactly these keys: Listening (Play or pause, Back 30 seconds, Forward 30 seconds), Reading (Back to narration; Previous page and Next page, "While nothing plays") and Library and Discover (Search).

The mini player (above the tab bar, or along the bottom on a desktop) shows the book, its source ("Device cache", "Host server", "TorBox" or "Online stream"; see Storage and security) and the transport. Its cover ("Open title page for <title>") opens the Book page, its title opens Now playing on the face last shown, and on a desktop its **Audiobook** button opens the Audiobook page and **Chapters and now playing** and **Expand player** open Now playing. **Read** (on the Book page, or Now playing's Read face) opens the work's chosen EPUB without asking: the shared default when there is one, then the edition chosen on this device, then the only (or first-added) EPUB. Opening Read loads that book into the player, paused at its own saved place, when the player holds nothing or another book that is not playing, so the reader follows its narration; the other book's place is saved first and stays its own. Another book that is playing plays on, and the reader then marks no narrated sentence (#862). Opening Listen never swaps the player's book: its play button does.

Library entries, saved server media, acquisitions, settings, and progress survive restarts in SQLite and the media drive. Removing a library entry preserves its files and progress, and records that choice so nothing adds it back; explicitly adding it again restores the entry. Older clients sending an empty JSON body on library DELETE are supported. Browser favorites are device-local. New library mutations need a server connection; playback progress works offline and syncs later.

The library can also be read by work (`server/library-works.ts`, type `LibraryWork` in `src/types.ts`): `GET /api/library` returns each work in the user's library once, earliest added first, and `GET /api/works/<workId>` returns one work in the same shape, in the library or not. A work lists as recordings its audio editions that are in the user's library and are not placeholders (an audio edition none of whose recordings has a track), the one added first first, so a removed recording is not listed and a work with only a placeholder has none; no response carries a placeholder's id. The chosen recording is the user's own choice, the same on all their devices: `PUT /api/works/<workId>/recording` with `{ recordingId }` stores it (one `user_settings` key per work) and answers the work; it refuses (400) a recording that is not one of the user's recordings of that work, such as another work's, a removed one, a placeholder's or one only another user has. Without a stored choice, or when the stored one is no longer among the user's recordings, it is the one with the user's newest saved place, otherwise the one added first. The work's cover is the chosen recording's; without one, the placeholder's. `addedAt` is the earliest of the user's library rows for the work. A work whose every audio edition is a placeholder the user may not see, and that has no ebook edition (ebook editions are listed to every user by `GET /api/ebooks`), is not found: a user who is not the administrator sees a placeholder only when it is in their library or its book is on their own stored Hardcover shelves or lists (kept, unused, since #721 part d), as in `GET /api/books`. A work also holds (#487): `finished` and `completionOverride`, derived as the series read derives them (`server/work-completion.ts`, shared by both); its ebook editions (the consensus text of an ebook set is not one) with format, size and whether the file is there as `GET /api/ebooks` gives them, the ebook-set member's status and hold reason, and the user's place from their reader checkpoint, plus `chosenEbookId`, the set's shared default when it is one of them; `readingSync`, one entry per pair of a listed recording and a listed ebook edition that has a job, in the summary form of `GET /api/alignments?summary=1` without steps, workers and stage times, with a running rebuild's state under `rebuild`; `series`, its AudiobookDB series with the ones the user saved first (#721); `mediaState` (ADR 0011) with its acquisition, whose status, progress and error only the administrator gets, as `/api/acquisitions`; and `hardcover`, the block of `GET /api/books`. `GET /api/library` sends a per-user `ETag` and answers `304` to a matching `If-None-Match`; the response is rebuilt when a database row changed or a file it checked (a track, a server copy, an ebook) changed on disk, which a read notices within 5 s. `GET /api/books` (one entry per audio edition and recording) is unchanged for older clients.

The device keeps its own copy of the library by work (#528, `src/library-works-store.ts`): one record per work of `GET /api/library` in the `works` table of the user's device database (Dexie version 5; the `books` table stays), replaced together with the stored `ETag` in one transaction. It is read again with `If-None-Match` when the app opens, comes back to the foreground or online, after an action on a work (`sonder:library-changed`, the shell's refresh), and every 6 s (the pace of the old Downloads page) while a stored work has a queued acquisition, a copy to the server that is queued or downloading, or a running reading sync or rebuild; a `304` leaves the store untouched. `useWork(workId)` gives a page its work: the stored record, or `GET /api/works/<workId>` for a work outside the library (which needs a connection; without one its status is "offline"). Either way `overlayDevicePlaces` (`src/library-works-overlay.ts`, pure) lays over it every place saved on this device that is newer than the server's: listening progress per recording and reader checkpoints per ebook edition; a place for a recording or edition the work does not list is left out. The Book page and its pages, the Get sheets, the Reading sync page and Now playing use it; the parts gallery's "Works on this device" section shows what it returns.

Discover reads the server's works with `GET /api/works` (#573, `serverWorks` in `server/library-works.ts`, type `WorkResult` in `src/types.ts`), answered as `{ works }`, at most 30, each with `workId`, `title`, `author`, `year`, `cover` (as the one-work read's), `inLibrary`, `hasAudiobook` (a recording with a track), `hasEbook` (the consensus text of an ebook set is not counted) and `hardcoverId`. With `q` (2 to 150 characters once trimmed; one character answers 400) it lists the works the user may see, by the one-work read's rule above, whose title or author holds every word of `q`, case and accents ignored (ø, æ, ß and the like as o, ae, ss), the ones in the user's library first, then by title. Without `q`, or with an empty one, it lists the works the user may see that are not in their library, that they have not removed (a hidden entry on any of the work's audio editions) and that have a recording with a track or an ebook edition, the work made last on the server first. Each entry of `GET /api/discover/series` carries `saved`, whether the user saved that series. Discover's book search (#721) asks the server, `GET /api/discover/audiobookdb?q=` (English audiobooks, with the server's AudiobookDB key) and `GET /api/discover/openlibrary?q=` (books without an audiobook) at once, for every account; Hardcover's book group is gone (`/api/discover/hardcover` answers 410). Each answers `{ books }` with `provider`, `id`, `title`, `authors`, `year`, `cover` (the provider's address, shown by URL and never stored), `workId` and `onServer`, or the provider's reason (409 without a key, 502 otherwise), shown with Retry. `workId` is the work on the server linked to the book (`work_catalogue_links`) that the user may see, else `work-abdb-<id>` / `work-ol-<id>`: the one-work read answers such an id from the provider without writing anything (ADR 0022's rule), and Add to library (or Get, which adds first) makes that work, its link and its placeholder, or, for the administrator, links the one unlinked work with the same title and author. Discover lists each book once: Open Library leaves out what AudiobookDB lists, and both leave out a work on the server of the same title and author. AudiobookDB's results and a Book page read from it show "Data from AudiobookDB" with a link.

## Hardcover (removed)

Hardcover is no longer part of Sonder (#721 part d): its listening and reading progress sync, the position pull, the shelf, list and status queues, the background sync loop, the token and its Settings, the Hardcover page (`#book/<workId>/hardcover`, which now opens the book's match page) and the Book page's Hardcover row are gone. The catalogue is AudiobookDB and Open Library (next section); Sonder's own **Want to read** shelf takes the place of Hardcover's shelves, and Reading and Finished come from the user's own progress.

- **The switch.** Once per database, at startup (`server/hardcover-switch.ts`, marker `migration:hardcover-removed` in `settings`), every user's stored Hardcover Want to read shelf is copied into their Want to read (`copyHardcoverWantToRead`: each book matched to its work, the books with no work kept as that user's unmatched list, `GET /api/want-to-read/hardcover-copy`), then every stored Hardcover token is deleted. It is one transaction: a failure keeps the tokens, writes no marker, is logged, and runs again at the next start. Hardcover lists are not copied.
- **The tables** (`hardcover_links`, `user_hardcover_*`) stay, unused, for one release and are dropped after. A stored link still names a placeholder `hc-<id>` and still decides, as before, which placeholders a user who is not the administrator may see.
- **Older builds.** The removed routes (`GET /api/hardcover`, `PUT /api/hardcover/token`, `POST /api/hardcover/test`, `PATCH /api/hardcover/config`, `POST /api/hardcover/sync`, `POST /api/hardcover/books`, `PATCH /api/hardcover/shelf`, `PATCH /api/hardcover/lists/<id>`, `POST /api/hardcover/progress/pull`, `GET /api/hardcover/editions`, `PATCH /api/hardcover/edition`) answer 410 with `code: "hardcover_removed"` and `Cache-Control: private, no-store`. `PATCH /api/settings` still accepts an older build's `hardcover` field from anyone and ignores it; `GET /api/settings` still answers `hardcoverConfigured`, always false; `GET /api/books` keeps its `hardcover` block, read from the stored rows.
- **Its catalogue** went with parts b and c2: the series are on AudiobookDB's ids (`server/series-routes.ts`), Discover searches AudiobookDB and Open Library, and `GET /api/discover/hardcover`, `GET /api/hardcover/books/<id>/series` and `POST /api/hardcover/series` answer the same 410. An older build's id `work-hc-<n>` opens the work stored as matched to that book (the kept `hardcover_links`), else 404; Hardcover is no longer asked. A test-only route, `POST /api/__fixture/library-book` (`tests/library-fixture-routes.ts`, browser server only), puts a book without a catalogue link in the library for the specs that used Hardcover's import.

## Catalogue: AudiobookDB, Open Library, Google Books and iTunes

AudiobookDB (`server/audiobookdb.ts`) is the catalogue for audiobooks; Open Library (`server/openlibrary.ts`, no key) gives a book without an audiobook its link (#721). Google Books (`server/googlebooks.ts`, the volumes API) and iTunes (`server/itunes.ts`, the Search API with `media=audiobook`, US store) need no key and are searched by the match page only. All four share `server/catalogue-provider.ts` (result shape, English check, cache, limiter, failure reasons) and are called by the server only, with the User-Agent `Sonder/<version> (+https://sonder.pecori.no)`.

- **Key:** the server's `AUDIOBOOKDB_API_KEY` (in `.env`). Settings → Connections then says "Set in the server's file" and offers **Test**. Without it, a key saved there (encrypted like the other keys) is used. Open Library needs nothing.
- **Limits:** one request at a time, waiting whenever AudiobookDB's `RateLimit-Remaining` reaches 0 (until `RateLimit-Reset`) or it answers `Retry-After`. Units are counted per UTC day (detail 1, list 2, search 3, of 10,000). Near the limit, new searches are refused with "AudiobookDB's daily limit is reached; try again later." and cached answers still serve.
- **Cache** (`catalogue_cache`): searches for a day, keyed by the lower-case, single-spaced query and its type. Book, release and work details are kept a week and fetched again by the hourly `catalogue-refresh` loop; one the provider no longer has (404) is deleted. Descriptions are never cached and covers are shown from the provider by address.
- **Links:** a work links to an AudiobookDB book or an Open Library work (`work_catalogue_links`, with the first series and its position kept for the series part). A recording may link to a release (`recording_release_links`: narrator, length, ASIN, chapters). A link fills only what is missing (the work's description, the edition's narrator); title, author and cover stay.
- **Match library** (administrator, Connections): one pass over every work without a link. A sure match is applied: the ASIN in the file names, or exactly one result with the same normalised title and author whose releases are not all in another language. A recording is linked to the release with its ASIN, or to the only English release within a minute (and 1 %) of its length. A book without audio that Open Library has under the same title and author links there. The title may also be an entry's title after words of its series' name ("X-Wing Rogue Squadron" is "Rogue Squadron" of "Star Wars: X-Wing - Legends"), one shared author is enough, and a work with several authors is also searched with each author's surname. Results under another title (by anyone) are not candidates: a work they alone come back for is "Not found", not "Not sure". The rest are listed under **Not matched** ("Several fit", "Not found", "Failed"); each opens the book's match page. A matched work is never searched again by the batch.
- **Google Books and iTunes limits:** Google Books at most one request a second and 1,000 a UTC day (its published default); when Google answers that the day's quota is spent ("Queries per day"; a key-less call from the build host got this on 19 Nov), no further request goes out that day and a search says "Google Books' daily limit is reached; try again later." iTunes at most one request every 3 s (Apple asks for about 20 a minute); a 403 or 429 holds requests back a minute. Their searches are cached a day and their volume/audiobook details a week, like the others. Results are English only where the provider names a language (Google Books); iTunes names none.
- **Match page** (`#book/<workId>/match`, from the Book page's **Match** row, administrator only): the link and Unlink, each recording's release with a picker, and a search of AudiobookDB, Open Library, Google Books and iTunes filled with the title and author. Each provider is one request (`GET /api/catalogue/search?q=…&provider=…`; without `provider` the older two-group answer), so each group shows as it arrives, with its results, "No books found", or its own failure line. Choose a result and **Match**. A Google Books or iTunes pick is kept beside the main link (`work_provider_links`, one per provider, each with **Open on …** and its own **Unlink**) and fills only what is missing (of series, position, narrator and description they give only the description). A work with any link counts as matched; the batch never searches Google Books or iTunes.
- A provider failure answers with its reason and touches nothing else; the library and playback never call a provider.

### Series on AudiobookDB (#721 part b)

Series use AudiobookDB's text ids (`server/series-catalogue.ts`, routes in `server/series-routes.ts`, same paths as before; an older client's number is taken as its text).

- **Reset:** at the first start of this version the Hardcover series tables (`series_catalogue`, `series_catalogue_works`, `user_saved_series`, `user_saved_series_works`, `user_series_seen_works`, `series_acquisition_jobs`, integer ids) are renamed `hardcover_<name>` and left unused; new tables with text ids take their names (`server/db.ts`, guarded by the old `id` column's type, so it runs once). Each saved series is noted in `series_resave` and saved again by its name on AudiobookDB (`server/series-resave.ts`, the `series-resave` loop, every 15 min until done; several of one name are told apart by the author). The books the user had come back added with the work they had, their "introduced" mark and library origin; nothing new joins the library, no search starts and nothing shows as New. A series not found (or not saved yet: no key) is listed in Activity under Series search, "Series not saved again · Not found on AudiobookDB" with Discard (Retry for a failure). Works, files, progress and alignments are untouched.
- **Membership and position** come from `GET /api/series/{id}`: each member's `position` label ("1.5") and `sortKey`. English only: a member AudiobookDB names in other languages only is left out; an unknown language stays.
- **No audiobook yet:** Open Library's books of the same series name (`series:"<name>"`, the series' author, a number and title no AudiobookDB member has) are listed as "No audiobook yet" (`openlibrary:<work>` ids). Added, the work links to Open Library and only its ebook is searched for. When AudiobookDB lists the book (a refresh), its row becomes the AudiobookDB member: the work, each user's choice and what they saw move to it, the work links to AudiobookDB and the audiobook is searched for.
- **Refresh and New:** the page reads AudiobookDB's cached answer (a week); Retry asks again, and the `series-refresh` loop reads every saved series again once a day. A book a user has not seen is New until Dismiss.
- **Discover** searches series on AudiobookDB (no Hardcover needed); **Save series**, the Add sheet, Remove series, the series searches and Get work as before on the new ids (the release picker they used is gone; Get audiobook took its place). The audiobook search ranks a candidate read by a narrator of the book's English releases, or as long as one, first.
- **The automatic audiobook pick respects the series' language (#897; `server/series-audio.ts`, `server/release-language.ts`).** The language is the one the user chose when saving the series (`POST /api/series` takes `language`, kept in `user_saved_series.language`; an older client sends none and leaves it), else the catalogue's language of the book, else English. A candidate whose source names another language (AudioBookBay's "Language"; Prowlarr names none), whose title marks one (`[FR]`, `(German)`, Français, Deutsch, Español, Italiano, Nederlands, `VF`, or the English name unless it is part of the book's or series' own title) or whose ASIN is of a release in another language is never picked; it stays in the manual list, which marks a Prowlarr release with the language its title marks. A candidate that names no language is picked only with evidence it is the wanted edition: the narrator (also named in its title), the length within the ranking's tolerance, or an ASIN in its title that AudiobookDB (`GET /audiobooks/external/audible/{ASIN}`, then the release's language) resolves to this book in the series' language; an ASIN of another book rules it out, and a failed lookup leaves it "language not known". Otherwise the book is left for the user to choose (media state held "empty_search", "Not added"). After a download, a series book whose files carry an ASIN of another language than the series' is held `another_language` and its Series row says "Another language" until another release is chosen.
- **A whole-series pack is downloaded once and split into its books (#899, ADR 0027; `server/series-pack.ts`, `server/acquisition-packs.ts`, `server/series-pack-step.ts`).** A release whose title names the series and a range of its books ("Books 1-8", "#1-3", "1-4") is a pack; one that names no range ("Complete Series") is not. Before a book's own search the series queue (1) lets a pack of the series that holds the book, on its way or done, take it without a second download, else (2) once per series every six hours, when two or more books of the series wait for audio, takes the pack that covers the most of them (not one in another language), for every waiting book it covers; a book with audio is never in it and a book it does not cover keeps its own search. On the Get audiobook sheet a pack row of a saved series the book is in starts with "Books 1–8", the line under the button says "Holds books 1–8 of <series>. Also gets <the other books without audio>.", and Get sends `pack: true` (`POST /api/works/:id/packs/describe` names the rows). When the pack is downloaded each book gets its own audio edition and recording of only its files, never copied: the units below the folder every file shares (a book's folder, or a loose file) are read by the book's title, then "Book 3"/"Vol 3"/"#3" or a leading number, then by order when none names a book and the counts match. A book the split is not sure of shows "In a downloaded pack" on its Get sheet, with the pack's folders and files to switch on and Use these files (`GET`/`POST /api/works/:id/pack`). Removing a book removes its recording only; the pack's files stay while another book of it has a recording or waits for one, and go with the last book. Choosing another recording for one book of a pack on its way lets only that book leave the pack.
- A work's `series` in `GET /api/library` and `GET /api/works/<id>` are its AudiobookDB series (with `positionLabel`); Hardcover's are no longer listed. `GET /api/books` is unchanged.

## Ebook sources

The Get ebook sheet (`#book/<workId>/get/ebook`, administrator only) searches its sources for the title and author (**Search for an edition**), each on its own (#901): **Library Genesis**, **Anna’s Archive** when its member key is saved, **Z-Library** when its account is saved, the other Library Genesis family (**Library Genesis (libgen.rs)**: libgen.is, libgen.rs, libgen.st, whose files are fetched by md5 through the libgen.li family's download pages, as their own mirror links do), **Prowlarr**'s book indexers when Prowlarr is connected (Newznab 7000 Books and 7020 EBook, torrents whose title names EPUB or PDF), and the public-domain **Standard Ebooks** (its OPDS search) and **Project Gutenberg** (its OPDS search). It opens from the **Get** on the Book page's Ebook row (a book with no ebook) and from **Get another edition** on the Ebook page. The Library Genesis mirror is Settings › Connections › Library Genesis › **Mirror address** (`https://libgen.li` by default). No source needs a key; a source that fails says so on its own line ("Library Genesis could not be searched.", with the reason and Retry) while the others' rows show, instead of appearing to return no matches. Each row is the source's title and "EPUB · size · language · year · source" (a Prowlarr release names its indexer and seeders), EPUBs before PDFs, in the sources' order; a file the book already has is marked "Already added" and cannot be chosen. **Get this edition** saves it on the server ("Saved on the server, then checked against the narration."); a Prowlarr release is a torrent ("Downloaded as a torrent first. It joins the book when the download ends."): it goes through the download queue as an audiobook does (TorBox when cached, else local Transmission), shows in Activity, and when its EPUB (else its PDF) is complete it is imported into the book as an upload is ("Ebook on server"). The foot is built as the Get audiobook sheet's: **Get this edition** pinned to the foot, its line above it and, above that, while an edition with an http(s) address is chosen, **On <source>**, which opens the edition's own page in a new tab (#889). **Other ways to get it**: **Import a file from this device**, and **Search on Library Genesis**, a link to the mirror's own search. Anna’s Archive is back (#901): Settings › Connections › Anna’s Archive holds its address (`https://annas-archive.gl` by default) and its member key, encrypted; the server signs in with the key, searches with that session (signing in again once when a kept session meets the check) and fetches through the member fast-download API. Without a key it is not asked, and a request for it is refused ("Add your Anna’s Archive key in Settings first."). Its browser check (a redirect to `?check=1` and DDoS-Guard's page), which only a member key passes (#8), is said plainly ("Anna’s Archive asks for browser verification, which only a member key passes."), and so is a refused key ("Anna’s Archive refused the key in Settings.", at sign-in or from the download API's 401); **Test** shows what it said. Z-Library: Settings › Connections › Z-Library holds its address (it changes; `https://z-library.sk` by default) and the account, email and password or a remember-me token (`remix_userid=…; remix_userkey=…`), each encrypted. The server signs in through its app API (`/eapi/user/login`), searches (`/eapi/book/search`) and downloads (`/eapi/book/<id>/<hash>/file`) as that account, refuses a download once the day's limit is reached, and **Test** shows "3 of 10 downloads today." or what it said ("Z-Library refused the login in Settings.", "Z-Library asks for browser verification." for its DiamWall check). Each of these sources is asked through a client of its own with Library Genesis's spacing, retries and rests (below), and a browser check is not retried.

Library Genesis is asked politely (#901), and every other shadow library the same way: one request at a time from the Get sheet and the series queue together, at least 2 s apart and 6 s for the download pages (`ads.php`, `get.php`). A 429, a 5xx or a verification page is tried again after 4 s and 12 s, then on the next mirror (the Settings one first, then libgen.li, libgen.la, libgen.gl, libgen.vg and libgen.bz, which serve the same pages). When every try was limited, that kind of page rests for 2, 5, 10 or 15 minutes in a row and is not asked meanwhile: the Get sheet says "Library Genesis is limiting requests, trying again at 13:05." and asks again then, and a series ebook search goes back in the queue until then ("Library Genesis is limiting requests, trying again at 13:05" in Activity). Each failure is logged once with the mirror, the page kind and the status. The 500s of the download pages seen in production are its database refusing connections (`max_user_connections`) on every mirror at once.

To add a file from elsewhere, download the EPUB/PDF and use **Import a file** on the book's Ebook page or **Import a file from this device** in Get ebook; the file is linked to that work. Discover › Ebooks and its Import ebook are gone, and so is the ebook shelf (#556): a book with only an ebook is in the Library like any other, with the Ebook cover mark. Imports stream to `MEDIA_ROOT/ebooks`, have a 150 MB limit, validate file signatures, deduplicate identical files and persist through restarts.

A book's ebook has a page of its own, the Ebook page (`#book/<workId>/ebook`), opened from the **Ebook** row of the Book page's Files ("Not added" with **Get** for the administrator when it has none). Under **Editions** it lists the editions ("EPUB · 2 KB") with each one's check against the narration ("Matches the narration", "Not checked") and the chosen one ticked; tapping an EPUB makes it the shared default when the administrator taps one that matches the narration, and this device's choice otherwise ("Only an edition that matches the narration can be the default."). A PDF ("Opens in another app") opens its file in a new tab. **Get another edition** (administrator) opens Get ebook for the work, **Import a file** imports an EPUB or PDF into it, **Available from** shows this device's copy (**Device copy**) and the server's (**Server copy**) with their sizes (the device copy is removed after one question, "Remove from this device?"; the reader then reads from the server), and **Export the file** downloads the chosen edition.

Ebooks are checksum-verified, saved under `MEDIA_ROOT/ebooks`, and open from their book in the Library. An edition got or imported for a book is linked to the same work. Ebook editions are independent of audiobook editions and recordings. EPUBs open in Now playing's Read face; PDFs remain available to download for an external reader. See the reading-sync workflow below.

A book with only an ebook is in the library through its placeholder (#555, decided in #467; `ensurePlaceholder` in `server/placeholder-edition.ts`): an audio edition "Audio not added" with one recording and no track, `hc-<book id>` for a work matched on Hardcover and `placeholder-<workId>` otherwise, never two for one work. Importing an EPUB or PDF (`POST /api/ebooks/import`, with or without a book chosen) and getting one from a search result (`POST /api/ebooks`) put its work in the library of the user who did it by the rule of **Add to library** (`PUT /api/works/<workId>/library`), when it is not there yet; that `PUT` of a work with no audio edition makes the placeholder and adds its row. Real audio arriving for a work (a finished download or an upload, `claimWorkAudio` in `server/work-library.ts`) gives every user who has its placeholder in their library the new recording's row with the same status and removes the placeholder's row, unless they hid that recording. Once, at the first server start with this change (marker `shelfEbooksJoined` in the administrator's settings), every work with an ebook outside the administrator's library joins it through its placeholder unless he hid that placeholder; a recording he removed stays removed.

The Library's **In progress**, **Not started** and **Finished** chips and its Finished mark follow the work of each entry (#556, `workProgress` in `src/work-progress.ts`), from the stored library by work with this device's newer places laid over: Finished as the read says (an override, or a recording or an ebook read to the end, ADR 0002); otherwise In progress with a place past the start of a recording or an ebook place above 0; otherwise Not started. A book without audio that is being read shows its ebook's percentage. `src/cover-marks.ts` decides the cover marks the Library's tiles draw (Audiobook, Ebook for an EPUB or a PDF, a ready reading sync, or the percentage while the first file downloads). The Library's other chips are All, Series, On device and Favorites; **Sort and view** (Sort: Recently added, Title, Author, Progress; View: Grid or List; Shelf: Want to read, Reading, Finished) holds the shelf that Hardcover's shelves and lists became (#721 part c1).

## MyAnonamouse (#911)

MyAnonamouse (MAM) is a private tracker for audiobooks and ebooks. Settings › Connections › **MyAnonamouse** holds the member's session, the `mam_id` made in MAM's own preferences (Security) for API use, encrypted like the other keys; **Test** runs one small search, and when MAM refuses the session the group says "Refused" and "MyAnonamouse refused this session on <day>. Make a new session in MyAnonamouse’s preferences (Security) and paste its mam_id." MAM renews the session with each answer (`Set-Cookie: mam_id`); the server keeps the newest one.

- **Only MAM's documented API, never a page** (MAM rule 1.7). Every call goes through `server/sources/myanonamouse.ts`, whose `MAM_ENDPOINTS` is the one allow-list, four functions of MAM's API Documentation: Torrent Search (JSON) (`tor/js/loadSearchJSONbasic.php`), Download Torrent (`tor/download.php/<dl>`, the `dl` the search answers with `dlLink`), Dynamic Seedbox IP and IP and ASN lookup (both from the host script below). Calls are few and spaced (one at a time, 3 s apart, 6 s for a `.torrent`, one more try after 15 s, then a rest of 5 to 60 minutes): a search when the owner searches, one search per book and one per series for its packs in the series queue, and one `.torrent` per download. The parser is built on real answers recorded with the owner's session (`tests/fixtures/myanonamouse/`, with the session, the download tokens, the passkey and the user id replaced).
- **Where it is searched.** The Get audiobook sheet asks MAM (main category 13) first, then AudioBookBay and Prowlarr; the Get ebook sheet asks it (main category 14) before the other ebook sources, listing an EPUB or a PDF torrent (one of neither is no row). A row says its narrator, format, size and seeders (MAM names its language, so the language filter applies to it), and **On MyAnonamouse** opens its page. The series queue's per-book search, its pack search and its ebook search ask it too; a MAM row is a book of the series by the series and place MAM names, else by its title, and never one by another author.
- **The order, for audiobooks and ebooks alike** (the owner): a release TorBox has cached (from any source), then MAM's, then every other source. In the Get sheets this orders the rows of the book (a row of another book never comes before the book's own; EPUBs stay before PDFs); in the series queue it comes before the ranking (narrator, length, ASIN) and, for packs, after the number of waiting books a pack covers. The series ebook search asks Prowlarr first for a cached release, then MAM (an EPUB torrent in the book's language), then the rest.
- **A private tracker's torrent.** A MAM torrent goes to the local Transmission only, never to TorBox, added from MAM's own `.torrent` (`metainfo`, label `mam`); the database keeps a magnet of its hash and name only, so the passkey is in the torrent client alone. Its ratio and idle limits are lifted (`seedRatioMode` and `seedIdleMode` unlimited), and a MAM ebook torrent is fetched whole. It seeds for as long as possible and never stops before 72 hours of seeding: nothing in Sonder stops or removes it on its own. Removing its book (a series' works) keeps the torrent and its files; choosing another recording lets the book stop waiting for it, but the torrent finishes and seeds on; **Cancel** marks the download cancelled and leaves the torrent in the client, downloading and seeding on; it removes the torrent only when it has already seeded 72 hours (a later cleanup may remove one after its 72 hours; none does yet). Activity › Server lists **Seeding on MyAnonamouse**: each MAM torrent with "Seeding · 31 h of 72 h · Ratio 0.42", "Seeding · 3 d 4 h · Ratio 1.20" once past its 72 hours, "Downloading 45%", "Stopped in the torrent client" or "Not in the torrent client" (`GET /api/mam/seeding`).
- **The VPN's address.** MAM accepts announces from an address it knows; Transmission announces through the VPN. `scripts/mam-dynamic-seedbox.sh`, run hourly by the user timer `scripts/install-mam-dynamic-seedbox.sh` installs on the production host, asks MAM's IP lookup from inside the torrent container (`docker exec sonder-torrents curl`), and only when the exit address changed, at most once an hour, calls Dynamic Seedbox IP there with the VPN's own session (`~/.config/sonder/mam-session-dynamic`, mode 600, passed on curl's standard input and renewed in place). `--dry-run` says what it would do.

Tap the centre of the text to show or hide the controls. In pages mode, tap the left or right edge or swipe to turn pages, and swipe down from the top to close. Long-press a sentence to play the narration from there (**Listen from here**); the foot's notice "Listening from here" offers **Undo**.

- **The head**: **Close reader**, the face control **Listen or read**, the bookmark button (**Bookmark current sentence**: it bookmarks the narrated sentence while following, otherwise the first sentence on the page, and removes that bookmark when pressed again, with "Bookmark removed" and **Undo**), **Search this book** and **Aa** (**Reader appearance**). At rest it shows the book and the chapter.
- **Appearance docked**: **Aa** opens Reader appearance in the foot's place, so nothing covers the text: **Reading mode**, **Follow the narration** (a switch), **Font**, **Size**, **Line height**, **Margins** and **Line width**; **Close appearance** closes it. The reader's theme is Settings › Appearance › Reader.
- **Pages of their own**: **Chapters** and **Bookmarks** (`#book/<workId>/chapters`, `#book/<workId>/bookmarks`, one page with **Chapters or bookmarks** to switch, "Back to the book") and **Search** (`#book/<workId>/search`, "N sentences"). Chapters lists the ebook's contents with the narrated chapter marked ("Now · N min left"); choosing one moves the page only. Bookmarks lists the bookmarks ("No bookmarks. The bookmark button at the top saves the sentence in view.").
- **The foot**: at rest a progress line and "Chapter · N min left" (or "N% of the book" without narration). With the controls shown, the chapter and "N% of book" or "N% of chapter" (", estimated timings" on a map), the slider, **Chapters**, **Back to narration**, **Back 30 seconds**, **Play narration**, **Forward 30 seconds**, and the sleep timer and speed. Each of these two opens a setting pop-up above its button, the one thing drawn over the text (at most 120 px into it, the page not dimmed and the text not laid out again; ADR 0019, amended 2026-11-24): **Speed** with **Use default** (while the recording has a speed of its own) and its stepper, **Sleep timer** with its stepper and the minutes left while it runs. Each change applies at once; there is no Done. The transport row stays usable underneath. A tap outside it, Escape, its button again or the controls hiding closes it, and Escape or the button puts the focus back on the button; a tap on another control does what it does and closes it, and a tap on the text only closes it (it does not show or hide the controls, turn a page, follow a link or start Listen from here). With this book’s narration loaded, the slider is the narration's, with elapsed and total time, following **Progress bar shows**; scrubbing it seeks the audio and the page returns to following the narration. Without narration (a book with only an ebook, or another book playing) the slider scrubs the ebook ("Position in the book") and the page moves when it is released; a book with no recording has only Chapters and the slider.
- **Messages are in the foot**, never over the text: the notices with **Undo** (8 seconds, or until the next tap on a control): at rest in the lower row with **Undo** directly after the sentence, and on a phone with the controls shown in the foot's first row (the timeline, or for a book without a recording the chapter and "N% of the book"), so the transport row, the sleep timer and Speed, or Chapters and the position slider, stay usable while it shows; "Finding the place in the text…", a place saved elsewhere ("A place in <chapter> was saved elsewhere." with **Stay** and **Go there**), errors with **Retry** or **Dismiss**, and "An update is ready." with **Reload**. These others, and on a desktop every message, take the place of the row's controls.

**Back to narration** sits in the foot between Chapters and Back 30 seconds (icon only; same place on phones and on desktop). It stays in that slot so the transport does not move: disabled while following, and enabled when the page is away from the narration. With no narrated sentence at the position (no map for the recording in the player, or before the map's first sentence), the administrator's Back to narration locates the passage from the audio (as the More sheet's Read from audio did before it was removed) while the foot says "Finding the place in the text…", and a failure is the foot's "The place in the text could not be found." with Retry; for anyone else it is off. `F` does the same as the button. On a desktop the reader has a **Contents** sidebar (**Hide contents**), **Previous page** and **Next page** arrows, and keyboard navigation. The reader serif is Literata, bundled for offline use.

Paging or scrolling by hand pauses following; **Back to narration** resumes it. Without a map, the text remains readable and the Book page's **Reading sync** row prepares one. Sentence timings are estimated. Reading checkpoints use sentence locators rather than display page numbers (checkpoints saved before #806 also carry a CFI). Offline positions and bookmark changes queue locally and retry when connected; conflicting sessions offer both positions. EPUB scripts and remote embedded resources never reach the page: the server sanitises every section as it prepares the text (ADR 0025), and the reader makes a part's nodes one by one from those the allow-list of `src/prepared-text-rules.ts` passes (README "The new reading view", "How a part enters the page"); a book's pictures are served with a sandboxing Content Security Policy of their own.

**How a book is cut into sentences** (`extractBook` in `server/reader.ts`, ADR 0026). A chapter is cut block by block, and a block is a `p`, heading, `li`, `blockquote`, `pre` or `figcaption` that holds no other one; a chapter without any is one block. A book whose blocks hold less than half of its text (paragraphs written as `<div>`s, or loose text in `<body>`) is cut another way, chapter by chapter: by the first of the standard rule, the standard rule with `<div>` as a block, and the whole chapter as one block, whose blocks hold nine tenths of the chapter's text. The chapter's section says which (`blocks: "div"` or `"body"`), and the reader counts its blocks by that rule. Every other book keeps the standard rule in every chapter, so its sentence ids never move. The cut reads only the file (`cutEpub`) and writes nothing. Reading places and bookmarks saved in such a book before it was cut this way are moved to the same text once, by the routes that answer or store a place (`bookWithPlaces`; `settings` key `reader-recut:<edition>`, one log line). A place a device sends later on the old cut is told apart by its quote and stored on its own text, or refused when its text is in neither cut. `scripts/compare-extractor.ts` shows, for every EPUB of a library, whether a change to the extractor leaves its sentences as they were (`docs/LOCAL_CHECKS.md`); an edition it cannot read fails it.

## Local ebook/audio synchronization

1. Add a matching EPUB to the book (Get ebook, or **Import a file** on its Ebook page). A reading sync is for one pair: the book's chosen recording (the Audiobook page's **Recordings**) and its chosen EPUB (the Ebook page's **Editions**), shown on the Reading sync page as **Recording** and **Edition**. The audiobook's Find ebook dialog and the reader's Reading sync panel are gone.
2. A clear language mismatch is refused (Not available). Pairing ebook sections with tracks or embedded chapters, and editing their start and length to exclude introductions or split a long physical file, were steps of the older engine's chapter matcher, which has no screen any more: the server pairs them itself where a job needs it. Each processing section is limited to two hours.
   With `ALIGNMENT_BOOK_JOBS=1` there is no matching step: the whole-book job gets every sentence of the ebook and every file of the release and locates the text itself, so a pairing would change nothing in its map (#405). `GET /api/alignments/options` says so with `bookJobs: true`. **Prepare** on the Reading sync page always sends only the ebook and the recording. The server still stores its automatic pairings on the job (used if the setting is turned off again); when none match on a chaptered release, the job is planned as an anchored one instead of being refused. An older client that still sends pairings or `mode` keeps working.
3. Select **Prepare** on the Reading sync page (`#book/<workId>/sync`, the Book page's Reading sync row). Audio is first saved to the server HDD when needed. The pool worker checks acoustic evidence before accepting supplied text. Jobs persist in SQLite and pause, cancel or resume at section boundaries. Completed section outputs are cached on the HDD.
   A release that is one audio file without chapter markers (or several files with none that match) is prepared without a chapter matcher. Sonder takes 30-second speech samples about every ten minutes, more densely near the start and end. CTC jobs locate these samples from the same cached acoustic data used for alignment, keeping alternative repeated passages until the forward-moving anchor chain is selected. Where the gap between samples disagrees with the text length, it adds samples between them. Known-text alignment then runs on bounded windows between samples, with overlapping edges, one window at a time. Intro and closing credits, ebook text with no narration, narration not in the ebook, and unaligned windows are listed in the sync status and left unsynced. If too few samples match, the text is left unsynced. Sampling and windows resume after a pause. A job with chapter pairings chosen by hand (an older client's) uses the chapter workflow instead.
4. **Back to narration** moves the ebook to the current audiobook position; where the map has no interval there (or there is no map), an admin's request locates a 30-second excerpt with one CTC `/anchor` request on a pool host (WSL first, then lisa), which needs the pool enabled (staging, scoring and cleanup together have 180 seconds; past that the request ends with an error and frees the host); **Listen from here** seeks the selected release to the current ebook passage. Listen from here is the long-press on a sentence. **Back to narration** resumes automatic following. It works the same from every place that asks for it (the player-bar button, `F`, its locating without a map, Listen from here and its Undo, the audio slider when it is released and the "Follow the narration" switch): a place chosen by hand that is still waiting for its save is dropped when there is a narrated sentence to follow on a map the server has confirmed for the current audio, so it cannot overwrite the listening place, and kept and saved when there is none, until following starts to work (a map shown from this device's cache counts once the server confirms it). The audio slider decides for the place the narration reached, after another file has loaded. A locating answer that arrives after the reader moved on, or after another map replaced the one it was asked with, is ignored. Optional follow-along highlights narration without writing new reading events. In pages mode a narrated sentence that crosses a page is highlighted on both pages, and the page turns inside it when the narration reaches the first word on the next page (estimated by spreading the sentence's time over its words); a jump in the audio shows the page of the word being narrated, a pause keeps the page, and a page turned by hand turns nothing until **Back to narration**. A sentence over several pages turns at each page's end; a word hyphenated across the page turns at its first character on the later page, at that share of the word's time; a picture in the sentence moves the turn to the word it pushed onto the next page. With two pages side by side (a wide window) the turn comes when the narration leaves the second page. The break is read from the word boxes as drawn when the sentence begins, again after each turn and after a change of font, text size, line height, margins or window size; the view measures it anew at each turn (`src/prepared-view.ts`); nothing is kept between sentences. When a word of the sentence has no box, the page turns at the sentence's midpoint. Scroll mode does not turn.
5. Timings are **estimated**, with unmapped passages left unsynced. The Reading sync page shows the outcome, and its **Details** the engine and the accumulated worker stage times. Manual sentence start/end corrections (`POST /api/alignments/:id/anchors`) are still accepted from older clients; no screen offers them now. A replaced EPUB or changed audio file invalidates its map.

**The Reading sync page** (#540, `src/pages/reading-sync-page.tsx`; its words and rules in `src/pages/reading-sync-model.ts` and `src/status-lines.ts`): `#book/<workId>/sync`, opened from the Book page's Reading sync row once the work has a recording and an EPUB (the row's name is the link, its info mark a button beside it), and from Activity's Now for a reading sync that is running, waiting or stopped. An address of a work without a recording or an EPUB shows its Book page in place of the entry. A Page header "Reading sync" with its tooltip ("Back to the book"), the book's title, then the pair the reading sync is for: **Recording** (the chosen recording's narrator, opening the Audiobook page) and **Edition** (the chosen EPUB with its size, opening the Ebook page). Then the Status: while it is prepared, the seven steps (Waiting for a worker, Copying audio, Decoding audio, Encoding audio, Anchoring text to audio, Aligning text, Saving the map) with the running one in bold, its count ("24 of 43 files", "3 of 8 parts", "2 books ahead", "2 in line") and its bar, the worker, its processor and the time so far on the caption ("On wsl · GPU · 12 min"); a job of the older window engine reads "Preparing · 43%" with its sections or passages and no steps. Ready (and a finished partial map of more than 95% of the text; 95% exactly is Partly ready) or Partly ready with "Timings are estimated" and Text mapped; No text matched with "Choose another recording or edition above."; Not available ("Reading sync works with English books only", or before any job when the options say the ebook and the narration are in different languages); Paused ("Resume starts this book over"); Cancelled; Stopped with the step it stopped in, the server's line and each worker's reason, and **Workers** "1 of 2 online" from `GET /api/alignments/pool`; while Prepare again runs over the map in use, the map's state "In use until the new one is ready" and Preparing again with the new run's steps; a new map not used reads "Not used: it matched 40% of the text" under Prepare again. Each state has its buttons (Pause or Pause after section, and Cancel; Resume and Cancel; Retry; Prepare again; Prepare): Pause, Cancel, Resume and Retry send `PATCH /api/alignments/<id>`, and Prepare and Prepare again send `POST /api/alignments` with only the ebook and the recording; a job that is no longer listed says "This reading-sync job is no longer listed. Reload the reader to see its current state.". On a stopped job the administrator's **Workers** row ("1 of 2 online") opens Activity › Server. **Details** (`#book/<workId>/sync/details`, "Back to Reading sync") lists Engine, GPU use, Processing time, the stage times, the warning, the older engine's line and its flags. Unsynced passages come last, with their count, each with its excerpt and sentences. The page reads the job from `GET /api/alignments?ebookId=<edition>` on open and every 4 seconds while it is visible. Someone who is not the administrator sees no buttons, no Prepare again, no Workers row and no worker's name. Without a connection the page shows the line the stored work has and "No connection".

The production server runs no alignment worker (#279): every alignment, probe and passage-locating request goes to a pool worker (WSL, then lisa), which is protected by a private token (`ALIGNMENT_WORKER_TOKEN`, the same value in `.env` and in each worker's `worker.env`). Audio is staged over SSH into the worker's own `MEDIA_ROOT/alignment/pool-jobs`; a probe's copy is removed when the probe ends, a job's stays until the administrator removes it: `GET /api/alignments/pool/staging` (admin only) lists every staged folder per host with its size and whether a run would remove it, and `POST /api/alignments/pool/staging/remove` (admin only, optional `{"host": "<id>"}`) removes the folders of finished or deleted jobs, never a folder the server has no record of, and nothing on any host unless every configured host was listed and no host's media root or pool-jobs folder (real paths) lies inside another host's pool-jobs folder (ADR 0013, #421). A probe folder left by an interrupted probe stays listed as unknown; the administrator removes it by hand (`docs/CTC_WORKER_POOL.md`). Models, temporary audio and analysis stay there. The pinned Wav2Vec2 Base CTC checkpoint is downloaded explicitly with `download_model.py` by `scripts/install-ctc-workers.sh`. Ordinary processing uses local weights and never downloads them. No paid API is called and audio leaves the server only for the owner's pool hosts. Reading again uses the cached map, with no inference charge. See [the measured local benchmark and limits](docs/ALIGNMENT_BENCHMARK.md).

Chapter-paired and anchored alignment use the CTC engine (Wav2Vec2 Base, English only). CTC runs only on the remote pool: WSL's GPU first, then lisa's CPU. The pool is disabled unless `ALIGNMENT_POOL_ENABLED=1`; when disabled, CTC jobs fail with instructions to enable it and can be resumed later. If remote dispatch fails, the Reading sync page's Stopped status lists the failed step and reason for each host; **Resume** starts a new attempt. `ALIGNMENT_BOOK_JOBS=1` (off by default) runs every full alignment as one whole-book job on the worker under one lease instead of the window requests below, and rebuilds every map of the window engine under the whole-book engine (`docs/CTC_WORKER_POOL.md`, "The server's whole-book runner"); a pause or cancel cancels the worker's job, so a resumed job starts over there. A whole-book job waits for a busy GPU host rather than taking a CPU host, which it takes only when no GPU host can be used (down, unhealthy, without whole-book jobs, or it failed this job); the Reading sync page shows such a job's worker step and count (Decoding audio, "24 of 43 files") and its pause button reads **Pause**. Activity › Server lists each pool host with its status, device and current work (`GET /api/activity`; `GET /api/alignments/pool`, admin only, still answers reachability, busy state and last error), and `LOG_LEVEL=debug` logs non-GET `/api/alignments` requests with status and duration. Alignment, ebook-candidate probing and passage locating all run on the pool; reading sync is available, and newly linked pairs are queued, only when the pool is enabled and `ALIGNMENT_WORKER_TOKEN` is set. A leftover `ALIGNMENT_WORKER_URL` is ignored. Whisper and aeneas were retired in #279, with the aeneas rollback switch; a job an older engine made that becomes active again (for instance on **Resume**) is planned under CTC before it runs. Each CTC worker needs the pinned checkpoint in its own media root (`download_model.py` fetches and verifies it); no model is downloaded during processing. Set `ALIGNMENT_CTC_DEVICE=cuda` on a GPU worker (the worker defaults to `cpu`). The model is loaded once per worker process from `alignment/models/ctc` and its checksum is verified. Non-English books remain unsynced with an explicit "language not supported" outcome. Passage checks compare constrained timing with unconstrained CTC hypotheses, local coverage, neighboring candidates, blank structure and timing. Failed checks leave the affected sentences unsynced. Oversized paths are split into bounded scopes; a sentence that cannot fit is left unsynced. Existing aeneas maps stay readable until their automatic engine-generation rebuild finishes. A manual prepare (`POST /api/alignments`, Prepare again) keeps the map in use the same way when that map has intervals and was made from the ebook and audio files as they are now (#538): the listing and `/map` serve it with the new job under `rebuild` (its status, `bookJob`, `generation`, `poolErrors`, `coverage`, `elapsedSeconds` and `createdAt`; someone who is not the administrator gets `bookJob` without its host and no `poolErrors`), and a new map that maps none of the text, more than 2 points less, or ends "language not supported" is stored as rejected while the map in use stays. Pause, cancel and a failure keep it too; it is admitted as new work, ahead of automatic rebuilds. Over a stopped, cancelled, no-text or not-available job, a map of changed files, or on a first prepare, nothing is kept. See [CTC pool setup and qualification](docs/CTC_WORKER_POOL.md).

Ebook-set candidates are checked against the audio with the same CTC engine (ADR 0005 amendment). The 30-second samples of the ADR 0004 outlier check are scored one `/anchor` request each against the recording's cached emissions, on a leased pool host (WSL first, lisa as the fallback; never the production worker), so the candidates of one run share the recording's acoustic pass (re-evaluating several held candidates also shares one staging of the audio; a run that downloads candidates frees the host between them). The outlier rule is unchanged. A candidate with no audio on the server yet stays held (`awaiting_audio`); one held because no pool host was free, the pool is off, alignment is paused, or the probe failed on both hosts has `awaiting_worker`; an EPUB that is not English has `language_not_supported`.

An EPUB added to a work (`POST /api/ebooks` with a `workId`, or an upload with `?workId=`) is saved, linked and recorded as a `pending` member, and the request returns at once; its response carries `ebookSet: { status }` next to the fields it always had. The check runs in the background in the ebook-set check loop (Activity › Server's **Ebook checks**) (`server/ebook-set-evaluation.ts`, every 30 s and at start, so a member left pending by a restart is picked up) and ends the member accepted, rejected or held. The loop also re-examines a member held `awaiting_worker` once the pool and worker token are configured and the hold is 10 minutes old. An evaluation that throws (a broken EPUB) holds the member as `evaluation_failed` with the message; such a member, and a sibling whose EPUB cannot be parsed, is not used as evidence for another member. Both pause switches (the loop's and alignment's) are read before each member's check: a check that runs finishes, the others stay pending. A result is written only if the member is still the one the check started for and its ebook is still linked to that work; otherwise it is dropped, and a member whose ebook moved to another work is not checked. Linking an ebook to another work (`POST /api/reader/:id/link`, or saving or uploading it again for another work) removes its pending member in the work it leaves in the same transaction, and that work's set is synced as after any member removal; a member with another status stays, and the work it joins gets what it got before (a link adds no member there). Reevaluate skips a member whose ebook is linked to another work and removes it if it is pending. Nothing automatic queues an alignment for an ebook whose member is pending: the upload, link and audio-import auto-queue, the backfill and the engine rebuild scan pass it by (the scan rebuilds such an older map at its next run, at start). Prepare in Reading sync (`POST /api/alignments`) is not gated, as before. Once a check ends (accepted, rejected or held) the alignment is queued right after its result is written, before the next member's check starts, as the upload queued it whatever the check said; the auto-queue's own conditions (pool and worker token, same work, language, audio) apply as before. Reevaluate does the same for a member it moves from pending to a result; a held member it checks again queues nothing. A failure to queue is logged and the batch goes on. A **spare edition** (an EPUB of the work that is not read: not the set's shared default or, without one, the work's first EPUB, and no account has a place in it; `server/ebook-chosen.ts`, ADR 0024) gets no whole-book sync by itself: the upload, link and audio-import auto-queue, the queueing after a check and the backfill skip it (`skipped.spare` in the backfill's answer). A cancel is final (#744): a cancelled pair is passed by the same way (`skipped.cancelled`), so a job cancelled while it ran on a pool host is not planned again by the auto-queue, the queueing after a check or Prepare for all books; Prepare and Resume of the book still run it, and the engine rebuild scan leaves a map the backfill made for one; Prepare still syncs it, and an edition someone starts reading is synced by the next backfill. An ebook search for a work (`fetchTopKIntoEbookSet`, also from a series) fetches one EPUB and checks it, and fetches the next only when that one is rejected or its download or check fails, at most five; one accepted or held ends the search. A series' ebook search asks its sources in order (#901): Library Genesis, Anna’s Archive and Z-Library when set up, the libgen.rs family, Prowlarr when it is connected, then Standard Ebooks and Project Gutenberg for a book published 96 or more years ago; a source that fails is passed for the next. A Prowlarr release whose title matches the book is started as an ebook download (the search ends there; its EPUB joins the set when it is complete). A search that found no accepted or held edition while a source could not be asked (Library Genesis limiting requests, a source out of reach) goes back in the queue, not before Library Genesis's rest ends, at most three times, as an audio search does. On Activity's Now, the syncs of a book's spare editions that were queued by themselves are one row under Waiting, "Checking another edition" or "Checking 4 other editions · 1 of 4", and a finished one is not listed under Finished today. A server stop between the result and the queueing leaves it unqueued; the backfill picks the ebook up. Activity shows only the member being checked as running, with its stuck time counted from the start of the check; members waiting for their turn are queued.  `POST /api/works/:id/ebook-set/reevaluate` evaluates pending and held members and waits for the results; Retry on the Activity item evaluates one member again in the background. An EPUB that is already an accepted or rejected member keeps its result when it is added again. The Ebook page shows a pending member as "Checking against the narration".

The alignment processor aligns up to two books at once (`ALIGNMENT_ADMITTED_BOOKS` in `server/alignment-scheduler.ts`); with one resident model per device that is one book on WSL and one on lisa. The next queued job starts as soon as a running one finishes. Two jobs for the same recording never run at the same time. Each job is claimed in the database by the running server and its generation; a cancelled or rebuilt job's late results are discarded, and after a restart an interrupted job resumes once its old claim is 30 seconds stale (immediately after a clean shutdown), ahead of newer queued work. The worker encodes acoustic chunks in microbatches of 4 (`ALIGNMENT_CTC_ENCODE_BATCH` overrides it) and halves the microbatch on an out-of-memory error; later requests of that job keep the halved size. The job's `runConfig` records the books admitted, resident models per device, microbatch configured and in use, the number of halvings, path-decode workers (2) and audio extraction workers.

CTC stores completed float32 acoustic chunks under `alignment/ctc-acoustic-v1`, shared by ebook editions of the same recording and engine. Audio bytes are fingerprinted, so changed audio is encoded again; interrupted work can reuse completed chunks. The default cache budget is 5 GiB, evicting least recently used recordings as needed. Set `ALIGNMENT_CTC_CACHE_BYTES` to a nonnegative byte count (up to 1 TiB), or `0` to disable the cache. A recording larger than the budget is cached only while space permits. The job's `acousticEncoding` and `acousticCacheRead` stage timings show encoding and cache reads separately.

To qualify this route on WSL or lisa, run `python3 worker/gate_ctc.py --help` for the labelled-sample gate arguments. Supply the trial's `reference.json`, `gold.json` and audio under the worker's media root, an output under its alignment directory, and the worker token through `ALIGNMENT_WORKER_TOKEN`. The gate scores `/align`, checks that CTC discovery locates the first and last labelled sentences, and checks that an unrelated chapter is unsynced. Missing utterances count in the denominator. It is intentionally outside `npm test` and requires the real model.

The worker stops a request that runs too long, so one runaway section cannot keep a core busy. Each `/align` request (audio extraction and CTC alignment) gets `min(ceiling, base + per_second × audio seconds)`: by default 120 s plus 0.15 s per second of audio, at most 1200 s (390 s for a 30-minute section, 1200 s for the 2-hour maximum). `/anchor` samples use the same formula capped at 150 s. At the limit the worker stops timed-out work, removes the temporary files, frees the job slot and answers HTTP 504. If the process does not die (for example a read blocked on a failing disk), the worker still answers 504 but keeps the slot busy and reports `stuck` until the process is gone, so a second job never runs next to a runaway one; the reading-sync job then shows "The alignment worker timed out on this section. Retry later, or choose a release with chapters." and keeps the sections it had finished, so **Resume** retries only that section. Override the limits with `ALIGNMENT_TIMEOUT_BASE_SECONDS` (0–1500), `ALIGNMENT_TIMEOUT_PER_AUDIO_SECOND` (0–1) and `ALIGNMENT_TIMEOUT_MAX_SECONDS` (1–1700) in the pool worker's `worker.env`; a value outside its range or not a number is ignored with a warning in the worker log. The ceiling stays under the server's own 30-minute wait so the worker's error is the one shown. A chapter-mode section longer than the limit (more than about 2 hours at the defaults) now fails with that message instead of running without bound; splitting long sections is not implemented. `GET /health` on the worker reports `busy`, `stuck`, `busySeconds` (how long the current job has held the worker, or `null`) and `lastTimeout` (ISO time of the last timeout, or `null`). Python tests for this live in `tests/worker/` (`python3 -B -m unittest discover -s tests/worker`).

CTC uses the same request limit. If resident inference outlives it, the worker answers 504 and holds the slot as `stuck` until that inference exits; its late result is discarded. Restart the worker if a GPU operation never returns.

Hardcover's two-way reading progress, with its durable retry queue, went with Hardcover (#721 part d): EPUB reading is published nowhere. Precise CFIs and timings stay in Sonder, and reader updates do not overwrite a recording’s listening checkpoint.

A download with no work yet has no work and keeps its own cover; a backup has none of the three. `facts` is one shape per kind (`ActivityFacts` in `src/types.ts`): the feature's own status word and, where the kind has them, a download's backend, a reading sync's outcome, coverage, worker stage and file counts, an ebook check's hold reason, a series search's kind. `attention` is true for an item that failed in the last 7 days, is stuck or is blocked, decided in `buildActivity`; the response's `attention` count is these items plus the down processes, as before.

A whole-book reading sync is judged by its worker stage (`bookStagePace` in `server/alignment-activity.ts`): a stage that reports as it goes (decoding, encoding by the audio encoded, aligning) is stuck after 20 min without a change; one that reports nothing until it ends (anchoring, the last pass, the text check after the encode) after 2 h, and an older worker's encode, which reports only finished files, after half the recording's length if that is longer; one that waits for another book's encode, the disk budget, its turn to resume or the window requests is never stuck. A stuck whole-book sync says "No progress on <host> for …" and offers **Retry**, which starts it again from the beginning while it still runs. ## Prepared text

The server makes an EPUB's text ready to read (ADR 0025; `server/prepared-text.ts`, `server/prepared-text-cache.ts`), so a page does not have to download the EPUB, lay it out and find the sentences again. The built-in reader shows it (next section) and never opens the EPUB file. The sentences are the ones `GET /api/reader/<edition>` lists, with the same ids and the same stored text; preparing never cuts or renumbers a sentence, it places each one by its stored block and offsets.

- `GET /api/reader/<edition>/prepared` answers the **manifest** and prepares the book first when it is not kept. It carries an `ETag` and must be revalidated (`no-cache`): asked again with `If-None-Match` for an unchanged book it answers 304 with no body, so a second open transfers neither the manifest nor, their addresses being immutable, any part or picture. Only an EPUB edition has one; the consensus text of an ebook set has no file and answers 404. `key` names this prepared output. The manifest holds the file's `fingerprint` and `language` but not the work's title or author, which can change while the file stays: take those from `GET /api/reader/<edition>`. `parts` lists the parts in order, each with `bytes`, `chars` and `charStart` (the length of its text as a browser's `textContent` counts it, and of all parts before it), `sentences`, `ordinal` (the place of its first sentence among all the book's sentences), `first` and `last` (sentence ids) and `ranges` (the same by chapter file: `section`, `first`, `last`, `count`). `sections` lists every file of the reading order, also one without a sentence (a picture page): `index` (a locator's `section`), `href`, `title`, the `part` it starts in, `chars`, `charStart`, `sentences`, `first`, `last`. `chapters` is the book's own contents (the EPUB 3 contents document, else the NCX, else the files' headings): `label`, `depth`, `section`, `part`, `sentence` (the first sentence at or after its start, or null) and `anchor` when the contents name an element. `problems` lists sentences that could not be tagged with their stored text; it is empty for every book of the library the check below was run on.
- `GET /api/reader/<edition>/prepared/<key>/parts/<n>` answers one part: HTML of about 120 KB (`PART_TARGET_BYTES`), cut before a block and never inside a sentence, so a part can be larger when one sentence or one block is. Short chapter files share a part; each file's text sits in `<section data-section="<index>">`, which a part closes and the next opens again when a file is cut.
- `GET /api/reader/<edition>/prepared/<key>/pictures/<name>` answers a picture of the book. Parts and pictures are cached for good (`immutable`): a changed EPUB file or changed preparing code gives another key, so another address. A key the server no longer keeps answers 404 with `code: "prepared_stale"`; load the manifest again. Only a part or picture that was served is kept by the browser: every refusal or failure of these three routes (not signed in, not found, a file that cannot be read) answers `Cache-Control: no-store`.
- **Sentences** are `<span data-s="<id>">`. A span holds text only, so a sentence with emphasis inside, or one that runs across blocks in a book made of bare `<div>`s, is several spans with the same id, one after another; their text joined, normalised as the server normalises (NFKC, runs of white space as one space), is the stored sentence. The page keeps the book's own characters (ligatures, an ellipsis, non-breaking spaces). Text the server does not count as a sentence (a table cell's loose text, the book's own contents list) is shown without a span.
- **What is kept**: headings, paragraphs, emphasis, block quotes, lists, tables, line breaks, rules and pictures, and from the publisher's stylesheets only these hints as classes: `t-c` and `t-r` (centred, right), `t-i`, `t-b`, `t-u`, `t-sc` (small caps), `t-up` (upper case), `t-ni` (no indent), `t-in1` and `t-in2` (indented block), `t-pb` (page break before), `t-hide` (the book hides it; the text is still a sentence), `t-pagebreak` (a print page number), plus `t-nav`, `t-p` and `t-table`, `t-tr`, `t-td`… where a container is written as a `<div>`. An element's `id` becomes `data-id`; a link inside the book carries `data-part`, `data-sentence` and `data-anchor` instead of an address.
- **Sanitising** happens here: the output is written tag by tag from an allow-list (`ALLOWED_TAGS`, `ALLOWED_ATTRIBUTES`), all text is escaped, and nothing of the book's markup is copied. No script, style, handler, frame, object or form survives (the words inside a refused element stay when they are sentences); a picture is shown only when it is a file inside the EPUB; the only addresses written are those pictures and `http(s)`/`mailto` links. Parts and pictures are served with `nosniff` and a sandboxing Content-Security-Policy, so an SVG picture opened by its address runs nothing.
- **Prepared ahead** (#827, `server/prepared-text-ahead.ts`): a book's text is ready before anyone opens it. An imported or downloaded EPUB is prepared in the background as soon as it is saved (the import's answer does not wait). A **sweep** prepares every EPUB edition that has no current prepared output (a deploy with new preparing code, a new Node, a file replaced on the drive, what a restart interrupted). It takes one book at a time: first the books someone is reading, latest place first, then the smallest, so the largest come last. For each book it prepares it also moves the places saved in the standard cut of a book that is cut by another rule (ADR 0026, `bookWithPlaces`), so the Book page shows the right share before anyone opens the book. It may be stopped at any point and run again, a second one joins the one that runs, and it writes its progress to the server's log ("prepared text: 12 of 80 editions to prepare", "prepared 3 of 12", "the library is prepared").
- **When the sweep runs.** A deploy starts it: `scripts/deploy.sh` runs `scripts/prepare-library.sh` after its live checks have passed, which starts the sweep on the running server and waits for it (`--no-wait` only starts it), so nothing heavy runs while a check plays real audio; a library that could not be fully prepared is said loudly and does not fail a deploy that is already live. The server's own first sweep waits `PREPARED_TEXT_FIRST_SWEEP_MINUTES` (15) after a start, for a restart without a deploy, and then runs every hour. The administrator's `GET /api/prepared-text` answers the counts and `POST /api/prepared-text/backfill` starts a sweep. `PREPARED_TEXT_AHEAD=0` switches preparing ahead off (the import's and the server's own sweep; the route and the command still sweep when called); a book is then prepared at its first open, which works either way. It does not bring the preparing back to the server's thread.
- **What the sweep removes.** Only the folders of editions that have left the library. An edition in the library keeps every folder it has: the one of a file that is away (the drive may be coming back), and an older output of a changed file or of older preparing code, which goes when the new one is in place and serves readers until then. A database without any edition removes nothing.
- **A book that cannot be prepared** is named once in the log and skipped; the next book is tried. It is tried again when its file changes, after a day of sweeps, or when the server restarts. A failure of the file system (the drive dropped, the disk was full) is not remembered: the next sweep tries the book again. A book that fails at its import is said in the server's log too.
- **Off the server's thread.** Preparing runs on a worker thread per book (`server/prepared-text-worker.ts`), because it holds a thread for up to a second at a time on a large book and the server answers nothing while its own thread is held, audio included. Measured on the production host with `scripts/measure-prepared-stall.ts` (the library's largest book, 71,225 sentences): the server's event loop is held under 20 ms while the book is prepared, against 350 to 450 ms when the same work ran on its thread. The sentences are still cut on the server's thread first (`extractBook`): 2 to 3 s for that book with single blocks of up to 0.3 s, as at every first open of a book after a restart; the sweep pauses half a second between books so those come in separate bursts.
- **The thread's ceilings.** `PREPARED_TEXT_THREAD_MB` (512) is its heap: the largest book uses 171 MB when held to 256 and runs at full speed there. `PREPARED_TEXT_THREAD_SECONDS` (300) is the time after which it is stopped: the slowest real book took 13 s. `PREPARED_TEXT_THREADS` (2) is how many run at once, the sweep's and the readers' together; each adds 160 to 530 MB to the process while it runs. Books prepared ahead never take the last thread, so a reader's open finds one free or waits only for another reader's book, and a reader who opens a book that waits to be prepared ahead moves it to the front. A thread that runs out of memory or time, exits or throws is one failed book: its reader gets "This EPUB could not be opened.", the cause is in the log, and nothing of it is left on the disk.
- **The size limit and the sweep.** `PREPARED_TEXT_CACHE_MB` (2048) bounds the cache; the library's 80 EPUBs take about 170 MB with their pictures. The sweep never removes a current folder to make room, and stops preparing ahead when the cache is nine tenths full: the remaining books are prepared when they are first opened, the log says how many ("the cache is full"), and `GET /api/prepared-text` answers `full` and `waiting`. Only an open of a book that is not prepared removes the folders read longest ago to get back under the limit. Raise the variable when the library outgrows it.
- **The cache** is `MEDIA_ROOT/prepared-text/<edition>-<key>/`. Requests that arrive together prepare a book once; the folder is written beside its place and renamed into it, so it is whole or absent, and nothing is written when the media drive is not the recorded one. After each preparing, the edition's older folders and abandoned work go.
- **The key** (`preparedKey`) covers what the output is made from and can change under a kept folder: the EPUB file by its size and time (the stamp `extractBook` goes by), `PREPARED_TEXT_VERSION` (raise it with any change to the output; a test fails otherwise), `EXTRACTOR_VERSION` in `server/reader.ts` (raise it with any change to which text is a sentence or what id it gets) and the ICU version of the running Node, whose data `Intl.Segmenter` cuts sentences with. The sentences are cut again after every restart, so without the last two a kept folder could hold other ids than `GET /api/reader/<edition>` gives. The key does **not** see a file replaced by another of the same size and time (a restore, `cp -p`); the manifest's `fingerprint` is of the file's content, and a reader that compares it with the fingerprint of `GET /api/reader/<edition>` notices.
- **The allow-list** is `src/prepared-text-rules.ts`, one module for the server and the reader: the elements, the attributes, the classes, the form of a sentence id and the two address rules (`allowedLinkAddress`, `allowedPictureAddress`), with `refusedElement(element, base)` to check a node as a browser's DOM gives it. The server writes from it; a reader should parse a part with the browser's own parser and check every node with it before the part enters the page.
- **Limits.** A chapter file over 5 MB or a reading order that leaves the archive is refused; a picture over 20 MB is left out, and a size read from a picture's header is used only up to 16,384 pixels a side. U+0000 is left out of the text and of `chars`, as a browser leaves it out. Markup nested too deeply to write answers "This EPUB is nested too deeply to open." A part has no upper size when one sentence or one block is larger than a part (a chapter of bare `<div>`s without a full stop is one sentence): no book of the library has one over 124 KB, and no ceiling is set.
- `npx tsx scripts/check-prepared-text.ts --db data/sonder.db --out artifacts/prepared-text-check.json` checks a whole library: for every EPUB edition each tagged sentence equals the stored one, every id once and in order, and the manifest's counts are those of the parts; it also times the largest books. It works on a copy of the database and writes only to a temp folder (see `docs/LOCAL_CHECKS.md`).

## The new reading view

Steps 3 to 7 of the reader plan (#799, #802 to #806): the reader shows the prepared text in the application's own page. Since step 7 (#806) it is the only reader: epub.js, DOMPurify and the reader's frame are gone, and the hidden switch that chose the view (`?reader-view=`) does nothing any more.

- **Scroll and pages** (step 4, #803). The view follows the saved Reading mode. In scroll mode it is one moving column. In pages mode a page is a CSS column, one in the band or two side by side on a desktop with room for them (`src/reader-spread.ts`, as in the epub.js reader before it); the view turns the pages itself on a tap in the outer thirds, a swipe, the arrow keys and the desktop's page arrows, and nothing scrolls under the finger. Nothing of the whole book is laid out. Every part begins on a new page, with two pages side by side on a left page (a part of an odd number of pages ends with an empty right page), so a part's pages depend on that part, the band and the style alone and are the same whatever parts are in the page around it; nothing is measured when a part comes or goes. Each loaded part is a run of columns of its own, in a box exactly as wide as the whole pages it fills, and the parts stand side by side (a forced column break in one run would say the same, but Firefox has none). A part is put in as the reader nears either end of the run and is whole in the page before any of its pages is shown; a part before the pages shown moves them by the whole pages it fills. The price is a short page where a part ends inside a chapter (ADR 0025). The page shown is held by a place in its text, never by a column's number: the place is where the reader last moved to and is not taken anew when the text is laid out again, so parts that come and go, another text size, Appearance opened or a band resized again and again do not move it. Every length of a page is a whole number of px (the text's box is exactly one page or two wide), so the pages stay exact at any width of the band. At most five parts are in the page reading on or back, and a tap for a page whose part is still on its way turns when the part is there. A page's saved place is the first sentence that starts on it, and opening the place shows exactly the page that was left at the same width and style. `positionInBook` (`src/prepared-book.ts`) gives a sentence's position in the whole book from the manifest's character counts alone, for the position bar of step 5. `tests/e2e/prepared-pages-walk.spec.ts` walks the pages at random from a seed and holds every page to the rules (it has text, joins the page before it, no line is cut, it does not change while shown, it comes again as it was read): four short walks in the suite, in Chromium (the smallest text, a part some two pages), at most 40 turns each, and by hand the long one, `SONDER_WALK=long npx playwright test tests/e2e/prepared-pages-walk.spec.ts --project=chromium` (the whole book backwards and forwards again and every kept seed, about 25 minutes a browser; `SONDER_WALK_SEEDS`, `SONDER_WALK_PARTS` and `SONDER_WALK_BAND=390x844` choose other seeds, lengths and a phone's window). The other pages-mode specs (`prepared-pages.spec.ts`, `prepared-pages-parts.spec.ts`, `prepared-pages-same.spec.ts`) open the book next to the few joints they cross, in a tall band where parts must come and go on the way (#904); `SONDER_LONG_READS=1` adds the read of the whole book backwards across every joint and a part's pages at a phone's and a desktop's height, and runs the long walk.
- **One head and foot.** `components/Reader.tsx` holds the head and the foot; the text band is `src/prepared-view.ts` (no React, no frame). The highlight, Listen from here (a long press), following through the one following module (ADR 0014, unchanged), Back to narration, bookmarks, Chapters, Bookmarks and Search work as in the epub.js reader before it. Nothing is drawn over the text (ADR 0019): the narrated sentence is marked by its own elements' background.
- **The same places.** A place, a bookmark and a checkpoint name a sentence id, as before; nothing is migrated and no alignment map is invalidated. The reader saves a place without a CFI and reads only the sentence of a place the epub.js reader saved with one, so every place, bookmark and checkpoint saved before step 7 opens as before. An older build still open in a browser may send a place with a CFI; the server keeps accepting it.
- **What an open asks for**, each once: the manifest (`GET /api/reader/<edition>/prepared`, revalidated by its ETag), what the user saved (`GET /api/reader/<edition>/state`: the work, its title and author, the checkpoint and the bookmarks, per user, `private, no-store`), the part that holds the place being opened, and the reading sync map. It asks for neither the book's sentences (`GET /api/reader/<edition>`) nor the EPUB file. Playback warming asks for the same manifest and map, which the reader then shares. A second open of an unchanged book transfers nothing for the manifest (a 304), its parts and its pictures.
- **Parts as the text is read.** Only the part with the place shown is loaded, its neighbours as the text is scrolled towards them, at most five in the page at once; a part far from the view is taken out again. Opening a long book costs what is on screen, not the book.
- **How a part enters the page** (`src/prepared-html.ts`). A part's string never becomes markup of a live element. It is parsed with `DOMParser` into an inert document, every element is checked with `refusedElement` of the one allow-list the server writes from (`src/prepared-text-rules.ts`), and the page's nodes are made one by one from those that pass. An element that does not pass stays out with everything under it and the rest of the part is shown; the reader reports it once for the part (`POST /api/reader/<edition>/prepared-refused`, a line in the server's log with only printable characters, at most six a minute for a user and a book), so a miss in the server's sanitiser is seen. A link out of the book opens in a new tab without its opener. The application's Content-Security-Policy is report-only in production and is not relied on.
- **The look** (`src/prepared-text.css`) is the application's: the reader's Appearance (font, size, line height, margin, width), the app's colours and the spacing tokens. The publisher's fonts and layout are dropped on purpose (ADR 0025); the server's style hints (`t-c`, `t-i`, …) are drawn. Text a book hides (`t-hide`) is hidden, as the epub.js reader hid it; it is still a sentence, and following and the highlight pass over it without moving the text.
- **When something cannot be loaded.** The manifest, the saved place and each part are asked for at most three times (waits of 1 s and 3 s); a refusal that stands is asked once, and "too many requests" is never asked again by itself unless the server names a wait of at most 10 s. After that nothing asks again until the reader does: the foot says "This part of the book could not be loaded." or "This book could not be loaded." with Retry, and a part that failed stays failed without another request. Without a connection a book kept on this device reads from its kept prepared text (next bullet); any other says "This book needs a connection to be read.". A book that keeps answering that its prepared text is stale is loaded again twice, then it is an error. The view never shows the browser's or the server's own sentence for a failed request.
- **Kept on this device** (#805, step 6): Keep on this device keeps the chosen EPUB's prepared text beside the book's tracks and map: every part and every picture the parts show, each under the address the server serves it at (a picture with the server's sandbox), and the manifest under its output's key, in the browser's Cache Storage (`sonder-kept-text-v1`, `src/keep-text.ts`, `src/keep-text-store.ts`). With them it keeps the book's sentences, which Search reads (`GET /api/reader/<edition>`, stored as `reader-book:<edition>`). A record `reader-text:<edition>` is written once every file is in, so a save that stopped leaves none and resumes without asking again for what it stored. The text is the book's file (no EPUB file is kept since step 7, #806: `KEEP_EPUB_FILE` is off in `src/keep.ts`), saved last in its save, and a book the server cannot prepare waits for Retry as a refused file does. A book kept before step 7 has its EPUB file and may have no text: it is Not complete until its text is saved at the next run of Keep, and its EPUB file is removed at the run that finds its text complete. The pair's map is matched against the kept text's file. The reader reads a kept part from there before the server (its address names the output, so it is the server's own), takes the kept manifest when the server does not answer (at once without a connection), and the service worker answers a kept picture. What the user saved comes from the device when the server does not answer: the state stored at the last open, the place saved here and the bookmarks that wait to be sent; Search uses the kept sentences when their file is the manifest's. A manifest the server answers for another output (the file changed, the server prepared it anew) marks the kept text stale: it still reads offline, and the next run of Keep saves the new output and removes the old one. Off and Remove remove it with the book's other files; Reset this device keeps it.
- **Search** searches the sentences on the device, as before. The reader holds no sentences, so the Search page asks for them (`GET /api/reader/<edition>`) when it is opened and shows its waiting line meanwhile; the reader's open never waits for them. Without a connection a kept book's kept sentences are searched. If their file is another one than the manifest's, the prepared book is dropped and loaded again.
- **A book with text outside any sentence** (a stored cut that leaves stretches untagged) reads normally; where no sentence is in view the place saved is the last sentence before it, and following and Listen from here hold on to tagged sentences only.
- **The text position rail** (#804, step 5; in both reading modes): a thin column of the book's chapters in the text band's right margin over the band's whole height, always shown (`src/text-rail.ts`, its rules in `src/text-rail-model.ts`). The thumb stands on the first sentence in view, in the accent colour while following; paged away, a narration mark shows where the narration is. Dragging the thumb moves the text as a scroll by hand does: following pauses, Back to narration returns, and the place let go at is saved as a hand move saves it; the audio is never touched. A place chosen on the rail (a drag, a click, a key) is a navigation as a page turn by hand is, so it counts as the reader's also in the moment after a follow jump; a press on the thumb that does not move it changes nothing. With the focus on the rail, Down and Up move one band, Page Down and Page Up a chapter, Home and End go to the ends; Left and Right stay the app's keys. Held on the rail the thumb moves finely: the rail is zoomed in 8 times about the thumb's place, with the whole of it shown at the band's outer edge, so a short chapter can be found. Pulling the finger away sideways zooms out, from 32 px, to the whole rail at 100 px, where the finger's travel is the thumb's. A press away from the thumb goes to the place the rail shows there, at any zoom. On touch the rail takes a finger only once it moves up or down; a tap there is the text's tap. A part not loaded is asked for only when the thumb rests or is let go. The text's right margin is at least the rail's 24 px and the band shows no scrollbar (ADR 0019, amended). **Reading position shows** (`appearance.reader.positionScope`; the reader's Appearance panel, and Settings › Playback) chooses what the rail is, as Progress bar shows does for the listening bar: Whole book, cut at the chapters, or the chapter of the place in view, cut at its sentences. A save from a client of an earlier build, which does not send the choice, keeps the stored one (`keepPositionScope`). In a chapter a cut stands for 2, 5, 10 … sentences where one is under 4 px, a drag stays in the chapter and ends on its last sentence, Home and End are the chapter's ends, the readout says `Chapter · N% of the chapter`, and a narration in another chapter has no mark. While the thumb is held the foot reads its chapter and percent; on a desktop, whose footer has no line for it, the head does. **In pages mode** the rail is the same through the same seam (`RailSeam`): the thumb stands on the first sentence that starts on the page shown, a place chosen on the rail shows the page that holds it as a page turned by hand (that page's first sentence is the place saved), Down and Up and a turn of the wheel over the rail turn one page, and the right margin of the page is the rail's column whatever Margin is.
- Not in these steps: PDF.

## Storage and security

- `data/sonder.db`: canonical library, recordings, tracks, download jobs, encrypted integration settings, and independent ebook editions.
- `data/.encryption-key`: generated AES-256-GCM key. Back it up with the database; losing it makes saved integration credentials unreadable.
- `MEDIA_ROOT/complete` and `incomplete`: local torrents, both mounted into Transmission as `/downloads`.
- `MEDIA_ROOT/alignment`: pinned speech models, temporary decoded audio, section results and alignment maps.
- `MEDIA_ROOT/prepared-text`: prepared reader text, one folder per EPUB edition and key. It is a cache: removing it loses nothing.
- `MEDIA_ROOT/imports`, `saved`, `ebooks`, and `demo`: imported audio, permanent stream copies, ebook files, and the included Alice sample.
- Session tokens are hashed in SQLite and use HTTP-only, SameSite=Strict cookies. Set `APP_PASSWORD` for sign-in. Cross-origin API writes are rejected.
- TorBox API keys and permanent authenticated link parameters never reach the browser. Signed links are resolved server-side. Media proxies accept only stored source records, not arbitrary URLs.
- Downloaded browser files are local device storage and are not encrypted. Signing out gates their access through the app and clears the bounded streaming cache.
- Content-Security-Policy (#76): the server sends an app-level policy on the HTML shell and `sw.js` (not on `/api` JSON). It allows only `'self'` scripts (no `unsafe-inline`, no `unsafe-eval`), blocks plugins, framing and `<base>` outside the origin, and limits `connect-src` to the app's own origin. Images also allow `https:` because catalogue (AudiobookDB, Open Library, Google Books, iTunes) and torrent-site covers are shown from their own hosts. A `srcdoc` reader frame inherits this policy and a `blob:` document inherits its creator's, so it backs up the reader's own section CSP against inline and cross-origin scripts only: it still allows a `<script src>` from the app's own origin, so the section CSP and the sanitiser remain what keep EPUB content inert. `CSP_MODE` picks the mode: `report-only` (the default when unset or misspelt, so nothing can break the app) sends `Content-Security-Policy-Report-Only`; `enforce` sends `Content-Security-Policy`; `off` sends neither. Browsers report violations to `POST /api/csp-report` (`application/csp-report` or `application/reports+json`; no sign-in needed). It stores at most 20 reports per minute per client address (and 200 in all), so one client cannot use up the quota and hide real reports; it refuses bodies over 8 KiB and writes one log line each with the directive, blocked URI and source file only (no query strings or inline data). Check the server log for `csp violation:` lines after a few days of use in report-only mode, then set `CSP_MODE=enforce` in `.env` and restart. Caddy is not involved. `npm run dev` serves the page from Vite, which sends no policy, so check violations in the Docker build. The service worker's offline shell keeps the headers it was cached with: after changing `CSP_MODE`, ship a new build (it bumps the cache) before testing offline.

App shell and bundled fonts are precached after a production build. If the installed app behaves unexpectedly, Settings › **App** › **Reset this device** (**Reset**, asked once) checks the connection, clears Sonder’s app and streaming caches, unregisters its service worker, and reloads. Books kept on this device, local settings, and unsynced progress are kept. Device downloads use bounded 4 MiB requests, retry interrupted sections and persist verified chunks in IndexedDB so they can resume after reload. Only complete files become offline downloads; previous OPFS and Blob downloads remain readable. A source without range support can still download, but must restart its transfer after an interruption. The audio proxy limits connection setup rather than imposing a two-minute deadline on an entire audiobook. **Keep on this device** (the Book page and Listen) saves a book here; Activity › This device shows what is saved and saving, with Pause and Resume, and removes a book; the Audiobook and Ebook pages choose recordings and editions. The expanded player, its Save on device and its Pause download and Resume download are gone.

A separate streaming cache retains at most 24 exact request segments, each at most 4 MiB, and is never labeled as an explicit download. Full local files support suffix, bounded, and open byte ranges plus HEAD and 416 responses. Service workers also serve byte ranges from complete browser downloads.

The mini player's source (`src/components/PlaybackSource.tsx`) reads **TorBox**, **Host server**, **Device cache**, or **Online stream** for other upstream services. This describes the serving path: a verified HDD copy of a TorBox track reports Host server, and offline files or cached streaming sections report Device cache. The choice of source uses the vocabulary's names instead: **Plays from** and **Available from** say Automatic, **Device copy** (this device), **Server copy** (the server) and **Original stream** (the online stream, "TorBox" when TorBox serves it).

Browser storage can be evicted. Sonder asks for persistent storage only when **Keep on this device** is turned on (the switch's tap, #550), and Activity › This device's **Protected storage** reports whether it was granted (**Ask** asks again). iOS background playback/download limits depend on browser and OS; locked-screen behavior still needs physical iOS/Android verification. Signed TorBox URLs and streaming fragments do not constitute an offline book.

## Verify

```bash
npm test
npm run build
npm run test:browser
```

The build rejects new empty server catch blocks and catches that discard their error. Pre-existing catches are frozen in `scripts/server-catches-baseline.json`; changing one requires handling its error.

Browser tests use a temporary isolated database and media directory. They verify mobile navigation, real audio playback, progress after reload, file import, complete offline download, service-worker range responses, and offline relaunch. Set `PLAYWRIGHT_CHROMIUM_EXECUTABLE` when using an existing Chromium installation. Unit/integration tests cover media ranges, authentication, secret storage, conflict reconciliation, source parsing, cache-hit routing, and local torrent completion. Live paid integrations require your own credentials; upstream mirrors can be unavailable or require browser verification.

Live checks exercise the deployed UI with the owner's real books and never run on a CI or build host. `scripts/deploy.sh` runs `verify-integrated-reader.mjs` and `verify-multi-user.mjs` after every deploy (`SONDER_DEPLOY_LIVE_CHECKS` overrides the list, `--skip-live-checks` skips them); `verify-playback-workflow.mjs` and `verify-reading-sync.mjs` are run by hand. `verify-multi-user-snapshot.mjs` is the multi-user check's comparison of the administrator's library, not a check of its own. Every check names only screens and controls the app has, by role and name (`tests/live-check-locators.test.mjs`), and intercepts its progress and reader writes (`tests/verification-safety.test.mjs`).

`SONDER_VERIFY_PRODUCTION=1 node --import tsx scripts/verify-playback-workflow.mjs [recording-id]` checks the deployed UI with real audio, embedded chapter seeking, precision drags, mobile/desktop widths, Plays from (available original/server sources), Earlier positions, Now playing's Listen and Read faces and the mini player. Its fresh browser uses device-only preferences and intercepts its own audio/reader checkpoint writes, preserving the listener’s canonical progress. Results and screenshots are written under `artifacts/`. Fault flags and copy removal are exercised against isolated media in the browser/API tests. `SONDER_VERIFY_PRODUCTION=1 node scripts/verify-integrated-reader.mjs [recording-id]` verifies inline reading, automatic passage highlighting, that the reader's head has no More button, long-press Listen from here with Undo, that the reader offers no view switch, and mobile/desktop layouts against an existing prepared map. It also isolates preferences and intercepts progress writes in its QA browser; results are saved to `artifacts/integrated-reader-verification.json`. Both checks start playback at the owner's saved position and may not move it, so each picks its own recording (`scripts/live-check-recording.mjs`, `scripts/live-check-playback.mjs`); a recording id on the command line (or in `SONDER_VERIFY_RECORDING`, which `scripts/deploy.sh` passes through) is only preferred, and is used when it qualifies. Neither check chooses a book the owner is listening to (#774): a recording whose saved progress for the signed-in user changed in the last 48 hours is skipped, with every other recording of its work, and the reason "listened to in the last 48 h" is recorded with the other rejections; a recording id that names such a recording is refused (exit 1) unless `SONDER_VERIFY_ALLOW_RECENT=1`, and the multi-user check's temporary user resolves and saves its own progress on a title the administrator has not played in that time while there is one. A recording qualifies when it is in the library and its saved position (the first file at 0 without progress) is more than 300 s before the end of the book and more than 60 s before the end of its file. The reader check tries each (recording, map) pair: a finished, non-projected map with intervals for an available EPUB of the work, one pair per map. Finished means ready or partial as the listing serves it (a map kept in use while its rebuild runs or after the rebuild was cancelled counts); a job that was cancelled, paused or failed, or is still running, with no published map, does not, and neither does a map whose own answer is no longer finished. Only a map of the edition Read opens counts: the check sets this device's edition to the map's EPUB, and Read opens the work's chosen edition by `chosenEbook`'s rule (the shared default Read can open, then this device's choice, then the work's first EPUB on the server, from the work as `GET /api/library` lists it), so a work with a shared default gives only that edition's maps, and a work missing from that listing gives none. After Listen the check leaves Now playing without reloading and opens Read from the dock, which still holds the selected book: after a reload the dock shows the book of the latest saved progress, which the check never writes. The long-press presses the middle of one of the narrated sentence's own highlighted lines on the shown page, not a corner of its bounding box: a sentence that starts mid-line has a box from the text's left edge, where the sentence before it is, unmapped on a partly mapped edition. A pair qualifies when the map can carry the check's own sequence, computed by `readerSequence` from the map and the saved position, the same function the check then seeks with: on the file of the saved position, each sampled passage longer than 4 s is the one highlighted at its seek target, and the check plays from a highlighted passage that another follows within 10 s, more than 60 s before the end of that file. The playback check needs the slider's chapter timeline at the saved position (`playbackTimeline` in `src/chapters.ts`, where an introduction or a gap between chapters is its own timeline) to last at least 120 s and to end more than 60 s after the saved position. The reader check asserts that Back to narration is off while the reader follows only where the map has a narrated sentence: at a saved position before the map's first sentence (an unmapped intro of a partial map, or the first file at 0 without progress) the reader has nothing to follow and the administrator's Back to narration is on to locate the passage, so the check first moves the paused audio to its first mapped sample (#744). Among qualifying candidates the reader check takes a recording that plays from the server's own copy before one that streams from TorBox or another remote source (#822), then a ready map before a partial one, then the most recently updated; the playback check takes the most recently listened. "No suitable recording" comes only from answers that say so: a listing read successfully that holds no qualifying candidate, or a map that answers 404 or 410 (stale), which excludes that map only. Any other failed request before the page opens (another status, a timeout, a body that is not JSON or has another shape) fails the check and names the request. When none qualifies the check prints `no suitable recording: <reason>`, opens no page and exits 3, which `scripts/deploy.sh` reports as skipped. A recording that was selected and then fails the check stays a failure: the check does not fall through to another recording. Without `SONDER_VERIFY_PRODUCTION=1` the live scripts accept only a local test server (loopback on a port other than 3001); they refuse the production site and its loopback port 3001, and any other URL (see `docs/LOCAL_CHECKS.md`, Live verification). `SONDER_VERIFY_PRODUCTION=1 node scripts/verify-multi-user.mjs` signs in as the admin with the password-only request older clients send, creates a temporary user, checks through the real sign-in screen and API that the user sees the shared catalogue with an empty library and none of the administrator's placeholders (an audio edition whose recordings have no track, #483, whatever its id; `scripts/multi-user-placeholders.mjs`), that Settings lists Account, Appearance, Playback and App and refuses the administrator's Connections, Users and Library and storage, gets 403 on admin-only routes, can stream, and cannot write under another user id, confirms the admin's library, progress, appearance and Hardcover state are unchanged, and always removes the temporary user (results in `artifacts/multi-user-verification.json`).

Demo recordings come from LibriVox/Internet Archive; the first Alice chapter is bundled so the initial player works immediately. Other chapters stream through the server. See `server/catalog.json` and [third-party notices](THIRD_PARTY_NOTICES.md). The covers and mark are original SVG illustrations.
