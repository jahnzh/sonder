# Sonder

A dark, mobile-first, self-hosted audiobook PWA inspired by [Vaka](https://github.com/vaka-hq/mobile). React, TypeScript, Vite, Tailwind, Radix dialogs, Fastify, SQLite/Drizzle, and Dexie. No Vaka account is needed.

## Run on this Ubuntu server

Node 24 and Docker are required. The 4 TB drive is mounted at `/mnt/usb_4t_1`. Media lives in `/mnt/usb_4t_1/sonder`; the app refuses to write media to the root filesystem if that mount is missing.

```bash
npm ci
node scripts/setup-local-torrents.mjs
# The setup script generates APP_PASSWORD privately in .env if one is not set.
docker compose build
docker compose up -d --no-build
```

Reading-sync alignment runs on the remote CTC pool hosts, not on this server; set them up with `scripts/install-ctc-workers.sh` (see [CTC pool setup](docs/CTC_WORKER_POOL.md)).

Open **https://sonder.pecori.no** and sign in as `admin` with `APP_PASSWORD` from `.env` (an empty username also signs in as admin). Caddy proxies this domain to the loopback-only app on port 3001; HTTPS cookies are enabled. The site block is recorded in `deploy/audiobooks.caddy`. For development, `npm run dev` starts the frontend at **http://localhost:5173** and the API at port 3001. Stop the production container before running development on the same API port. The server reads `.env` at startup.

`setup-local-torrents.mjs` creates a dedicated `sonder-torrents` Transmission 4 queue using the installed image and the **existing `transmission-openvpn` container’s network**. It does not change the existing daemon or its downloads. Its RPC uses port 9092, requires generated credentials, and is not published on the host. A stable volume marker is checked by both the app and the torrent daemon, so Docker cannot silently redirect media onto the system disk when the HDD is absent. Both incomplete and completed audiobook files are on the HDD. Credentials are written to the ignored, private `.env`; daemon settings live under ignored `data/transmission/`. If the VPN container is recreated with a different private IP, run the setup script again and restart Sonder. The VPN container must be running before the torrent queue starts.

`sonder-torrents` joins the VPN container's network namespace when it starts. A restart of `transmission-openvpn` keeps its container ID but gives it a new namespace, and `sonder-torrents` stays in the old one: its RPC no longer answers at `TRANSMISSION_RPC_URL` and downloads stall (#123). Settings and Activity's Now then say the client cannot be reached and name the fix, `docker restart sonder-torrents`, which makes it join the VPN's current namespace; Transmission resumes the torrents from `incomplete`. The setup script restarts it for the same reason: it compares the two containers' `State.StartedAt` and restarts `sonder-torrents` when the VPN started after it (every start of `sonder-torrents` joins the namespace of that moment, so no label is needed). To do this unattended, install the watcher on the host once from the main checkout: `scripts/install-torrent-watch.sh` (`--print` shows the systemd user unit, `--remove` removes it). It runs `scripts/torrent-vpn-watch.mjs`, which follows `docker events` for the VPN's start and checks every five minutes as a backstop. Once the VPN has stayed up for three minutes it restarts `sonder-torrents` if the VPN started after it, at most three times an hour; at the limit it stops restarting and says so in `journalctl --user -u sonder-torrent-watch.service`. It does nothing when either container is missing or `sonder-torrents` is stopped, and leaves a container on another VPN container's network to the setup script. The Sonder server itself has no Docker access.

Why the VPN restarts: between 2026-10-27 and 2026-11-14 the Docker daemon restarted `transmission-openvpn` 50 times, all with exit code 0 (Docker daemon journal). They came in six episodes: four bursts of 3 to 22 restarts about two minutes apart (2026-10-28, 10-30, 11-09, 11-13; the longest lasted 47 minutes) and single restarts on 11-04 and 11-06. The likely mechanism, from the current start's log: PIA pushes `ping 10, ping-restart 60`, and the image (haugene/transmission-openvpn) remaps OpenVPN's soft restart to SIGTERM ("Remap SIGUSR1 signal to SIGTERM"), so a tunnel that stays silent for 60 s (a PIA server or upstream outage) ends OpenVPN cleanly with exit code 0, and the container's `unless-stopped` policy starts it again until a connection holds. Health checks do not restart it (`SELFHEAL=false`, and no autoheal container runs), and the kernel log of that boot has no out-of-memory kill. The container's own logs from before its last start (2026-11-14, the host restart) are gone, so the OpenVPN message of each exit could not be read. The container lives in `/home/jahn/homelab`, so any change there (another PIA region, other ping options) belongs to that repository.

The app container binds to loopback. Put an HTTPS reverse proxy in front of it for phone access and set `COOKIE_SECURE=true`. PWA installation, OPFS, and service workers require HTTPS or localhost. On first use, add your TorBox key in Settings to enable cached streaming; without it, magnet links use the local client.

## Local checks and backups

`npm run check` checks the committed `HEAD` in a disposable directory: dependency installation, build/typecheck, unit tests, then browser tests, including extra runs of specs changed against `origin/main`. Uncommitted changes are recorded in the report and are excluded from the snapshot. Use `npm run check -- --ref <commit>` to check another revision. Each invocation has its own logs and reports under `artifacts/ci/`.

Before deploying an existing installation, create a consistent SQLite snapshot with `npm run backup -- data/sonder.db data/backups/before-<change>-$(date +%s).db`. The destination must be new; the command verifies the backup before reporting success. See [local checks and verification](docs/LOCAL_CHECKS.md) for details.

The server also makes a **daily backup** itself (#361), with the same backup function: `<DATA_DIR>/backups/daily-<day>.db`, where the day is the UTC day and its backup is due from 03:00 UTC. The loop checks every 10 minutes, so a server that was down at 03:00 makes the day's backup within 10 minutes of starting (one backup for the latest day, not one per missed day). Every backup passes `PRAGMA integrity_check` before it appears. Whether a backup is due is decided from the recorded successful runs (`backup_runs`) only, never from the file names in the folder, and a recorded day later than today (a clock that ran ahead) is ignored. Each run stores the size and SHA-256 of its verified copy before it publishes it; when a later attempt of the same day finds that file at the day's name (the earlier attempt published it, then failed before it recorded its result), it adopts the file instead of failing, and any other file there is a failure that is never deleted or overwritten. Retention removes older daily backups after a successful run only, and deletes a file only when a successful run names it, it is a regular file directly in the folder, and its size and SHA-256 are still the recorded ones; only such files count toward the 14 kept. It works newest first, one file at a time, and checks each file right before deleting it: opened without following a symlink, a regular file of the recorded size, hashed through that same descriptor, unchanged by a write during the hash, and still the inode the path names; then the path is unlinked at once. The one window it cannot close is between that last check and the `unlink` call (which takes a path): another process writing into the backups folder at that instant could have its file removed. When the rows cannot exceed the 14 kept, no file is read. A missing, replaced, changed or non-regular entry is left alone and its run stops counting. A file that cannot be read or removed stops retention for that run: nothing further is deleted, and the Activity page shows the run as succeeded with the reason its old backups were not removed. The `before-*` deploy copies and every other file in the folder are never touched, and a failed run removes nothing. A run claims its day in the database first, so two servers sharing the database never back up the same day at once; a working run renews its claim at each stage and every minute, and only a claim not renewed for 30 minutes is a run whose server stopped or hung, which the next check takes over (after a restart mid-run the day's backup therefore waits up to 30 minutes). Every failure, including an unusable backups folder, is recorded as a failed run with its reason. A run is refused, and shown as failed on the Activity page with the reason, when the backup folder has less than 1 GiB free or when it is inside the media root and the media drive check (`REQUIRE_MEDIA_MOUNT`) fails. A failed day is tried again at the next check. The backups stay on the same disk as the database; an off-machine copy is not made.

## Users

Sonder has one administrator (`admin`, password `APP_PASSWORD`) and any number of users, created in Settings → **Users**. Passwords are stored as scrypt hashes; users change their own password in Settings → **Account**. Without `APP_PASSWORD` (development and browser tests) there is no sign-in and every request acts as the admin.

- **Shared:** the catalogue and its files (works, editions, recordings, server copies, ebooks, reading-sync maps). Anyone can add an existing title to their library, stream it and save it on their own device.
- **Per user:** library, favourites, hidden titles, listening progress (still per recording), reader positions, bookmarks, appearance, and the Hardcover token, sync state and queues. Device storage is separate per user, and queued writes carry an `X-Sonder-User-Id` header so another tab's sign-in can never receive them (the server answers 409).
- **Admin only:** TorBox, torrents, Prowlarr, AudioBookBay and Library Genesis search, imports, Save to server, fault flags, removing server copies, preparing reading sync, linking ebooks, server settings and user management.

The first start after upgrading copies all existing per-user rows to the admin and leaves the old single-user tables untouched, so the previous version can still run against the same database.

## Addresses and Back

Every page has an address behind the `#` (ADR 0020; the table is in issue #480, "Addresses and the page stack"). `src/routes.ts` is the only code that reads or writes one; `src/navigation.ts` keeps the browser's history as the page stack. Switching place with the tab bar or the rail adds a step for Back, and tapping the tab of the place you are in returns to its first page without adding one. A reload shows the same page and keeps what lies behind it. An address that names nothing, a page not built yet, or Activity's Server for someone who is not the administrator shows the place's first page, and the address is replaced by it. After signing in you land on the address you opened. Back returns a list to where it was scrolled. The installed app starts on the Library. The old names keep working: `#downloads` opens Activity's Now (replacing its entry) and `#reader/<ebook id>` opens the reader; closing the reader goes back, so Back afterwards does not reopen it. A reader link to an ebook that has been removed shows the Library in its place.

Now playing (with its reader) has a history entry of its own but no address yet: Back closes it and leaves the page under it where it was, its own close goes back too, and a reload with it open shows the page without it. Playback carries on through all of these. Back that leaves a page closes the dialogs open on it (book details, versions and sources, a series, adding an audiobook) and confirms nothing. The Library's shelf or list, Favorites, status filter and search are remembered when you leave it, so Back returns to the same list; Discover starts at its top, since its results are not kept yet. A list is returned to its position only while you have not scrolled, touched or typed, and not at all when it does not come back as it was. When what lies behind a page is not known (an entry from an older version, an address typed in, history the browser has dropped), the page's back button goes to its parent rather than out of the app or nowhere.

## Listening workflow

1. Browse the included public-domain recordings, search AudioBookBay, import your audio files, or add a magnet link. AudioBookBay search has a release picker with language (English by default), format, size, bitrate, narrator details and pagination. Confirm **Use this release** before anything is queued. **Find another release** on a book keeps the new recording linked to the same work; available recordings can be switched in the book dialog and retain independent progress. Filename order is natural, so chapter 2 precedes chapter 10.
   With Prowlarr connected (Settings → **Prowlarr**: address plus API key, stored encrypted; **Test Prowlarr** checks status and counts enabled torrent indexers), the picker also searches Prowlarr’s audiobook category (3030) and book categories (7000, kept only when the title marks it as audio). Sonder only reads Prowlarr; indexers are managed there. Each source fills in as it answers, and a failing source shows a short note above the others. Releases are merged by info hash, then across sources by normalized title and size within 1%; merged cards list every source. Results sort by title match, then TorBox cache (known hashes only), then seeders. Indexers do not report language, so their releases stay visible under every language filter. Prowlarr download links contain its API key and never reach the browser: the server keeps them for six hours per search and replays them only against the configured Prowlarr address, turning a magnet redirect or `.torrent` file into a magnet. A chosen Prowlarr release then follows the same TorBox check, local queue and validation as any other magnet. Prowlarr results load on the first page only; **Load more releases** pages AudioBookBay.
2. A magnet is checked against TorBox’s cache. A cache hit creates a TorBox torrent with `add_only_if_cached=true` to protect against a cache race. A miss still asks TorBox to take the job without cache-only (`add_only_if_cached=false`). If TorBox cannot take the job, or TorBox is not configured, the magnet uses local Transmission when that path is healthy.
3. Local downloads run independently of the browser. The persistent server queue shows checking, preparing, downloading, paused, ready, and error states. Stable info hashes deduplicate repeated requests. Downloads resume after an application restart. A book joins the library only after Transmission reports completion, every wanted audio file is complete, and local metadata can be read. Preallocated partial files are never considered playable.
4. Listen with 30-second forward/back controls, speed, volume, a sleep timer, and Media Session controls. Headphone/lock-screen next, previous and seek commands all jump 30 seconds, including across audio files with known durations, while preserving paused playback. Choose chapters explicitly from the chapter list. Imported and locally downloaded M4B/MP3 files expose their embedded QuickTime, Nero, or ID3 chapters; the physical file and recording identity remain unchanged when seeking between chapters. Streaming files obtain embedded metadata when saved to the server; multi-file streams expose one chapter per file until then. Progress is keyed by recording and track, saved locally every five seconds and on pause/seek, then reconciled with the server by timestamp.
   Speed runs from 0.5× to 3× in 0.05× steps (slider and −/+ stepper), with 0.75–2× quick picks; pitch is preserved. A speed chosen in the player is remembered per recording, on this device only, in the signed-in user’s local database, so each narrator keeps its own speed and offline playback needs no server. **Use default** in the speed menu removes that recording’s own speed so it follows the default again. Recordings without their own speed use **Settings → Playback → Default speed**, which is saved with the user’s playback settings on the server and so follows the user across devices (unless appearance is kept device-only). Moving the slider only previews the value in Settings; playback uses the new default once it is saved. Saving after **Reset** or after importing a preset without a speed clears the default on the server as well. Until a default is saved, the device-wide speed from earlier builds still applies, and a speed chosen while the player has no book becomes that device-wide speed. At any speed other than 1×, the expanded player shows the time left at that speed for the book or chapter (following the progress-bar setting). Chapter lists show real chapter lengths at any speed; only the current chapter’s time left is shown at the speed the book plays at. The lock-screen position state reports the actual playback rate on every rate change and position update. The speed menu and the sleep-timer menu move to stay on screen when their button is near the edge.
5. **Save to server** keeps a permanent copy on the HDD, including TorBox or LibriVox streams. Up to three files of a book are copied at once, in chapter order (`SONDER_DOWNLOAD_CONCURRENCY`). A file that fails is retried three more times with a fresh TorBox link (waits of 2, 5 and 15 seconds, `SONDER_DOWNLOAD_RETRY_MS`) before the copy stops; failures a retry cannot fix, such as TorBox not being connected, stop it at once. Complete chapters survive pause/retry/restart. An interrupted file is kept as a partial file and continued with a range request; a source that ignores the range, or answers with a range that does not reach the end, sends the file again from the start. Partial files are named after their source, so a re-linked source never continues an older file; cancelling a copy deletes them. Completed media is committed atomically. Keeping a cached recording does not change its recording identity or listening progress.
6. **Save offline / Save on device** keeps a complete copy in the current browser using persistent IndexedDB chunks. Completed chapter metadata is written only after size validation. Keep the tab open while downloading; pause or retry can reuse completed sections after reload. Partial books show completed chapter counts; only fully downloaded books receive the offline badge. This copy is independent of the server copy.

Settings → **Playback** chooses a whole-audiobook or current-chapter progress bar. Chapter mode uses embedded chapters inside M4B files. Whole-audiobook mode spans files when their durations are known; otherwise it explicitly shows the current file. Drag the bar horizontally to seek; moving farther above or below it reduces sensitivity. The drag previews your destination and seeks on release; keyboard arrows skip 30 seconds. Both player bars expand on wider screens.

The expanded player offers **Undo jump** after a seek, chapter selection, Listen from here, Hardcover position adoption, or source change that moves the position; it restores a position inside the recording that is playing, and never switches to another recording. Starting another recording is recorded for the recording that was left, so its Undo jump is there when you return to it. The button keeps its place in the layout while it is unavailable. Undoing a Listen from here with its reader toast takes its history entry back too. Repeated 30-second skips within ten seconds share one undo point. History stays on this device, separately for each recording and user, and holds at most 20 positions for 24 hours. Removing the library entry or resetting the app on this device clears its history; undo saves the restored position through the normal progress sync.

Keyboard shortcuts: `Space` plays or pauses (with no audio loaded it does nothing), `←` and `→` skip 30 seconds, `/` searches, and in the reader `f` returns to the narration (also with the focus in the pages or on a button; not while a dialog or the Playback options sheet is open above the reader, while typing in a field, with Ctrl, Alt or Meta, or without the book's narration in the player). **Keyboard shortcuts** in Now Playing and Settings opens the list.

The compact player’s cover opens the title page and its book icon opens a linked EPUB. The expanded player puts **Title page**, **Read ebook** and **Versions & sources** at the top. A matched book's Hardcover page links to the book's canonical page on hardcover.app (**Open on Hardcover**). If multiple EPUBs are linked, choose an edition once; Sonder remembers it for that work.

**Versions & sources**, also available on title pages and device-download rows, separates recordings from their delivery sources. Choose Automatic, Device copy, Server HDD copy or the original online/TorBox stream. Switching delivery source preserves position and paused playback. Switching recordings keeps a newer checkpoint of the target as it is. When the target has no checkpoint, or an older one than the recording in the player, Versions & sources first asks where to resume: **Resume at <chapter or N%> (hh:mm:ss)**, **Start from beginning**, and, if the target has an older checkpoint of its own, **Resume saved position (hh:mm:ss)**; nothing is switched or transferred before the choice, and the chosen place is saved to the target recording right away. **Start from beginning** replaces the target’s own saved position (the helper line under the buttons names it, for example “replaces your saved position at 00:00:42”); the replaced place stays in that recording’s position history. A recording that is open in the player, playing or paused, counts as listened to now when it is compared with the target’s checkpoint. The position is carried over by chapter (the same chapter index when both recordings have the same number of chapters, otherwise the chapter with the same title, keeping the offset into it and clamped to the target chapter’s length), and otherwise by the share of the whole book (tracks of unknown length are left out of that share). Two recordings with the same number of chapters are matched by index with high confidence even when their chapter splits differ, so check the resume label when the releases were cut differently. Undo jump after switching recordings only restores a place within the recording now playing; it does not switch back to the previous recording. A mapping is marked low confidence, with a warning line, when the total durations differ by more than 10% (such as abridged against unabridged) or only the share of the book was usable. Sentence alignment maps are not used for this yet. Progress is never merged between recordings: each keeps its own position. Automatic prefers a healthy device copy, then server media, then the original stream; explicitly selected sources never silently fall back. The one exception is a Server HDD copy or original stream choice that cannot reach the server (offline, or online with no route): when a complete, un-flagged device copy exists, that playback switches to it at the same position, shows “Device cache” and a short notice, and leaves the saved choice unchanged. A gateway answer (502, 503 or 504, such as the reverse proxy answering while the Sonder process is down) counts as unreachable; other HTTP refusals and decode errors do not trigger it, and an incomplete device copy is never used. A pause or seek made while the app checks the connection is kept. A stream that stalls or waits for 10 s gets the same check, so a connection that goes silent without an error also switches to the device copy at the current position; a stall that clears while the check runs is left alone, and the check is not repeated for it. Once the server is confirmed unreachable it is remembered for 60 s, and the next chapters of that recording play the device copy straight away without trying the stream first. A successful answer from the server, the browser reporting `online`, or choosing a source in Versions & sources clears that memory sooner. The notice appears once per recording, not on every chapter, and not when the player only opens a chapter without starting it. Mark an entire recording or an individual copy faulty with a reason and optional note. Device flags stay on the device; recording/server/original flags persist on the server. Clear a flag when resolved. Removing a downloaded copy preserves the library and progress. Server removal deletes only managed downloads in `MEDIA_ROOT/saved`, preserving original imports and torrent files.

Library entries, saved server media, acquisitions, settings, and progress survive restarts in SQLite and the media drive. Removing a library entry preserves its files and progress, and records that choice so Hardcover sync will not add it back; explicitly adding it again restores the entry. Older clients sending an empty JSON body on library DELETE are supported. Browser favorites are device-local. New library mutations need a server connection; playback progress works offline and syncs later.

The library can also be read by work (`server/library-works.ts`, type `LibraryWork` in `src/types.ts`): `GET /api/library` returns each work in the user's library once, earliest added first, and `GET /api/works/<workId>` returns one work in the same shape, in the library or not. A work lists as recordings its audio editions that are in the user's library and are not placeholders (an audio edition none of whose recordings has a track), the one added first first, so a removed recording is not listed and a work with only a placeholder has none; no response carries a placeholder's id. The chosen recording is the user's own choice, the same on all their devices: `PUT /api/works/<workId>/recording` with `{ recordingId }` stores it (one `user_settings` key per work) and answers the work; it refuses (400) a recording that is not one of the user's recordings of that work, such as another work's, a removed one, a placeholder's or one only another user has. Without a stored choice, or when the stored one is no longer among the user's recordings, it is the one with the user's newest saved place, otherwise the one added first. The work's cover is the chosen recording's; without one, the placeholder's. `addedAt` is the earliest of the user's library rows for the work. A work whose every audio edition is a placeholder the user may not see, and that has no ebook edition (ebook editions are listed to every user by `GET /api/ebooks`), is not found: a user who is not the administrator sees a placeholder only when it is in their library or its book is on their own Hardcover shelves or lists, as in `GET /api/books`. A work also holds (#487): `finished` and `completionOverride`, derived as the series read derives them (`server/work-completion.ts`, shared by both); its ebook editions (the consensus text of an ebook set is not one) with format, size and whether the file is there as `GET /api/ebooks` gives them, the ebook-set member's status and hold reason, and the user's place from their reader checkpoint, plus `chosenEbookId`, the set's shared default when it is one of them; `readingSync`, one entry per pair of a listed recording and a listed ebook edition that has a job, in the summary form of `GET /api/alignments?summary=1` without steps, workers and stage times, with a running rebuild's state under `rebuild`; `series`, its Hardcover book's series with the ones the user saved first; `mediaState` (ADR 0011) with its acquisition, whose status, progress and error only the administrator gets, as `/api/acquisitions`; and `hardcover`, the block of `GET /api/books`. `GET /api/library` sends a per-user `ETag` and answers `304` to a matching `If-None-Match`; the response is rebuilt when a database row changed or a file it checked (a track, a server copy, an ebook) changed on disk, which a read notices within 5 s. `GET /api/books` (one entry per audio edition and recording) is unchanged for older clients.

The device keeps its own copy of the library by work (#528, `src/library-works-store.ts`): one record per work of `GET /api/library` in the `works` table of the user's device database (Dexie version 5; the `books` table stays), replaced together with the stored `ETag` in one transaction. It is read again with `If-None-Match` when the app opens, comes back to the foreground or online, after an action on a work (`sonder:library-changed`, `sonder:hardcover-changed`, the shell's refresh), and every 6 s, the Downloads page's pace, while a stored work has a queued acquisition, a copy to the server that is queued or downloading, or a running reading sync or rebuild; a `304` leaves the store untouched. `useWork(workId)` gives a page its work: the stored record, or `GET /api/works/<workId>` for a work outside the library (which needs a connection; without one its status is "offline"). Either way `overlayDevicePlaces` (`src/library-works-overlay.ts`, pure) lays over it every place saved on this device that is newer than the server's: listening progress per recording and reader checkpoints per ebook edition; a place for a recording or edition the work does not list is left out. No screen uses the hook yet; the parts gallery's "Works on this device" section shows what it returns.

Discover reads the server's works with `GET /api/works` (#573, `serverWorks` in `server/library-works.ts`, type `WorkResult` in `src/types.ts`), answered as `{ works }`, at most 30, each with `workId`, `title`, `author`, `year`, `cover` (as the one-work read's), `inLibrary`, `hasAudiobook` (a recording with a track), `hasEbook` (the consensus text of an ebook set is not counted) and `hardcoverId`. With `q` (2 to 150 characters once trimmed; one character answers 400) it lists the works the user may see, by the one-work read's rule above, whose title or author holds every word of `q`, case and accents ignored (ø, æ, ß and the like as o, ae, ss), the ones in the user's library first, then by title. Without `q`, or with an empty one, it lists the works the user may see that are not in their library, that they have not removed (a hidden entry on any of the work's audio editions) and that have a recording with a track or an ebook edition, the work made last on the server first. Each hit of `GET /api/discover/hardcover` carries `workId`, the work the Book page opens for it (ADR 0022): the work matched to that Hardcover book that the user may see, one in their library first, with `onServer: true`; otherwise `work-hc-<Hardcover id>` with `onServer: false`, so a match the user may not see is not named. Each entry of `GET /api/discover/series` carries `saved`, whether the user saved that series.

## Hardcover library and reading progress

Hardcover organizes the library as well as supplying metadata. Each user connects their own Hardcover account: add your token in Settings, save it, then use **Hardcover library & progress** to test the account, choose a sync mode, and sync now.

- **Off** keeps catalog search and explicit book matching available.
- **Import only** brings your reading shelves, custom lists, and available reading positions into Sonder without writing to Hardcover.
- **Two-way** also publishes listening status and progress. Pending changes are stored in SQLite, coalesced to the latest position, and retried after outages. The server checks pending changes roughly once a minute and refreshes the full remote library every 15 minutes. Sync now runs immediately.

Use a token with `read:catalog`, `read:library`, and `read:me:content`. Two-way shelves/progress need `write:library`. Lists need `read:lists` and `write:lists` to edit membership. These are described in [Hardcover’s scope catalog](https://github.com/hardcoverapp/hardcover-docs/blob/main/capabilities.json). Missing optional list permissions retain the previous list cache and show a warning.

Reading shelves and custom lists appear as filters in the library. Exact, unique title-and-author matches link existing books automatically; other entries become metadata-only books with **Find audio**. A book's details have one **Hardcover** row, shown when this user has connected Hardcover, with the book's shelf, "Not on a shelf" or "Not matched"; it opens the book's Hardcover page, `#book/<workId>/hardcover` (#529; `src/pages/hardcover-page.tsx`, its words and rules in `src/hardcover-page-model.ts`). For a matched book the page has **Shelf** (a picker of the five shelves) and **Use Hardcover position** (Hardcover's place, "62%"; it plays the chosen recording from there without asking, and the place left is kept under Earlier positions; "No position" and off without one, off with sync off), then the last sync, "Saved · waiting to sync" or the sync error; **Lists**, one switch per list, where a change that fails switches back and says why on its row; and **Match**: the **Hardcover edition** picker (Automatic, then each audio edition as narrator · length; saving says "Hardcover edition saved."), **Open on Hardcover**, and **Change match** for the administrator. Without two-way sync the shelf and lists are off, with one line saying so. An unmatched book's page lets the administrator search Hardcover (filled with the title and author), choose a result and **Match** (`POST /api/hardcover/books` with the work); anyone else reads "Not matched on Hardcover. The administrator can match it." Until the Book page exists, the page's back button goes back in history, or to the Library when it was opened by a link. Removing a local library entry does not delete the Hardcover entry or any media files.

Progress uses the cumulative position across physical tracks. It maps by percentage to the selected Hardcover audio edition’s duration, or to pages when Hardcover has no audio edition but does have a page count. Incoming page progress also maps proportionally onto the local recording. This is approximate cross-format progress, not sentence alignment. Unknown chapter durations are never guessed: play or save the audio on your server to read its metadata first.

Local playback stays authoritative while its changes are queued. Later remote changes can move a position backward as well as forward. An unchanged remote checkpoint is not repeatedly imported. A first import preserves a newer local position; two-way mode publishes that position on the first sync. **Use Hardcover position** explicitly selects the remote position and resumes playback. Matching preserves recording IDs, file paths, and each recording’s own progress. Switching account tokens disables sync and clears account-specific queues/list caches before another account can be used.

## Ebook sources

Discover → Ebooks searches **Library Genesis**; its mirror is configurable in Settings. It requires no key; unavailable mirrors are reported instead of appearing to return no matches. Anna’s Archive was removed for now (#8). Older clients that still ask for it get a clear refusal.

To add a file from elsewhere, download the EPUB/PDF and use **Import ebook** on your ebook shelf. Imports stream to `MEDIA_ROOT/ebooks`, have a 150 MB limit, validate file signatures, deduplicate identical files and persist through restarts. Importing through an audiobook’s **Find ebook** dialog links the file to that work.

Ebooks are checksum-verified, saved under `MEDIA_ROOT/ebooks`, and downloadable from the ebook shelf. “Find ebook” on an audiobook links the chosen edition to the same work. Ebook editions are independent of audiobook editions and recordings. EPUBs open directly in the built-in reader; PDFs remain available to download for an external reader. See the reading-sync workflow below.

A book with only an ebook is in the library through its placeholder (#555, decided in #467; `ensurePlaceholder` in `server/placeholder-edition.ts`): an audio edition "Audio not added" with one recording and no track, `hc-<book id>` for a work matched on Hardcover and `placeholder-<workId>` otherwise, never two for one work. Importing an EPUB or PDF (`POST /api/ebooks/import`, with or without a book chosen) and getting one from a search result (`POST /api/ebooks`) put its work in the library of the user who did it by the rule of **Add to library** (`PUT /api/works/<workId>/library`), when it is not there yet; that `PUT` of a work with no audio edition makes the placeholder and adds its row. Real audio arriving for a work (a finished download or an upload, `claimWorkAudio` in `server/work-library.ts`) gives every user who has its placeholder in their library the new recording's row with the same status and removes the placeholder's row, unless they hid that recording; a work matched on Hardcover then takes each user's Hardcover shelf status and remembered position as before. Once, at the first server start with this change (marker `shelfEbooksJoined` in the administrator's settings), every work with an ebook outside the administrator's library joins it through its placeholder unless he hid that placeholder; a recording he removed stays removed.

Save account defaults or select **Use these settings only on this device**. JSON import/export accepts validated settings; browser chrome and offline reload use the cached theme.

Linked EPUBs fill **Now Playing**: with an ebook shown, Now Playing is a full-screen reader with one player bar (Chapters, **Back to narration**, back and forward 30 seconds, play/pause, sleep timer and speed); standalone EPUBs open from Discover → Ebooks in the same reader. The reader shows the book's own text and nothing else, as pages or as one scrolling column (**Reading mode** in **Aa**); an older saved choice of the removed Lyrics or Word view also opens the book's text. The player’s ebook icon opens the saved position without starting playback. In pages mode, tap the left or right edge or swipe to turn pages; tap the centre to show or hide the top bar and the position slider, and swipe down from the top to close. Long-press a sentence to play the narration from there (**Listen from here**); a short notice offers **Undo**. The top bar holds Close, the bookmark button (it bookmarks the narrated sentence while following, otherwise the first sentence on the page, and removes that bookmark when pressed again), Search, **Aa** (reader appearance) and **More**. **More** holds **Listen from here**, **Read from audio**, saved bookmarks, reading sync and offline saving, plus Title page, Versions & sources, the ebook edition and Downloads in Now Playing. With this book’s narration loaded, the bar shows the narration: its chapter and percentage of the book, and a slider with elapsed and total time that follows the book/chapter progress setting. Scrubbing it seeks the audio and the page returns to following the narration. Without narration, the slider scrubs the ebook instead and the page moves when it is released. **Chapters** opens the ebook contents with the narrated chapter marked; choosing one moves the page only. **Back to narration** sits in the player bar between Chapters and Back 30 seconds (icon only; same place on phones and on desktop). It stays in that slot so the transport does not move: disabled while following or when there is no narrated sentence, and enabled when the page is away from the narration. Desktop readers have a contents sidebar that can be hidden, page arrows, a footer player and keyboard navigation. The reader serif is Literata, bundled for offline use.

Paging or scrolling by hand pauses following; **Back to narration** in the player bar resumes it. Without a map, the text remains readable and **Reading sync** in **More** prepares one. Sentence timings are estimated. Reading checkpoints use CFIs and sentence locators rather than display page numbers. ## Local ebook/audio synchronization

1. Import a matching EPUB through an audiobook’s **Find ebook** dialog, or explicitly link it to the desired book in the reader’s **Reading sync** panel.
2. Choose the exact audiobook release. A clear language mismatch is refused. Match ebook sections to tracks/embedded chapters; edit their start and length to exclude introductions or split a long physical file. Each processing section is limited to two hours.
   With `ALIGNMENT_BOOK_JOBS=1` there is no matching step: the whole-book job gets every sentence of the ebook and every file of the release and locates the text itself, so a pairing would change nothing in its map (#405). `GET /api/alignments/options` says so with `bookJobs: true`; the card then hides the matcher, its count, the review line, **Rebuild without chapter matching** and the hint to choose a release with chapter markers, and **Prepare reading sync** sends only the ebook and the recording. The server still stores its automatic pairings on the job (used if the setting is turned off again); when none match on a chaptered release, the job is planned as an anchored one instead of being refused. An older client that still sends pairings or `mode` keeps working.
3. Select **Prepare reading sync**. Audio is first saved to the server HDD when needed. The pool worker checks acoustic evidence before accepting supplied text. Jobs persist in SQLite and pause, cancel or resume at section boundaries. Completed section outputs are cached on the HDD.
   A release that is one audio file without chapter markers (or several files with none that match) is prepared without a chapter matcher. Sonder takes 30-second speech samples about every ten minutes, more densely near the start and end. CTC jobs locate these samples from the same cached acoustic data used for alignment, keeping alternative repeated passages until the forward-moving anchor chain is selected. Where the gap between samples disagrees with the text length, it adds samples between them. Known-text alignment then runs on bounded windows between samples, with overlapping edges, one window at a time. Intro and closing credits, ebook text with no narration, narration not in the ebook, and unaligned windows are listed in the sync status and left unsynced. If too few samples match, the text is left unsynced. Sampling and windows resume after a pause. Selecting chapters manually in the matcher uses the chapter workflow instead.
4. **Read from audio** moves the ebook to the current audiobook position; where the map has no interval there, an admin's request locates a 30-second excerpt with one CTC `/anchor` request on a pool host (WSL first, then lisa), which needs the pool enabled (staging, scoring and cleanup together have 180 seconds; past that the request ends with an error and frees the host); **Listen from here** seeks the selected release to the current ebook passage. Both are in the reader's **More** sheet, and a long-press on a sentence also listens from there. **Back to narration** resumes automatic following. It works the same from every place that asks for it (the player-bar button, `F`, Read from audio, Listen from here and its Undo, the audio slider when it is released and the "Follow the narration" switch): a place chosen by hand that is still waiting for its save is dropped when there is a narrated sentence to follow on a map the server has confirmed for the current audio, so it cannot overwrite the listening place, and kept and saved when there is none, until following starts to work (a map shown from this device's cache counts once the server confirms it). The audio slider decides for the place the narration reached, after another file has loaded. A Read from audio answer that arrives after the reader moved on, or after another map replaced the one it was asked with, is ignored. Optional follow-along highlights narration without writing new reading events. In pages mode a narrated sentence that crosses a page is highlighted on both pages, and the page turns inside it when the narration reaches the first word on the next page (estimated by spreading the sentence's time over its words); a jump in the audio shows the page of the word being narrated, a pause keeps the page, and a page turned by hand turns nothing until **Back to narration**. Scroll mode does not turn.
5. Timings are **estimated**, with unmapped passages left unsynced. The sync panel shows the engine, outcome and accumulated worker stage timings, and offers manual sentence start/end corrections while that recording is selected. A replaced EPUB or changed audio file invalidates its map.

The production server runs no alignment worker (#279): every alignment, probe and passage-locating request goes to a pool worker (WSL, then lisa), which is protected by a private token (`ALIGNMENT_WORKER_TOKEN`, the same value in `.env` and in each worker's `worker.env`). Audio is staged over SSH into the worker's own `MEDIA_ROOT/alignment/pool-jobs`; a probe's copy is removed when the probe ends, a job's stays until the administrator removes it: `GET /api/alignments/pool/staging` (admin only) lists every staged folder per host with its size and whether a run would remove it, and `POST /api/alignments/pool/staging/remove` (admin only, optional `{"host": "<id>"}`) removes the folders of finished or deleted jobs, never a folder the server has no record of, and nothing on any host unless every configured host was listed and no host's media root or pool-jobs folder (real paths) lies inside another host's pool-jobs folder (ADR 0013, #421). A probe folder left by an interrupted probe stays listed as unknown; the administrator removes it by hand (`docs/CTC_WORKER_POOL.md`). Models, temporary audio and analysis stay there. The pinned Wav2Vec2 Base CTC checkpoint is downloaded explicitly with `download_model.py` by `scripts/install-ctc-workers.sh`. Ordinary processing uses local weights and never downloads them. No paid API is called and audio leaves the server only for the owner's pool hosts. Reading again uses the cached map, with no inference charge. See [the measured local benchmark and limits](docs/ALIGNMENT_BENCHMARK.md).

Chapter-paired and anchored alignment use the CTC engine (Wav2Vec2 Base, English only). CTC runs only on the remote pool: WSL's GPU first, then lisa's CPU. The pool is disabled unless `ALIGNMENT_POOL_ENABLED=1`; when disabled, CTC jobs fail with instructions to enable it and can be resumed later. If remote dispatch fails, the Reading sync card lists the failed step and reason for each host; **Resume** starts a new attempt. `ALIGNMENT_BOOK_JOBS=1` (off by default) runs every full alignment as one whole-book job on the worker under one lease instead of the window requests below, and rebuilds every map of the window engine under the whole-book engine (`docs/CTC_WORKER_POOL.md`, "The server's whole-book runner"); a pause or cancel cancels the worker's job, so a resumed job starts over there. A whole-book job waits for a busy GPU host rather than taking a CPU host, which it takes only when no GPU host can be used (down, unhealthy, without whole-book jobs, or it failed this job); the Reading sync card shows such a job's worker stage and count (for example "Decoding audio: 24 of 43 files") and its pause button reads **Pause**. Activity › Server lists each pool host with its status, device and current work (`GET /api/activity`; `GET /api/alignments/pool`, admin only, still answers reachability, busy state and last error), and `LOG_LEVEL=debug` logs non-GET `/api/alignments` requests with status and duration. Alignment, ebook-candidate probing and passage locating all run on the pool; reading sync is available, and newly linked pairs are queued, only when the pool is enabled and `ALIGNMENT_WORKER_TOKEN` is set. A leftover `ALIGNMENT_WORKER_URL` is ignored. Whisper and aeneas were retired in #279, with the aeneas rollback switch; a job an older engine made that becomes active again (for instance on **Resume**) is planned under CTC before it runs. Each CTC worker needs the pinned checkpoint in its own media root (`download_model.py` fetches and verifies it); no model is downloaded during processing. Set `ALIGNMENT_CTC_DEVICE=cuda` on a GPU worker (the worker defaults to `cpu`). The model is loaded once per worker process from `alignment/models/ctc` and its checksum is verified. Non-English books remain unsynced with an explicit "language not supported" outcome. Passage checks compare constrained timing with unconstrained CTC hypotheses, local coverage, neighboring candidates, blank structure and timing. Failed checks leave the affected sentences unsynced. Oversized paths are split into bounded scopes; a sentence that cannot fit is left unsynced. Existing aeneas maps stay readable until their automatic engine-generation rebuild finishes. A manual prepare (`POST /api/alignments`, Prepare again) keeps the map in use the same way when that map has intervals and was made from the ebook and audio files as they are now (#538): the listing and `/map` serve it with the new job under `rebuild` (its status, `bookJob`, `generation`, `poolErrors`, `coverage`, `elapsedSeconds` and `createdAt`; someone who is not the administrator gets `bookJob` without its host and no `poolErrors`), and a new map that maps none of the text, more than 2 points less, or ends "language not supported" is stored as rejected while the map in use stays. Pause, cancel and a failure keep it too; it is admitted as new work, ahead of automatic rebuilds. Over a stopped, cancelled, no-text or not-available job, a map of changed files, or on a first prepare, nothing is kept. See [CTC pool setup and qualification](docs/CTC_WORKER_POOL.md).

Ebook-set candidates are checked against the audio with the same CTC engine (ADR 0005 amendment). The 30-second samples of the ADR 0004 outlier check are scored one `/anchor` request each against the recording's cached emissions, on a leased pool host (WSL first, lisa as the fallback; never the production worker), so the candidates of one run share the recording's acoustic pass (re-evaluating several held candidates also shares one staging of the audio; a run that downloads candidates frees the host between them). The outlier rule is unchanged. A candidate with no audio on the server yet stays held (`awaiting_audio`); one held because no pool host was free, the pool is off, alignment is paused, or the probe failed on both hosts has `awaiting_worker`; an EPUB that is not English has `language_not_supported`.

An EPUB added to a work (`POST /api/ebooks` with a `workId`, or an upload with `?workId=`) is saved, linked and recorded as a `pending` member, and the request returns at once; its response carries `ebookSet: { status }` next to the fields it always had. The check runs in the background in the **Ebook set checks** loop (`server/ebook-set-evaluation.ts`, every 30 s and at start, so a member left pending by a restart is picked up) and ends the member accepted, rejected or held. The loop also re-examines a member held `awaiting_worker` once the pool and worker token are configured and the hold is 10 minutes old. An evaluation that throws (a broken EPUB) holds the member as `evaluation_failed` with the message; such a member, and a sibling whose EPUB cannot be parsed, is not used as evidence for another member. Both pause switches (the loop's and alignment's) are read before each member's check: a check that runs finishes, the others stay pending. A result is written only if the member is still the one the check started for and its ebook is still linked to that work; otherwise it is dropped, and a member whose ebook moved to another work is not checked. Linking an ebook to another work (`POST /api/reader/:id/link`, or saving or uploading it again for another work) removes its pending member in the work it leaves in the same transaction, and that work's set is synced as after any member removal; a member with another status stays, and the work it joins gets what it got before (a link adds no member there). Reevaluate skips a member whose ebook is linked to another work and removes it if it is pending. Nothing automatic queues an alignment for an ebook whose member is pending: the upload, link and audio-import auto-queue, the backfill and the engine rebuild scan pass it by (the scan rebuilds such an older map at its next run, at start). Prepare in Reading sync (`POST /api/alignments`) is not gated, as before. Once a check ends (accepted, rejected or held) the alignment is queued right after its result is written, before the next member's check starts, as the upload queued it whatever the check said; the auto-queue's own conditions (pool and worker token, same work, language, audio) apply as before. Reevaluate does the same for a member it moves from pending to a result; a held member it checks again queues nothing. A failure to queue is logged and the batch goes on. A server stop between the result and the queueing leaves it unqueued; the backfill picks the ebook up. Activity shows only the member being checked as running, with its stuck time counted from the start of the check; members waiting for their turn are queued. The series view counts pending members and shows "Checking". `POST /api/works/:id/ebook-set/reevaluate` evaluates pending and held members and waits for the results; Retry on the Activity item evaluates one member again in the background. An EPUB that is already an accepted or rejected member keeps its result when it is added again. The source picker shows a pending member as "Checking" and reads the set again every 15 s until no member is pending.

The alignment processor aligns up to two books at once (`ALIGNMENT_ADMITTED_BOOKS` in `server/alignment-scheduler.ts`); with one resident model per device that is one book on WSL and one on lisa. The next queued job starts as soon as a running one finishes. Two jobs for the same recording never run at the same time. Each job is claimed in the database by the running server and its generation; a cancelled or rebuilt job's late results are discarded, and after a restart an interrupted job resumes once its old claim is 30 seconds stale (immediately after a clean shutdown), ahead of newer queued work. The worker encodes acoustic chunks in microbatches of 4 (`ALIGNMENT_CTC_ENCODE_BATCH` overrides it) and halves the microbatch on an out-of-memory error; later requests of that job keep the halved size. The job's `runConfig` records the books admitted, resident models per device, microbatch configured and in use, the number of halvings, path-decode workers (2) and audio extraction workers.

CTC stores completed float32 acoustic chunks under `alignment/ctc-acoustic-v1`, shared by ebook editions of the same recording and engine. Audio bytes are fingerprinted, so changed audio is encoded again; interrupted work can reuse completed chunks. The default cache budget is 5 GiB, evicting least recently used recordings as needed. Set `ALIGNMENT_CTC_CACHE_BYTES` to a nonnegative byte count (up to 1 TiB), or `0` to disable the cache. A recording larger than the budget is cached only while space permits. The job's `acousticEncoding` and `acousticCacheRead` stage timings show encoding and cache reads separately.

To qualify this route on WSL or lisa, run `python3 worker/gate_ctc.py --help` for the labelled-sample gate arguments. Supply the trial's `reference.json`, `gold.json` and audio under the worker's media root, an output under its alignment directory, and the worker token through `ALIGNMENT_WORKER_TOKEN`. The gate scores `/align`, checks that CTC discovery locates the first and last labelled sentences, and checks that an unrelated chapter is unsynced. Missing utterances count in the denominator. It is intentionally outside `npm test` and requires the real model.

The worker stops a request that runs too long, so one runaway section cannot keep a core busy. Each `/align` request (audio extraction and CTC alignment) gets `min(ceiling, base + per_second × audio seconds)`: by default 120 s plus 0.15 s per second of audio, at most 1200 s (390 s for a 30-minute section, 1200 s for the 2-hour maximum). `/anchor` samples use the same formula capped at 150 s. At the limit the worker stops timed-out work, removes the temporary files, frees the job slot and answers HTTP 504. If the process does not die (for example a read blocked on a failing disk), the worker still answers 504 but keeps the slot busy and reports `stuck` until the process is gone, so a second job never runs next to a runaway one; the reading-sync job then shows "The alignment worker timed out on this section. Retry later, or choose a release with chapters." and keeps the sections it had finished, so **Resume** retries only that section. Override the limits with `ALIGNMENT_TIMEOUT_BASE_SECONDS` (0–1500), `ALIGNMENT_TIMEOUT_PER_AUDIO_SECOND` (0–1) and `ALIGNMENT_TIMEOUT_MAX_SECONDS` (1–1700) in the pool worker's `worker.env`; a value outside its range or not a number is ignored with a warning in the worker log. The ceiling stays under the server's own 30-minute wait so the worker's error is the one shown. A chapter-mode section longer than the limit (more than about 2 hours at the defaults) now fails with that message instead of running without bound; splitting long sections is not implemented. `GET /health` on the worker reports `busy`, `stuck`, `busySeconds` (how long the current job has held the worker, or `null`) and `lastTimeout` (ISO time of the last timeout, or `null`). Python tests for this live in `tests/worker/` (`python3 -B -m unittest discover -s tests/worker`).

CTC uses the same request limit. If resident inference outlives it, the worker answers 504 and holds the slot as `stuck` until that inference exits; its late result is discarded. Restart the worker if a GPU operation never returns.

In Hardcover two-way mode, deliberate EPUB reading publishes overall page progress (or an audio fraction if no pages are available), including books without local audio. This has its own durable retry queue. Precise CFIs and timings remain in Sonder, and reader updates do not overwrite a recording’s listening checkpoint. Incoming coarse Hardcover progress does not replace a precise EPUB checkpoint.

## Activity (administrator)

Activity is one of the places, in the tab bar and the rail where Downloads was, for everyone, with the attention dot (#516; the dot still reads the server's count, for the administrator). It has a Page header and a Segmented control: Now (`#activity`) shows what the Downloads page showed (the server's downloads for the administrator, this device's saves for everyone) and, for the administrator, the work items of every background process in the groups Needs attention, Running, Waiting and Finished in the last 24 hours, until Now's own ticket: the download queue, copies to the server, series acquisition, Hardcover sync (one row per user and queue), alignment jobs including the ebook-set consensus check, ebook-set member checks (pending, waiting for a worker, failed, or finished in the last day) and the latest daily database backup, a failed one with its reason.

Server (`#activity/server`, administrator only, #519) lists the queues, the workers and the torrent client in three groups: **Reading sync** (Reading sync queue, Prepare for all books, then Workers with one row per worker), **Downloads** (Download queue, Torrent client, Copies to server, Series search) and **Other** (Ebook checks, Hardcover sync, Database backups, Imports). Each queue has its name with the pause sentence as its tooltip, a line in its own words ("1 preparing · 1 waiting", "1 downloading", "1 checking", "2 changes waiting · admin") or "Nothing running", and a switch; a queue switched off reads "Paused" first, one an environment setting holds reads "Paused by a server setting" and its switch cannot be used, and a switch the server refuses shows why on its row. The Database backups line is the schedule: the last run with its result and size, the reason when its retention failed, and the next run (times in UTC), or "Next run when resumed" while it is off. Prepare for all books queues reading sync for every eligible book (`POST /api/alignments/backfill`, as Settings › Reading sync did) and shows how many are ready; its result is a message. A worker's row reads "Online · GPU · Encoding: <title>", "Offline since 14:02" (the time the server first saw it offline since its own start), or "Not in use · CPU" when switched off (muted, no mark; switched off and unreachable reads only "Not in use"), and opens `#activity/server/<worker>`: until the worker's page (#520) exists that address shows Server with the worker's restart and switch beside the list (under it on a phone). The torrent client reads "Running", or its health message when it cannot download. A row whose process lights the dot (a torrent client or a worker that is down) carries the attention mark. Imports read "Not tracked yet". Without a connection Server shows only a card. Settings no longer has a Reading sync section, and the Downloads list no longer shows the torrent warning: both live on Server. `GET /api/activity` (administrator only) builds the rows from the existing tables; nothing is stored for it.

- Each item of `GET /api/activity` names its book and the facts of its status line (#514), so the page can group by book and word the line with the status lines of `src/status-lines.ts` without a second vocabulary on the server. `workId`, `bookId` (the audio edition of the work's chosen recording; null when the work has none, and never a placeholder's) and `cover` follow the library by work for the administrator who asks (`server/work-cover.ts`: the chosen recording's cover, otherwise the placeholder's). A download with no work yet has no work and keeps its own cover; a Hardcover queue and a backup have none of the three. `facts` is one shape per kind (`ActivityFacts` in `src/types.ts`): the feature's own status word and, where the kind has them, a download's backend, a reading sync's outcome, coverage, worker stage and file counts, an ebook check's hold reason, a series search's kind. `attention` is true for an item that failed in the last 7 days, is stuck or is blocked, decided in `buildActivity`; the response's `attention` count is these items plus the down processes, as before.
- A running item is **stuck** when nothing about it changed for longer than normal for its kind (copy 5 min, series acquisition 10, download 15, alignment 20, database backup 30); a Hardcover change is stuck when it has a permanent error or has waited 30 min. The settings key `activityStuckMultiplier` (0.25 to 10) scales all of them. Downloads rewrite their row on every poll, so the server remembers when their progress last changed; it starts counting when the server starts.
- An item that cannot move because its process is down (a local download with the torrent client down, an alignment on a worker host that is unreachable) says "Blocked by <process>".
- Finished items stay for 24 hours. Failed items stay listed; one older than 7 days no longer lights the indicator on Activity.
- **Pause** (download queue, copies to the server, series acquisition, Hardcover sync, alignment processor, ebook checks, database backups): starts no new work and lets running work finish. The switch is stored in the settings table (`activityPaused:<process>`) and survives a restart. `SONDER_SKIP_SERIES_ACQUISITION=1` still disables series acquisition for good; Server shows "Paused by a server setting" and the server refuses the switch. Each switch states what it does and does not stop: pausing the download queue stops Sonder checking and importing downloads but the torrents keep running in the torrent client; pausing Hardcover sync keeps saving your changes and "sync now" still works. Every pause and every Retry or Discard is logged.
- **Hardcover queues** are listed per user for three queues: shelf changes, listening progress and reading progress. A failed change that can never succeed (for example "book not found") offers **Discard** (two clicks; only the failed rows of that queue go, never other rows or another user's queue); any other waiting change offers **Retry now**, which runs that user's sync. Failed rows are re-sent on every sync anyway.
- **Alignment worker hosts** (one row per configured pool host, ADR 0013) show online or offline, the device, the worker's code version (`revision` from its `/health`, "unknown" when it reports none) and its current job: window requests running, whole-book jobs (and whether one is encoding), a resume of retained jobs and stuck requests, from the worker's `/health`, plus the titles of the alignment jobs Sonder runs there.
- **Restart** (on a host's row, with a confirmation) restarts the worker's systemd user service through one fixed command sent over the pool's SSH connection (`systemctl --user restart sonder-ctc-worker.service`, ADR 0002; `server/alignment-host-control.ts`); nothing from the request is sent. It is refused while the host runs anything (window requests, whole-book jobs, an encode, a resume, or a job Sonder holds there) or while its `/health` cannot be read or understood (a field missing or of the wrong type); the row then offers **Restart anyway**. From that check until the restart has finished, Sonder gives the host no new work. After the command the server waits up to 120 s for `/health` to answer ready and the row shows the result (restarted and ready again, or why not). A second restart of the same host while one runs is refused. `POST /api/activity/services/alignment-host:<id>/restart` with `{ force }`.
- **Disable** (per host) takes a host out of use: it gets no new alignment jobs, probes or whole-book jobs, and its row on Server says "Not in use" (an offline host that is not in use does not light the attention dot). Work already running there finishes, also a whole-book job the server picks up again after its own restart; a whole-book job the worker there no longer has is not started on it again but moves to another host or waits. With the GPU host disabled, whole-book jobs go to the CPU host; with every host disabled, new work waits in the queue. The switch is stored in the settings table (`activityHostDisabled:<host id>`) and survives a restart. `POST /api/activity/services/alignment-host:<id>/disable` with `{ disabled }`. Every restart (including a refusal) and every switch change is logged.

## Storage and security

- `data/sonder.db`: canonical library, recordings, tracks, download jobs, encrypted integration settings, and independent ebook editions.
- `data/.encryption-key`: generated AES-256-GCM key. Back it up with the database; losing it makes saved integration credentials unreadable.
- `MEDIA_ROOT/complete` and `incomplete`: local torrents, both mounted into Transmission as `/downloads`.
- `MEDIA_ROOT/alignment`: pinned speech models, temporary decoded audio, section results and alignment maps.
- `MEDIA_ROOT/imports`, `saved`, `ebooks`, and `demo`: imported audio, permanent stream copies, ebook files, and the included Alice sample.
- Session tokens are hashed in SQLite and use HTTP-only, SameSite=Strict cookies. Set `APP_PASSWORD` for sign-in. Cross-origin API writes are rejected.
- TorBox API keys and permanent authenticated link parameters never reach the browser. Signed links are resolved server-side. Media proxies accept only stored source records, not arbitrary URLs.
- Downloaded browser files are local device storage and are not encrypted. Signing out gates their access through the app and clears the bounded streaming cache.
- Content-Security-Policy (#76): the server sends an app-level policy on the HTML shell and `sw.js` (not on `/api` JSON). It allows only `'self'` scripts (no `unsafe-inline`, no `unsafe-eval`), blocks plugins, framing and `<base>` outside the origin, and limits `connect-src` to the app's own origin. Images also allow `https:` because Hardcover and torrent-site covers are shown from their own hosts. A `srcdoc` reader frame inherits this policy and a `blob:` document inherits its creator's, so it backs up the reader's own section CSP against inline and cross-origin scripts only: it still allows a `<script src>` from the app's own origin, so the section CSP and the sanitiser remain what keep EPUB content inert. `CSP_MODE` picks the mode: `report-only` (the default when unset or misspelt, so nothing can break the app) sends `Content-Security-Policy-Report-Only`; `enforce` sends `Content-Security-Policy`; `off` sends neither. Browsers report violations to `POST /api/csp-report` (`application/csp-report` or `application/reports+json`; no sign-in needed). It stores at most 20 reports per minute per client address (and 200 in all), so one client cannot use up the quota and hide real reports; it refuses bodies over 8 KiB and writes one log line each with the directive, blocked URI and source file only (no query strings or inline data). Check the server log for `csp violation:` lines after a few days of use in report-only mode, then set `CSP_MODE=enforce` in `.env` and restart. Caddy is not involved. `npm run dev` serves the page from Vite, which sends no policy, so check violations in the Docker build. The service worker's offline shell keeps the headers it was cached with: after changing `CSP_MODE`, ship a new build (it bumps the cache) before testing offline.

App shell and bundled fonts are precached after a production build. If the installed app behaves unexpectedly, Settings → **This device → Reset app on this device** checks the connection, clears Sonder’s app and streaming caches, unregisters its service worker, and reloads. Device downloads, local settings, and unsynced progress are kept. Device downloads use bounded 4 MiB requests, retry interrupted sections and persist verified chunks in IndexedDB so they can resume after reload. Only complete files become offline downloads; previous OPFS and Blob downloads remain readable. A source without range support can still download, but must restart its transfer after an interruption. The audio proxy limits connection setup rather than imposing a two-minute deadline on an entire audiobook. Open the expanded player for **Save on device**, **Pause download**, **Resume download**, download management and book editions.

A separate streaming cache retains at most 24 exact request segments, each at most 4 MiB, and is never labeled as an explicit download. Full local files support suffix, bounded, and open byte ranges plus HEAD and 416 responses. Service workers also serve byte ranges from complete browser downloads.

The compact and expanded player show **TorBox**, **Host server**, **Device cache**, or **Online stream** for other upstream services. This describes the serving path: a verified HDD copy of a TorBox track reports Host server, and offline files or cached streaming sections report Device cache.

Browser storage can be evicted. Sonder requests persistent storage and reports whether it was granted. iOS background playback/download limits depend on browser and OS; locked-screen behavior still needs physical iOS/Android verification. Signed TorBox URLs and streaming fragments do not constitute an offline book.

## Verify

```bash
npm test
npm run build
npm run test:browser
```

The build rejects new empty server catch blocks and catches that discard their error. Pre-existing catches are frozen in `scripts/server-catches-baseline.json`; changing one requires handling its error.

Browser tests use a temporary isolated database and media directory. They verify mobile navigation, real audio playback, progress after reload, file import, complete offline download, service-worker range responses, and offline relaunch. Set `PLAYWRIGHT_CHROMIUM_EXECUTABLE` when using an existing Chromium installation. Unit/integration tests cover media ranges, authentication, secret storage, conflict reconciliation, source parsing, cache-hit routing, and local torrent completion. Live paid integrations require your own credentials; upstream mirrors can be unavailable or require browser verification.

`SONDER_VERIFY_PRODUCTION=1 node --import tsx scripts/verify-playback-workflow.mjs [recording-id]` checks the deployed UI with real audio, embedded chapter seeking, precision drags, mobile/desktop widths, available original/server sources, reader shortcuts and canonical Hardcover links. Its fresh browser uses device-only preferences and intercepts its own audio/reader checkpoint writes, preserving the listener’s canonical progress. Results and screenshots are written under `artifacts/`. Fault flags and copy removal are exercised against isolated media in the browser/API tests. `SONDER_VERIFY_PRODUCTION=1 node scripts/verify-integrated-reader.mjs [recording-id]` verifies inline reading, automatic passage highlighting, the More sheet, long-press Listen from here with Undo, that the reader offers no view switch, and mobile/desktop layouts against an existing prepared map. It also isolates preferences and intercepts progress writes in its QA browser; results are saved to `artifacts/integrated-reader-verification.json`. Both checks start playback at the owner's saved position and may not move it, so each picks its own recording (`scripts/live-check-recording.mjs`, `scripts/live-check-playback.mjs`); a recording id on the command line is only preferred, and is used when it qualifies. A recording qualifies when it is in the library and its saved position (the first file at 0 without progress) is more than 300 s before the end of the book and more than 60 s before the end of its file. The reader check tries each (recording, map) pair: a finished, non-projected map with intervals for an available EPUB of the work, one pair per map. A pair qualifies when the map can carry the check's own sequence, computed by `readerSequence` from the map and the saved position, the same function the check then seeks with: on the file of the saved position, each sampled passage longer than 4 s is the one highlighted at its seek target, and the check plays from a highlighted passage that another follows within 10 s, more than 60 s before the end of that file. The playback check needs the slider's chapter timeline at the saved position (`playbackTimeline` in `src/chapters.ts`, where an introduction or a gap between chapters is its own timeline) to last at least 120 s and to end more than 60 s after the saved position. Among qualifying candidates the reader check takes a ready map before a partial one, then the most recently updated; the playback check takes the most recently listened. "No suitable recording" comes only from answers that say so: a listing read successfully that holds no qualifying candidate, or a map that answers 404 or 410 (stale), which excludes that map only. Any other failed request before the page opens (another status, a timeout, a body that is not JSON or has another shape) fails the check and names the request. When none qualifies the check prints `no suitable recording: <reason>`, opens no page and exits 3, which `scripts/deploy.sh` reports as skipped. A recording that was selected and then fails the check stays a failure: the check does not fall through to another recording. Without `SONDER_VERIFY_PRODUCTION=1` the live scripts accept only a local test server (loopback on a port other than 3001); they refuse the production site and its loopback port 3001, and any other URL (see `docs/LOCAL_CHECKS.md`, Live verification). `SONDER_VERIFY_PRODUCTION=1 node scripts/verify-multi-user.mjs` signs in as the admin with the password-only request older clients send, creates a temporary user, checks through the real sign-in screen and API that the user sees the shared catalogue with an empty library, gets 403 on admin-only routes, can stream, and cannot write under another user id, confirms the admin's library, progress, appearance and Hardcover state are unchanged, and always removes the temporary user (results in `artifacts/multi-user-verification.json`).

Demo recordings come from LibriVox/Internet Archive; the first Alice chapter is bundled so the initial player works immediately. Other chapters stream through the server. See `server/catalog.json` and [third-party notices](THIRD_PARTY_NOTICES.md). The covers and mark are original SVG illustrations.
