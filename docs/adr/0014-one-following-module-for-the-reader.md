# One following module for the reader

Whether the reader is **following** the narration or **paged away** is decided by one module with no React and no epub.js in it. The reader components send it events (the narration reached a sentence, the view relocated, the reader made a gesture, opened Contents, turned a page, stepped a word, resized, a layout started or ended, back to narration) and render what it answers: following or not, and whether a jump to the narrated sentence should run and under which epoch. The epochs, the time windows and the rules for which input wins live there and nowhere else.

**Back to narration is one operation, with one rule.** Every way of asking for it (the player-bar button, the `F` key, Read from audio, Listen from here and its Undo, the audio scrubber, a seek in Lyrics mode, switching on "Follow the narration") calls `backToNarration()` in the module. It drops a waiting manual position only when there is a narration to follow: a map for the open ebook that matches the recording in the player, with a narrated sentence at the player's position (also in a gap after it, #502), and that the server has confirmed for the current audio in this reader. A map restored from the cache is shown and followed before the map endpoint answers, but the audio may have changed in place, so until that answer it is no reason to drop a save; the map lifecycle reports the confirmation as a fact with each map it hands over. It then drops every pending save of a place the reader chose by hand, and the module owns all of them (the page debounce, Word mode's reading checkpoints by hand and while the words advance at a set speed, a Lyrics turn, a search result, the ebook scrubber), starts following, forgets the last followed sentence, resets the retry count and clears a follow error that is shown. A Word mode checkpoint of the listening place (a step that moved the narration) is not a manual position and is kept. Without a narration to follow, a waiting manual position is left alone and still gets saved; the question is asked again when following starts to work (the map arrives or is confirmed, or the audio reaches a mapped sentence), and what is still waiting then is dropped. When the server refuses the map, nothing was dropped. Paging away ends that wait. A relocation reported late by a navigation (or gesture) from before the return is not a manual move, unless the reader made a gesture after the return: it does not page away again. With a narration to follow it arms no save; without one, nothing replaces its place, so that place is saved.

An entry point that moves the narration itself decides for the place it moves to: Listen from here and a Lyrics seek move it to a mapped sentence; Undo decides for the place it goes back to. The audio scrubber asks for the operation when the seek is committed (the pointer released, or a key that moved the thumb), not when a drag starts, and runs it once the player reports the place the seek went to: on another track the player loads that track first, and a decision made meanwhile would be for the track left. Until then nothing changes and every waiting save is kept; a choice of the reader meanwhile (a gesture, a navigation, a Word step, paging away) or another return cancels it. If the seek ends without getting there, the operation runs for where the player is. Read from audio before the map's first sentence (where there is no narrated sentence) or without a map keeps what is waiting while speech recovery runs; its answer counts only if nothing changed since the request (no other return, no paging away, no change of recording, and no other map shown: a rebuilt or corrected map of the same recording replaces the one the request was made with, while the server confirming the same map does not), and then the recovered passage is the narration to follow. A stale answer moves nothing and drops nothing.

This rule replaces the first version of this decision, which dropped the waiting position unconditionally. Two reviewed attempts showed why: with no narration to follow that loses the reader's only saved place, and a pending save can wait in several independent places, so the operation needs one owner for all of them. On 2026-11-14 the entry points were eight hand-written copies that differed in which steps they ran; #417 replaced them with the one operation and tests each of its nine sequences.

The module also decides which sentence is the narrated one (#502): given the map's sentences and the order of the recording's tracks, it answers the sentence with the latest start at or before the narration's position, with no time limit, and none before the map's first sentence, for a map of another recording, or while paged away. The reader highlights and follows only what it answers.

Page mode, Lyrics mode and Word mode share one following state. A word step in Word mode is an event like a page turn: it pages away and invalidates a jump that is in flight.

The four time windows (500 ms, 1000 ms, 1500 ms and 10 s) are tolerances for epub.js reporting a relocation after the cause. They become named constants with a sentence each on what they wait for. Their values do not change in this work; changing one is a separate change with a measurement.

## Considered options

- **Leave the state in `Reader.tsx` and extract only back to narration.** That fixes the copies but leaves the ordering rules testable only through the browser, where the two open flaky tests in this area (#369, #374) live.
- **A following state per mode.** Switching mode would then need rules for carrying the state over, and the reader has one narration to follow.

## Consequences

- Built behaviour-first: unit tests that drive the module with a scripted event sequence pin each ordering rule as it is today, then `Reader.tsx` is moved onto the module. The `integrated-reader`, `reader-frame` and `position-history` browser tests stay unchanged and must pass with repeats.
- Built in two parts. First the module and the move of `Reader.tsx` onto it, with no behaviour change (#390). Then the one operation for back to narration (#417), the only intended behaviour change, checked in the deployed UI with real media before that issue closes (CLAUDE.md, Conventions). Its browser tests are in `tests/e2e/back-to-narration.spec.ts`.
- This is a slice of the wider reader sync work in #24 and does not touch the fallback rules of #160.
- Issues: #390, #417.
