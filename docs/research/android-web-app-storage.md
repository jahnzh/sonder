# What Firefox and Chrome on Android may store, and when they clear it

Research for issue #479, written 2026-11-16. It feeds the design of "Keep on this device" ([#465](https://github.com/jahnzh/sonder/issues/465)) and the checks on the owner's phone ([#476](https://github.com/jahnzh/sonder/issues/476)). The iPhone counterpart is `installed-web-app-storage.md` (issue #464); this file does not cover iOS.

Scope: Firefox for Android (the owner's daily browser) and Chrome for Android, in a browser tab and as an installed or home-screen web app. Only primary sources are used: MDN and its compatibility data, the browsers' own documentation and release notes, Bugzilla and the Chromium and Mozilla standards-position trackers, the Gecko and Chromium source, developer.chrome.com and web.dev articles by the Chrome team, and Android platform documentation. Where a Mozilla support article would have been the source (SUMO), it could not be read: the site returned a bot challenge to every automated fetch. Each claim carries its source and the date or version it describes.

Versions current when this was written: Firefox 160.0 stable and 161.0 beta ([Mozilla product details](https://product-details.mozilla.org/1.0/firefox_versions.json), read 2026-11-16); Chrome 158.0.8127.36 stable on Android, release record dated 2026-11-12 ([Chromium Dash](https://chromiumdash.appspot.com/fetch_releases?channel=Stable&platform=Android&num=1), read 2026-11-16). The owner's installed versions are not known.

Three kinds of evidence appear below, and they are not equally strong:

- **Documented**: a vendor or a standard says it in prose. The page date is given.
- **Source code**: read on 2026-11-16 from Firefox `main` (commit [`d7161e3`](https://github.com/mozilla-firefox/firefox/commit/d7161e35da7704cff60e48ee86fb7747ffcc93c7), 2026-11-16 04:57 UTC) or Chromium `main` (commit [`b760e58`](https://chromium.googlesource.com/chromium/src/+/b760e58eb02c59981c5d4fa06dbed8c16fe5848e), 2026-11-16 16:18 UTC). It shows what the engine does at `main` today. It is not a promise, and `main` is ahead of Firefox 160 and Chrome 158, so a detail may differ in the shipped build.
- **Inference**: my conclusion from the two above. Always marked.

## Short answers

1. **How much may it store?** Firefox: a best-effort origin gets about 10% of the disk, at most 10 GiB; an origin that is granted persistent storage gets up to 50% of the disk. Chrome: 60% of the disk in both modes. Both compute from the total size of the disk, so free space is the real limit. A tab and an installed app are the same origin in the same browser profile and get the same figures.
2. **When is it cleared?** Both evict least-recently-used origins that are not persistent, and an eviction removes the whole origin. Neither has a "not used for N days" rule that touches a regular app (Firefox has a 13-month archive rule that only runs when its startup is slow). The user clearing site data, clearing the browser's storage in Android settings, and uninstalling the browser all remove it.
3. **How does storage become persistent?** Firefox for Android shows a prompt: "Allow *origin* to store data in persistent storage?". Chrome shows no prompt and decides alone: yes for an origin with an installed web app on Android, or one of the ten "most important" sites by engagement, notifications, bookmarks or home-screen use; otherwise `false`.
4. **Can a save go on in the background?** Chrome has Background Fetch (since 74); Firefox has none. Without it, a save written from the page depends on the page staying alive. Chrome on Android freezes a hidden page one minute after it goes hidden, unless audio is playing. Firefox has no such rule in the source read, but Android's own limits (cached-app freezer, Doze) apply to both. Playing audio keeps both browsers running a foreground service.
5. **Can the page tell Wi-Fi from mobile data?** Chrome for Android: yes, `navigator.connection.type`. Firefox for Android: no, since version 99 (it was exposed in versions 14 to 98).
6. **What is "installed" in Firefox for Android?** A launcher shortcut. One menu item, "Add to Home screen", makes either a standalone web-app shortcut (when the page has a suitable manifest) or a plain bookmark-like shortcut. Neither is an APK, and the source read shows no code path where install status changes quota, eviction or `persist()`.

## Detail

### 1. How much an origin may store

**Firefox for Android.**

- Documented: "the maximum storage space an origin can use in best-effort mode is whichever is the smaller of: 10% of the total disk size where the profile of the user is stored. Or 10 GiB, which is the group limit that Firefox applies to all origins that are part of the same site." "Origins for which persistent storage has been granted can store up to 50% of the total disk size, capped at 8 TiB, and are not subject to the group limit." ([MDN, Storage quotas and eviction criteria](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria), modified 2026-01-05). The page does not distinguish Android from desktop.
- Source code, same arithmetic with no Android branch: the temporary storage limit is half the disk capacity, capped at 8 TiB (`GetTemporaryStorageLimit` in [ActorsParent.cpp](https://github.com/mozilla-firefox/firefox/blob/d7161e35da7704cff60e48ee86fb7747ffcc93c7/dom/quota/ActorsParent.cpp)); the group limit is `min(limit / 5, 10 GB)`, never below 10 MB (`GetGroupLimitForLimit`, same file); a persisted origin is "bound by the global temporary storage limit instead" of the group limit (comment in `GetUsageAndLimit`, same file). That makes the best-effort figure 10% of the disk, as MDN says.
- The disk is the volume that holds the profile directory, measured by its capacity, not by its free space. MDN: "it might not actually be possible for the origin to reach its quota because it is calculated based on the hard drive **total** size, not the currently available disk space."
- Illustration (my arithmetic, not a source figure): on a phone whose data volume reports 100 GB, a tab-grade origin may hold about 10 GB, and a persisted one up to 50 GB.
- Tab versus installed: no difference in the source read. The quota code takes an origin and never asks how the page was opened. The Fenix web-app shell is part of the same app package (see section 6), so the profile and the origin are the same. This last step is inference.
- Disagreement: web.dev says "Firefox allows the browser to use up to 50% of free disk space" ([Storage for the web](https://web.dev/articles/storage-for-the-web), updated 2024-09-23). MDN (2026-01) and the source say 50% of total disk and 10% per group; use those.
- A write that does not fit fails with `QuotaExceededError` on IndexedDB and the Cache API ([web.dev](https://web.dev/articles/storage-for-the-web), 2024-09-23). `src/media-download.ts` already catches this name.

**Chrome for Android.**

- Documented: "an origin can store up to 60% of the total disk size in both persistent and best-effort modes" and "Chrome currently uses at most 80% of the total disk size" ([MDN](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria), 2026-01-05; the page does not name Android).
- Source code: the pool is 80% of the disk (`kPoolSizeRatio` 0.8, [quota_features.cc](https://chromium.googlesource.com/chromium/src/+/b760e58eb02c59981c5d4fa06dbed8c16fe5848e/storage/browser/quota/quota_features.cc)), one origin may use 75% of the pool, which is 60% of the disk (`kDefaultPerStorageKeyRatio`, [quota_settings.cc](https://chromium.googlesource.com/chromium/src/+/b760e58eb02c59981c5d4fa06dbed8c16fe5848e/storage/browser/quota/quota_settings.cc)). Neither file has an Android branch. The file also names two free-space reserves: `should_remain_available` = `min(2 GB, 10% of disk)`, below which eviction starts, and `must_remain_available` = `min(1 GB, 1% of disk)`, which it calls the amount Chrome "attempts to keep free at all costs".
- The figure `estimate()` reports is not the real quota: `kStaticStorageQuota` is enabled by default, "a kill switch for the new reported quota being a static value" ([quota_features.cc](https://chromium.googlesource.com/chromium/src/+/b760e58eb02c59981c5d4fa06dbed8c16fe5848e/storage/browser/quota/quota_features.cc)). The `#464` research cites the matching Chrome 138 announcement.
- Tab versus installed: the same code; installed Chrome web apps use Chrome's profile (section 6).
- On Android the quota code clamps a case where the system reports more free than total space ("On Android, `statvfs()` may return `f_bavail > f_blocks`", [quota_manager_impl.cc](https://chromium.googlesource.com/chromium/src/+/b760e58eb02c59981c5d4fa06dbed8c16fe5848e/storage/browser/quota/quota_manager_impl.cc), crbug.com/501709109). It is the only Android branch in the quota files read.

### 2. When the browser clears it

**Both browsers, documented.** "When an origin's data is evicted by the browser, all of its data, not parts of it, is deleted at the same time." Eviction uses a least-recently-used policy and "skips over origins that have been granted data persistence"; a persistent origin "is only evicted, or deleted, if the user chooses to" ([MDN](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria), 2026-01-05). MDN adds that Chrome's own research "shows that data is very rarely deleted by the browser."

**Firefox for Android, source code.**

- Eviction happens when the global limit is exceeded or when one group exceeds its group limit. In both, it takes inactive, non-persisted origins in order of last access (`CollectOriginsForEviction`, `GetOriginInfosExceedingGroupLimit`, `GetOriginInfosExceedingGlobalLimit` in [ActorsParent.cpp](https://github.com/mozilla-firefox/firefox/blob/d7161e35da7704cff60e48ee86fb7747ffcc93c7/dom/quota/ActorsParent.cpp)). "Inactive" means no open directory lock, so an origin in an open page is skipped. Persisted origins are skipped (`if (originInfo->LockedPersisted()) continue;`).
- I found no trigger in these functions that evicts because the device is short of free space. Firefox's quota is measured against the total disk. What happens on a nearly full phone is not established (section "Not established").
- The only age rule is `dom.quotaManager.unaccessedForLongTimeThresholdSec` = 33,696,000 s (13 months). Its comment: such origins are archived "only when `dom.quotaManager.checkQuotaInfoLoadTime` is true and loading of quota info takes a long time" (21 s, `dom.quotaManager.longQuotaInfoLoadTimeThresholdMs`) ([StaticPrefList.yaml](https://github.com/mozilla-firefox/firefox/blob/d7161e35da7704cff60e48ee86fb7747ffcc93c7/modules/libpref/init/StaticPrefList.yaml); `ArchiveOrigins` in ActorsParent.cpp). The lambda that collects those origins does not test `persisted` in the code shown.
- User action: Fenix "Delete browsing data" → "Cookies and site data" clears cookies, auth sessions and `DOM_STORAGES` ([DeleteBrowsingDataController.kt](https://github.com/mozilla-firefox/firefox/blob/d7161e35da7704cff60e48ee86fb7747ffcc93c7/mobile/android/fenix/app/src/main/java/org/mozilla/fenix/settings/deletebrowsingdata/DeleteBrowsingDataController.kt)). GeckoView maps `DOM_STORAGES` to `CLEAR_DOM_QUOTA` ([GeckoViewStorageController.sys.mjs](https://github.com/mozilla-firefox/firefox/blob/d7161e35da7704cff60e48ee86fb7747ffcc93c7/mobile/shared/modules/geckoview/GeckoViewStorageController.sys.mjs)), the quota manager's clear, which covers IndexedDB and the Cache API (inference from the constant's name; I did not read the service). "Delete browsing data on quit" exists with a per-type "Cookies and site data" item and defaults to off (`shouldDeleteBrowsingDataOnQuit`, `getDeleteDataOnQuit`, [Settings.kt](https://github.com/mozilla-firefox/firefox/blob/d7161e35da7704cff60e48ee86fb7747ffcc93c7/mobile/android/fenix/app/src/main/java/org/mozilla/fenix/utils/Settings.kt)).
- Private browsing: stored data "is usually deleted when the private browsing mode ends" (MDN).

**Chrome for Android, source code.**

- A background evictor runs every 30 minutes (`kEvictionInterval`, [quota_manager_impl.h](https://chromium.googlesource.com/chromium/src/+/b760e58eb02c59981c5d4fa06dbed8c16fe5848e/storage/browser/quota/quota_manager_impl.h)). It evicts when usage passes 70% of the pool (`kUsageRatioToStartEviction`), or when free space is below `should_remain_available` ([quota_temporary_storage_evictor.cc](https://chromium.googlesource.com/chromium/src/+/b760e58eb02c59981c5d4fa06dbed8c16fe5848e/storage/browser/quota/quota_temporary_storage_evictor.cc)). The candidates are buckets with `persistent = 0`, oldest `last_accessed` first (`GetBucketsForEviction`, [quota_database.cc](https://chromium.googlesource.com/chromium/src/+/b760e58eb02c59981c5d4fa06dbed8c16fe5848e/storage/browser/quota/quota_database.cc)). So, unlike Firefox, a nearly full phone does start eviction in Chrome, to the extent that the free space falls below the lower of 2 GB and 10% of the disk.
- No age rule for ordinary apps. A bucket can carry an expiration time (`EvictExpiredBuckets`); that applies only to storage buckets that a page created with an expiry, which Sonder does not.
- User action: Chrome's "Cookies and site data" clears "application caches, Web Storage data, Web SQL Database data, and Indexed Database data", and also site settings and permissions ([Chrome Help: Delete cookies and site data](https://support.google.com/chrome/answer/2392709?co=GENIE.Platform%3DAndroid&hl=en), read 2026-11-16, undated).
- A WebAPK uses Chrome's profile: "if the user clears their Chrome profile, or chooses to delete site data, that will apply to the WebAPK as well" ([web.dev, WebAPKs](https://web.dev/articles/webapks), 2017-05-21, old; it is the Chrome team's own statement, and I found nothing newer that contradicts it).

**Both, platform.** Files in an app's own storage are removed when the user uninstalls the app ([Android Developers, App-specific storage](https://developer.android.com/training/data-storage/app-specific), read 2026-11-16, undated). A browser's profile lives there (inference), so uninstalling the browser removes the profile. The same page says app-specific cache files "might be removed sooner" when space is low; a browser's IndexedDB is not a cache directory, but whether Android's cache clearing reaches Gecko's or Chromium's storage is not documented.

### 3. How storage becomes persistent

**Firefox for Android.**

- Documented: "In Firefox, when a site chooses to use persistent storage, the user is notified with a UI popup that their permission is requested" ([MDN](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria), 2026-01-05). MDN does not say this holds on Android; the source does.
- Source code, Gecko: `StorageManager.cpp` sends `persist()` through a `PersistentStoragePermissionRequest` for the permission `persistent-storage`. In private browsing, or when the permission delegate refuses, it cancels, and the promise resolves to the current state (`false`). Otherwise it asks the embedder ([StorageManager.cpp](https://github.com/mozilla-firefox/firefox/blob/d7161e35da7704cff60e48ee86fb7747ffcc93c7/dom/quota/StorageManager.cpp), `PersistentStoragePermissionRequest::Start`). I found no check for a user gesture and no check for installed status.
- Source code, Fenix: GeckoView hands the request to the app as `PERMISSION_PERSISTENT_STORAGE` ([GeckoPermissionRequest.kt](https://github.com/mozilla-firefox/firefox/blob/d7161e35da7704cff60e48ee86fb7747ffcc93c7/mobile/android/android-components/components/browser/engine-gecko/src/main/java/mozilla/components/browser/engine/gecko/permission/GeckoPermissionRequest.kt)). Fenix has a site permission "Persistent Storage" whose default is "Ask to allow" (`getSitePermissionsPhoneFeatureAction(..., default = Action.ASK_TO_ALLOW)` in Settings.kt; [site_permissions_preferences.xml](https://github.com/mozilla-firefox/firefox/blob/d7161e35da7704cff60e48ee86fb7747ffcc93c7/mobile/android/fenix/app/src/main/res/xml/site_permissions_preferences.xml)). The dialog reads "Allow %1$s to store data in persistent storage?" and offers to remember the choice (`SitePermissionsFeature.kt`, `shouldSelectRememberChoice = true`; text in [strings.xml](https://github.com/mozilla-firefox/firefox/blob/d7161e35da7704cff60e48ee86fb7747ffcc93c7/mobile/android/android-components/components/feature/sitepermissions/src/main/res/values/strings.xml)).
- History: GeckoView first delivered no callbacks for this request, and the bug was fixed in Firefox 68 ([Bug 1527074](https://bugzilla.mozilla.org/show_bug.cgi?id=1527074), 2019-02-11, resolved fixed, target 68). Enabling the Storage API for GeckoView is [Bug 1539429](https://bugzilla.mozilla.org/show_bug.cgi?id=1539429) (2019-03-27, fixed). The code above is `main`, which is later than Firefox 160.
- Once granted, the origin is exempt from eviction and has the 50% limit (section 1, section 2). The user can still clear it.
- A refusal resolves `false` (the `Cancel()` path reports `Persisted()`). Whether a second `persist()` after a refusal asks again depends on whether the user ticked "remember"; the code treats a remembered block as `doNotAskAgain`.

**Chrome for Android.**

- Documented: "Safari and most Chromium-based browsers, such as Chrome or Edge, automatically approve or deny the request based on the user's history of interaction with the site and do not show any prompts to the user" ([MDN](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria), 2026-01-05). web.dev lists the grounds: engagement, installed or bookmarked, notification permission ([Persistent storage](https://web.dev/articles/persistent-storage), 2020-05-12, old).
- Source code: `PersistentStoragePermissionContext::DecidePermission` ([persistent_storage_permission_context.cc](https://chromium.googlesource.com/chromium/src/+/b760e58eb02c59981c5d4fa06dbed8c16fe5848e/chrome/browser/storage/persistent_storage_permission_context.cc)):
  1. Only the top-level origin may be granted.
  2. Not granted when cookies are session-only or blocked for the origin.
  3. Granted when the registrable domain has an installed web app. On Android that means a WebAPK or a Trusted Web Activity (`GetOriginsWithInstalledWebApksOrTwas`, [installable_utils.cc](https://chromium.googlesource.com/chromium/src/+/b760e58eb02c59981c5d4fa06dbed8c16fe5848e/chrome/browser/webapps/installable/installable_utils.cc)).
  4. Granted when the domain is among the ten most important ones (`kMaxImportantResults = 10`). Importance comes from `GetImportantRegisterableDomains` ([important_sites_util.cc](https://chromium.googlesource.com/chromium/src/+/b760e58eb02c59981c5d4fa06dbed8c16fe5848e/chrome/browser/engagement/important_sites_util.cc)): site engagement at least MEDIUM; notification permission allowed; persistent storage already allowed; a bookmark (at most five bookmarks are used, those with the highest engagement when there are more); or a "home screen" signal (`installed_bonus > 0` in the engagement record).
  5. Otherwise the answer is `false`, passed with `persist=false`, meaning the decision is not stored; I read this as: a later `persist()` re-evaluates (inference).
- No prompt in any branch.

### 4. Whether a save can go on in the background

The case: a `fetch` of 4 MiB Range requests, each written to IndexedDB in one transaction, in a loop in the page (`downloadInChunks` in `src/media-download.ts`). The loop resumes from `downloadParts.loaded`, retries four times with growing delays, and keeps completed chunks; an unfinished chunk is lost.

**Background Fetch and Background Sync.**

| API | Firefox for Android | Chrome for Android |
| --- | --- | --- |
| Background Fetch | Not supported. Mozilla's position request [#30](https://github.com/mozilla/standards-positions/issues/30) is open, labelled "under review", last substantive comment 2020-04-15 | Supported since Chrome 74 on desktop; the Android column of the compatibility data mirrors it |
| Background Sync, Periodic Background Sync | Not supported; Mozilla's position on Periodic Background Sync is negative ([#214](https://github.com/mozilla/standards-positions/issues/214), closed 2019-12-12) | Chrome 49 and 80 on desktop, mirrored |

Sources: [MDN browser-compat-data](https://github.com/mdn/browser-compat-data/tree/3cb18048cf3d25701bedc97cb9d72e1bd9470c12/api) (`BackgroundFetchManager.json`, `SyncManager.json`, `PeriodicSyncManager.json`, revision of 2026-11-16, where Android entries say "mirror" of the desktop browser).

Chrome's Background Fetch, documented: "If the user closes pages to your site after step 1, that's ok, the download will continue"; "On some platforms (such as Android) it's possible for the browser to close after step 1"; "Chrome's implementation currently only accepts requests without a body" and does not support requests "that would require a CORS preflight"; when it succeeds the service worker gets `backgroundfetchsuccess` and must copy the responses into storage, because "After this event, the fetched requests and responses are no longer accessible" ([Introducing Background Fetch](https://developer.chrome.com/blog/background-fetch), updated 2018-12-03, old). The specification is a WICG draft ([wicg.github.io/background-fetch](https://wicg.github.io/background-fetch/), 2021-04-21). Whether Sonder's authenticated Range requests would be accepted is not established; the article does not mention request headers.

**Chrome for Android, page running in the background.**

- Source code: the "stop in background" scheduler feature is enabled by default on Android (not on Cast or desktop Android): "Freeze scheduler task queues in background after allowed grace time" (`kStopInBackground`, [features.cc](https://chromium.googlesource.com/chromium/src/+/b760e58eb02c59981c5d4fa06dbed8c16fe5848e/third_party/blink/common/features.cc)). The default grace is one minute: `kDefaultDelayForBackgroundTabFreezing = base::Minutes(1)`, counted from the later of the page becoming hidden and the last change in audio state ([page_scheduler_impl.cc](https://chromium.googlesource.com/chromium/src/+/b760e58eb02c59981c5d4fa06dbed8c16fe5848e/third_party/blink/renderer/platform/scheduler/main_thread/page_scheduler_impl.cc)). A field trial can change the delay; I have not seen the live value.
- A page that is playing audio is not "backgrounded": `IsBackgrounded() = !IsPageVisible() && !IsAudioPlaying() && ...` (same file). So with a book playing, the freeze does not start; when the audio stops, the clock restarts from that moment.
- What a frozen page cannot do: Chrome's Page Lifecycle article says "In the frozen state the browser suspends execution of freezable tasks in the page's task queues until the page is unfrozen. This means things like JavaScript timers and fetch callbacks don't run" ([Page Lifecycle API](https://developer.chrome.com/docs/web-platform/page-lifecycle-api), updated 2026-10-16). Inference: a `fetch` body read stalls until the page is shown again, and the download loop resumes by itself because it reads chunks in a `while` loop. The article does not describe Android specifically.
- Chrome's media notification controller "manages the notification, foreground service, and `MediaSessionCompat`" for a playing session ([MediaNotificationController.java](https://chromium.googlesource.com/chromium/src/+/b760e58eb02c59981c5d4fa06dbed8c16fe5848e/components/browser_ui/media/android/java/src/org/chromium/components/browser_ui/media/MediaNotificationController.java)).
- A service worker does not carry a download either: MDN lists that Chrome is likely to stop one that "has been idle for 30 seconds", "running synchronous JavaScript for 30 seconds", or a `waitUntil()` promise "taken more than 5 minutes" ([MDN, Offline and background operation](https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps/Guides/Offline_and_background_operation), modified 2026-09-13).

**Firefox for Android, page running in the background.**

- Source code: timers in a background window are clamped to 1000 ms (`dom.min_background_timeout_value`) and budget-throttled (`dom.timeout.enable_budget_timer_throttling` true) ([StaticPrefList.yaml](https://github.com/mozilla-firefox/firefox/blob/d7161e35da7704cff60e48ee86fb7747ffcc93c7/modules/libpref/init/StaticPrefList.yaml)). That slows timers; it does not stop network reads. I found no Gecko counterpart of Chrome's one-minute freeze in the files read.
- While media plays, Fenix runs a foreground service: `handleMediaPlaying` calls `startForeground` and requests audio focus; pausing (not transiently) stops it ([MediaSessionServiceDelegate.kt](https://github.com/mozilla-firefox/firefox/blob/d7161e35da7704cff60e48ee86fb7747ffcc93c7/mobile/android/android-components/components/feature/media/src/main/java/mozilla/components/feature/media/service/MediaSessionServiceDelegate.kt)). Gecko also holds an `audio-playing` wake lock while an audio element plays ([HTMLMediaElement.cpp](https://github.com/mozilla-firefox/firefox/blob/d7161e35da7704cff60e48ee86fb7747ffcc93c7/dom/media/mediaelement/HTMLMediaElement.cpp), `CreateAudioWakeLockIfNeeded`).

**The operating system, both browsers.**

- Android Doze: when the device is "unplugged and stationary for a period of time, with the screen off", the system "suspends network access", "ignores wake locks" and defers jobs; it leaves Doze periodically for "a brief maintenance window" ([Optimize for Doze and App Standby](https://developer.android.com/training/monitoring-device-state/doze-standby), read 2026-11-16, undated). The page does not say whether playing audio from a foreground service keeps a device out of Doze.
- App Standby does not apply to "an app [that] has a process currently in the foreground, either as an activity or foreground service" (same page).
- Cached-app freezer: "App processes in the cached state are frozen 10 seconds after entering the cached state" (Android 14 and higher); "Android 11 (API level 30) or higher supports the cached apps freezer" ([Android Open Source Project](https://source.android.com/docs/core/perf/cached-apps-freezer), read 2026-11-16, undated). The page does not say it is on by default.
- Inference: a browser with no visible activity and no foreground service becomes a cached process and can be frozen within seconds on newer Android. That would stop a page-driven save in either browser, whatever the browser's own rules say. A foreground service (playing audio) is the case that avoids it.

**Screen Wake Lock** keeps the screen from turning off while the page is visible: "prevents the screen from turning off, dimming or locking", and "previously acquired locks are automatically released when document becomes inactive" ([MDN, Screen Wake Lock API](https://developer.mozilla.org/en-US/docs/Web/API/Screen_Wake_Lock_API), modified 2026-11-12). Chrome 84; Firefox 126 on desktop, mirrored for Android in the compatibility data. It helps a save that runs with the app in front and does nothing once the user locks the phone.

### 5. Telling Wi-Fi from mobile data

| Browser | `navigator.connection` | `connection.type` |
| --- | --- | --- |
| Chrome for Android | Yes, since 38 | Yes, since 38 |
| Firefox for Android | Versions 14 to 98 only; removed in 99 | Versions 31 to 98 only |

Sources: [MDN browser-compat-data, NetworkInformation.json and Navigator.json](https://github.com/mdn/browser-compat-data/tree/3cb18048cf3d25701bedc97cb9d72e1bd9470c12/api) (2026-11-16); [Firefox 99 release notes](https://developer.mozilla.org/en-US/docs/Mozilla/Firefox/Releases/99): the API "was previously enabled on Android (only), but is now disabled by default on all platforms. This API is on the path for removal because it exposes a significant amount of user information that might be used for fingerprinting" ([Bug 1637922](https://bugzilla.mozilla.org/show_bug.cgi?id=1637922), fixed, target 99); `dom.netinfo.enabled` is `false` in `main` ([StaticPrefList.yaml](https://github.com/mozilla-firefox/firefox/blob/d7161e35da7704cff60e48ee86fb7747ffcc93c7/modules/libpref/init/StaticPrefList.yaml)).

- `type` returns one of "bluetooth", "cellular", "ethernet", "none", "wifi", "wimax", "other", "unknown" ([MDN, NetworkInformation.type](https://developer.mozilla.org/en-US/docs/Web/API/NetworkInformation/type), modified 2024-03-24). The Chrome `saveData` flag is Chrome 65 and later; Firefox has none (compatibility data).
- Mozilla's standards position on the API is negative, because `type` and `downlinkMax` "expose information that a site cannot measure" ([standards-positions #117](https://github.com/mozilla/standards-positions/issues/117), closed 2020-04-15, cited as read in the #464 research).
- Consequence: in Firefox for Android a page cannot tell Wi-Fi from mobile data by any API I found. Installed status does not change this. Whether Chrome's `wifi` value means "unmetered" is not established: `type` names the radio, not the cost of the connection.

### 6. What "installed" means in Firefox for Android

Everything here is source code of Fenix at `main` (commit `d7161e3`); the Mozilla support article on web apps could not be read (bot challenge, see the top).

- One menu item, "Add to Home screen" ([strings.xml](https://github.com/mozilla-firefox/firefox/blob/d7161e35da7704cff60e48ee86fb7747ffcc93c7/mobile/android/fenix/app/src/main/res/values/strings.xml)). The shortcut manager then chooses ([WebAppShortcutManager.kt](https://github.com/mozilla-firefox/firefox/blob/d7161e35da7704cff60e48ee86fb7747ffcc93c7/mobile/android/android-components/components/feature/pwa/src/main/java/mozilla/components/feature/pwa/WebAppShortcutManager.kt), `requestPinShortcut`):
  - If the tab has an "installable manifest", it pins a web-app shortcut that launches `WebAppLauncherActivity`. An installable manifest means a secure page, a `display` other than `browser`, and an icon of at least 192×192 with purpose `any` or `maskable` ([SessionState.kt](https://github.com/mozilla-firefox/firefox/blob/d7161e35da7704cff60e48ee86fb7747ffcc93c7/mobile/android/android-components/components/feature/pwa/src/main/java/mozilla/components/feature/pwa/ext/SessionState.kt), [WebAppManifest.kt](https://github.com/mozilla-firefox/firefox/blob/d7161e35da7704cff60e48ee86fb7747ffcc93c7/mobile/android/android-components/components/feature/pwa/src/main/java/mozilla/components/feature/pwa/ext/WebAppManifest.kt)). Sonder's `public/manifest.webmanifest` (display `standalone`, 192 and 512 icons) meets all three.
  - Otherwise it pins a basic shortcut that opens the URL with `ACTION_VIEW` in the browser.
- Both are Android launcher shortcuts (`ShortcutManagerCompat.requestPinShortcut`). Neither is an APK, and neither appears as a separate app in the app drawer by itself.
- Launch: `WebAppLauncherActivity` reads the stored manifest; for display `standalone`, `fullscreen` or `minimal-ui` it starts the web-app shell with `ACTION_VIEW_PWA` inside the same package; with no stored manifest, or `browser`, it opens the browser ([WebAppLauncherActivity.kt](https://github.com/mozilla-firefox/firefox/blob/d7161e35da7704cff60e48ee86fb7747ffcc93c7/mobile/android/android-components/components/feature/pwa/src/main/java/mozilla/components/feature/pwa/WebAppLauncherActivity.kt)).
- "Installed" inside the app is a stored manifest that was used in the last 30 days (`getWebAppInstallState`, `ManifestStorage.ACTIVE_THRESHOLD_MS` = 30 days, [ManifestStorage.kt](https://github.com/mozilla-firefox/firefox/blob/d7161e35da7704cff60e48ee86fb7747ffcc93c7/mobile/android/android-components/components/feature/pwa/src/main/java/mozilla/components/feature/pwa/ManifestStorage.kt)). It is bookkeeping for the menu and for the shell; none of the quota, eviction and permission code read above consults it.
- Does it change anything above? In the source read, no: quota (section 1), eviction (section 2) and the `persist()` prompt (section 3) have no installed branch; the shell and the browser share one package and so, by inference, one Gecko profile and one origin. Section 4: the shell is an activity of the same app, so the foreground-service and Android rules apply the same way.
- Firefox for Android does not mint an APK as Chrome does. Removing the home-screen icon removes the shortcut; what it does to the stored manifest and to site data is not established. `removeManifests` exists, and I did not trace its callers.

**Chrome for Android, for comparison.** Chromium's Android architecture document names three systems: WebAPK (a real APK minted by a server, "thin shells that load Chrome to render the content"), standard Trusted Web Activities (which "share cookies and storage with the user's main Chrome profile") and an auto-minted TWA ([android_architecture.md](https://chromium.googlesource.com/chromium/src/+/b760e58eb02c59981c5d4fa06dbed8c16fe5848e/components/webapps/docs/android_architecture.md)). The Chrome team's WebAPK article says "Chrome uses the current profile to store any data, and it will not be segregated away" ([web.dev](https://web.dev/articles/webapks), 2017-05-21, old). In Chrome, installed status does matter, for exactly one thing found: `persist()` is granted to a domain with an installed WebAPK or TWA (section 3). The uninstall flow in the architecture document ends in metrics and has no step that clears site data.

## Where the sources disagree or say nothing

- **Firefox quota.** web.dev (2024-09-23): 50% of free disk. MDN (2026-01-05) and the source: 10% of total disk, at most 10 GiB, per group; 50% of total disk when persisted. Use MDN and the source.
- **Who gets a prompt.** MDN says Firefox prompts and does not mention Android; the Fenix source confirms a prompt for Android. web.dev (2020-05-12) says Chrome decides without a prompt, as the Chromium source does.
- **Quota figure in `estimate()`.** web.dev says the reported quota can exceed the real one; Chromium reports a static figure by default. Neither is the ceiling.
- **Chrome WebAPK storage.** The only statement that WebAPK storage is Chrome's profile is the 2017 web.dev article; the 2026 architecture document says it for TWAs and calls WebAPKs "thin shells that load Chrome". A Chromium issue that I could not open ([40733514](https://issues.chromium.org/issues/40733514), "PWA could have a standalone/dedicated storage") shows the question has been raised; I did not read it.
- **Firefox on Android and Network Information.** The compatibility data and the release notes agree that it was on in Android until 98. Mozilla's own note speaks of a "path for removal"; the pref is `false` and the bug is fixed.

## Not established from primary sources

- **Firefox for Android: what happens on a nearly full phone.** The quota code measures the total disk and has no free-space trigger in the functions read; whether the app or the OS reports a full disk as `QuotaExceededError`, `UnknownError` or an aborted transaction is not documented.
- **Firefox for Android: whether a page-driven save continues behind a locked screen** with no audio playing, and how long after backgrounding the process stays unfrozen. The sources give Android's 10-second cached-app freezer (Android 14 and later, default not stated) and Doze (device stationary), and no Gecko rule. Needs the phone.
- **Whether playing audio keeps a save running** with the screen locked, in either browser. Chrome's source says an audible page is not frozen; Fenix and Chrome start a foreground service; neither vendor says a download in the same page continues. Doze's treatment of a device playing audio is not stated.
- **What a frozen `fetch` does when the page returns** in Chrome: reject, or continue. Not documented.
- **Chrome's live freeze delay.** The source default is one minute; a field trial can differ.
- **Whether Background Fetch accepts Sonder's requests** (authenticated, a `Range` header). The article names only the body and preflight limits.
- **Firefox install: what removing the home-screen shortcut does to site data**, and what the Mozilla support article says on web apps (unreadable).
- **Chrome: what uninstalling a WebAPK does to site data.** The architecture document lists no clearing step.
- **Whether Android's "Clear cache" or "Clear storage" for the browser reaches IndexedDB in each browser.** Only uninstalling is documented.
- **Whether a `persist()` call made without a tap, or while the app is in the background, shows Firefox's prompt.** No gesture check in the Gecko code; Fenix's prompt behaviour in that case is untested.
- **Whether Chrome's `connection.type` is `wifi` on a mobile hotspot** and so whether it can stand in for "unmetered".
- **Versions on the owner's phone**, so which of the source-level facts above apply.
- **Single-source statements**, none corroborated by a second primary source: Firefox's 13-month archive rule (StaticPrefList.yaml and `ArchiveOrigins` only); Chrome's 1-minute freeze on Android (Blink source only); Chrome's grant rules for `persist()` (Chromium source, with web.dev's older, less specific list); the Fenix prompt and its default (Fenix source only); the Fenix shortcut and web-app logic (Fenix source only); WebAPK sharing Chrome's profile (a 2017 article); the one-menu-item behaviour.
